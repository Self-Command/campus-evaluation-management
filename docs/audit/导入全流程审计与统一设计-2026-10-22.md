# 全量导入安全审计与统一设计报告

日期：2026-10-22  
状态：**待用户审批。报告完成前未修改导入代码、数据库结构或数据库数据，未执行修复后的导入测试。**  
范围：账号导入、成绩导入、参与名单导入，以及三类内置模板、权限范围内的全部角色入口。  
依据：代码只读审计、现有集成测试阅读、本地开发库 `campus_dev` 只读聚合核对。未连接生产库。

---

## 一、结论摘要

1. **用户报告的重复学生账号已在本地开发库复现并确认。** 同一姓名、同一学院、同一专业、同一班级存在两个学生账号；两个学号均为 8 位且仅相差 1 位数字，数据库唯一约束因此没有拦住。
2. **根因不是数据库唯一键失效，而是账号导入只按“学号（login）”判重。** 同一自然人在学号录错一位后，会被当成另一名学生，预览为 `NEW`，提交后直接创建第二个账号。
3. **该问题不只在账号导入。** 成绩导入、参与名单导入会逐一校验学号、姓名、学院、专业、班级，但两个账号各自都有完整档案时，系统无法知道它们属于同一个人；后续成绩、扣分、参与、申报会被拆到两个账号，排名和发布结果失真。
4. **手动建号和资料修改同样可绕过。** `createAccount`、`updateAccount`、`updateStudentProfile` 都没有“同班同名但不同学号”的阻断，只修导入会被手动入口绕过。
5. 现有账号导入是 `ADMIN` 独占；成绩导入是 `ADMIN` 直接生效、`COUNSELOR` 提交学院审核；参与名单导入是 `ADMIN`、`COLLEGE`（本学院活动）、`PUBLISHER`（本人历史活动）。本轮不建议扩大导入角色。
6. 另发现两项确定的功能缺陷：参与名单页面宣称支持 5MB/2000 条，但通用请求体上限实际为 1.1MB；参与名单模板无论固定分还是逐人分都带“活动得分”列，与固定分活动“得分列留空”的规则冲突。
7. **建议的总体方案：** 建立统一的“学生身份判重 + 模板注册 + 文件指纹 + 服务端范围校验 + 预览快照 + 整批事务 + 幂等重放 + 重复身份例外审计”管线；同班同名不同学号默认阻断，只有管理员填写理由并明确确认“确为两名不同学生”才允许放行。存量重复账号另走停用/合并工具，不自动删除。

## 二、已确认的高危问题与现场证据

### 2.1 现场核对结果

对本地开发库做只读聚合查询，结果如下（不记录姓名、完整学号等个人信息）：

| 核对项 | 结果 |
| --- | --- |
| 学生账号总数 | 13 |
| 重复学号（`StudentProfile.studentNumber` 相同） | 0 组；数据库唯一约束正常 |
| 同姓名 + 同学院 + 同专业 + 同班级的账号 | **1 组，共 2 个账号** |
| 两个学号的关系 | 同为 8 位，仅 1 位数字不同 |
| 较早账号 | 创建于 2026-10-21 03:27，早于导入；无 `ACCOUNT_IMPORTED` 审计 |
| 较晚账号 | 创建于 2026-10-21 18:16；有 `ACCOUNT_IMPORTED` 审计 |
| 导入批次 | 1 个 `COMMITTED` 批次，仅 1 行，结果 `{created:1, skipped:0}` |
| 业务记录分布 | 较早账号承载成绩、扣分、参与、申报、发布结果等记录；较晚账号暂无这些业务记录，仅有学生档案和班级归属 |

### 2.2 根因定位

`src/server/account-import.ts` 的预览逻辑只做两类判重：

- 查询已有账号：`where: { login: { in: ... } }`，只按学号匹配；
- 文件内判重：只比较 `login`，同一文件内学号完全相同才标记重复。

因此：

```text
已有账号：姓名=某学生，班级=某班，学号=XXXXXXXX
导入文件：姓名=某学生，班级=某班，学号=XXXXXXXZ  （仅 1 位不同）
```

两个学号都唯一，预览结果为 `NEW`，提交后创建第二个账号。数据库的 `User.login @unique` 和 `StudentProfile.studentNumber @unique` 只能防止“同一学号重复”，不能防止“同一人换一个学号”。

现有测试 `tests/integration/account-import.test.ts` 覆盖了同一学号重复、错误整批拒绝、并发与重放，但**没有覆盖同姓名同班级不同学号**，所以测试通过不代表该风险已关闭。

### 2.3 影响评估

- 同一学生的成绩、扣分、参与、申报、发布结果可能被拆到两个账号，班级排名、学院汇总和最终结果失真。
- 两个账号都可登录、都可被导入、都可能被辅导员或学院审核，后续合并成本高。
- 如果只修账号导入，手动建号、账号编辑、学生资料修改仍可制造同样的重复。
- 如果只新增“同班同名”数据库唯一约束，会误伤真实同名的两名学生，不可取；必须采用“默认阻断 + 管理员例外确认 + 审计”的方式。

**风险等级：高。** 在修复和存量清理完成前，不应把“导入已安全”作为交付结论。

## 三、导入清单与当前实现

### 3.1 三类导入

| 导入 | 页面/接口 | 当前允许角色 | 当前模板 | 当前行数/大小 |
| --- | --- | --- | --- | --- |
| 学生账号导入 | `/imports?kind=accounts`；`POST /api/admin/account-import` | `ADMIN` | `学生账号模板-v1.csv`：学号、姓名、学院、专业、班级 | 100 行 / 1MB |
| 成绩导入 | `/imports?kind=grades`；`POST /api/grade-import` | `ADMIN`、`COUNSELOR` | `成绩输入模板-v2.csv`：学号、姓名、学院、专业、班级、成绩 | 100 行 / 1MB |
| 参与名单导入 | `/imports?kind=participation`；`POST /api/participation-import` | `ADMIN`、`COLLEGE`、`PUBLISHER` | `活动参与名单模板-v3.csv`：学号、姓名、学院、专业、班级、活动得分 | 2000 行 / 5MB（实际请求体被 1.1MB 截断） |

除此之外，证明附件上传、品牌图片上传属于文件上传，不是名单导入，不纳入本报告的三类模板测试；其文件类型、大小和授权仍按既有证据/品牌资源规则执行。

### 3.2 现有防线

已经具备且应保留的部分：

- 路由层同源校验、会话实时校验、角色校验、强制改密阻断、限流。
- 成绩导入：六列身份核对；辅导员只能导入自己负责班级；管理员可按已发布名单快照核对。
- 参与名单：五列身份核对、班级/辅导员/学院/专业启用状态核对、活动范围核对、固定分/逐人分规则、整批错误阻断。
- 参与名单：首次名单封存、补录更正、活动修订基线、事务锁、重放。
- 账号导入：整批事务、同一学号重复跳过/冲突报错、预览过期、提交重放、初始密码只返回一次。
- 文件解析：UTF-8 CSV、XLSX ZIP 结构限制、公式/宏/外部链接拒绝、数字学号拒绝、行数/列数/大小限制。
- 数据库：`User.login` 唯一、`StudentProfile.studentNumber` 唯一、`GradeInput(termId, studentId, nodeId)` 唯一、`Participation(activityId, studentId)` 唯一。

### 3.3 关键缺口

| 缺口 | 影响 | 涉及 |
| --- | --- | --- |
| 只按学号判重，无同班同名不同学号检测 | 可创建重复学生账号 | 账号导入、手动建号、账号编辑、学生资料修改 |
| 成绩/参与只认学号，不识别“同一人两个账号” | 业务数据被拆分 | 成绩导入、参与名单导入 |
| 账号导入无说明/原因字段 | 无法追溯为什么建这批账号 | `AccountImport` |
| 导入批次无文件指纹、模板版本 | 无法证明导入的是哪份文件、哪个模板 | 三个批次模型 |
| 模板接口只校验角色，不校验周期/活动范围 | 可下载与当前活动分制不匹配的模板 | `import-templates` |
| 参与名单模板固定分也带得分列 | 用户照模板填写后被整批拒绝 | 模板、页面文案 |
| 请求体 1.1MB 硬上限与 5MB 文案冲突 | 大名单无法上传，错误信息也写 1MB | `boundedForm`、参与导入路由 |
| 表头允许空名/重名，CSV/XLSX 可被错误映射 | 列错位后可能导入错误数据 | `spreadsheet`、映射界面 |
| 无预览审计、无行级结果留存 | 出事只能看最终计数 | 三个批次、审计事件 |
| 无存量重复账号核查/合并工具 | 已发生的重复无法安全处置 | 账号管理 |

## 四、统一设计

### 4.1 设计原则

1. **学号是学生身份的权威键，但不是唯一判重条件。** 学号唯一约束继续保留；同班同名不同学号必须进入人工确认，不得静默创建。
2. **服务端决定身份、范围和模板，客户端只提交文件与选择项。** 不信任客户端传来的学院、班级、活动归属、列映射或角色范围。
3. **默认阻断，例外留痕。** 疑似重复默认不能提交；只有管理员明确确认“确为两名不同学生”并填写理由才可放行，例外记录永久保留。
4. **预览只读，提交整批事务。** 预览不写业务数据；提交时任一行失败则整批不写入。
5. **同一份预览只能提交一次。** 批次、文件指纹、快照、幂等键共同防止重复提交和并发重复创建。
6. **模板、解析、导入共用一份模式定义。** 不允许模板是手写字符串、解析器另写一套、导入再写一套。
7. **存量数据先核实再处置。** 不自动删除账号，不自动猜测哪条成绩属于哪个人；先停用、再按明确规则合并。

### 4.2 统一导入管线

```text
选择导入类型和业务上下文（周期/成绩模块/活动）
        ↓
服务端生成或校验模板版本
        ↓
上传文件 → 大小/类型/ZIP/公式检查 → 计算 SHA-256
        ↓
解析首个工作表 → 校验表头唯一、字段完整、无合并/空表头
        ↓
规范化（NFKC、去首尾空白、去零宽字符、保留文本前导零）
        ↓
服务端解析组织、周期、活动、成绩模块、角色范围
        ↓
身份核对 + 学号判重 + 同班同名判重 + 业务状态核对
        ↓
生成预览批次：文件指纹、模板版本、范围键、快照、逐行状态
        ↓
用户核对；疑似重复必须逐项选择“跳过/使用已有/确认两人不同”
        ↓
提交：重新校验会话、角色、范围、快照、重复候选、活动状态
        ↓
账户锁/周期锁/活动锁 → 整批写入 → 行级结果 → 审计 → 返回结果
```

### 4.3 学生身份判重规则

#### 4.3.1 规范化

- 学号：文本单元格，NFKC 规范化，去除首尾空白和零宽字符；禁止数字单元格、内部空白、控制字符。
- 姓名：NFKC，去除首尾空白，判重键去除所有空白并统一大小写；显示仍保留原文。
- 学院/专业/班级：不使用客户端文本作为权限依据；服务端解析为 `collegeId`、`majorId`、`classId`，要求启用且班级已配置有效辅导员。
- 班级优先用 `classId` 判重；历史无 `classId` 的档案用 `(college, major, className)` 兜底。

#### 4.3.2 判定顺序

| 场景 | 处理 |
| --- | --- |
| 文件内学号完全重复，且五列信息一致 | `SKIP`，说明“文件内重复，保留首行” |
| 文件内学号完全重复，但信息不一致 | `ERROR`，整批阻断 |
| 已有账号同学号、同姓名、同班级 | `SKIP`，说明“已存在，不重复创建” |
| 已有账号同学号，但姓名/班级不一致 | `ERROR`，提示核对学号或档案 |
| 同班同名，但学号不同（无论差几位） | **`DUPLICATE_IDENTITY`，默认阻断** |
| 同班同名，学号仅 1 位不同 | **`LIKELY_DUPLICATE`，默认阻断，提示优先核对学号** |
| 同名但在不同班级 | 警告，不阻断；可能是转专业或重名 |
| 同一人已有账号，但状态为停用 | 默认阻断，要求管理员先确认是恢复还是新建 |

#### 4.3.3 例外确认

- 账号导入仅 `ADMIN` 可确认例外。
- 例外必须同时满足：
  1. 管理员看到两个账号的学号、姓名、班级、创建时间和业务记录数量；
  2. 选择“确为两名不同学生”，填写不少于 10 个字符的理由；
  3. 服务端再次确认两个学号确实不同、两个账号都属于同一班级；
  4. 写入 `DuplicateIdentityException`（或等价审计表），记录操作人、时间、批次、两个学号、理由。
- 未确认的疑似重复不能通过“忽略警告”绕过；接口必须拒绝。
- 同一组例外只对当次新建有效，不自动授权以后继续新建第三个同名学生。

#### 4.3.4 手动入口同步

以下入口必须调用同一个身份检查服务：

- `createAccount`：新建学生账号前；
- `updateAccount`：修改姓名、学号、角色、班级时；
- `updateStudentProfile`：修改姓名或班级时；
- 账号导入：预览和提交时；
- 成绩导入、参与名单导入：身份核对时检查目标学生是否存在未处置的疑似重复。

只修账号导入而保留手动入口，等于留下同等风险的旁路。

### 4.4 预览、提交、幂等与并发

每个批次保留：

| 字段 | 用途 |
| --- | --- |
| `fileHash` | 文件 SHA-256，证明预览对应哪份文件 |
| `templateVersion` | 模板版本，拒绝旧模板/错模板 |
| `scopeKey` | 角色 + 周期 + 模块/活动 + 班级范围的服务端规范键 |
| `snapshot` | 已有账号、组织、活动、成绩、参与事实、证据版本等快照 |
| `rows` | 规范化后的输入行 |
| `confirmations` | 疑似重复的处理选择与理由 |
| `requestId` | 提交幂等键，重放返回原结果 |
| `status` | `PREVIEW` / `COMMITTED` / `EXPIRED` / `REJECTED` |
| `result` | 创建、跳过、更新、提交审核等计数；不含密码 |
| `expiresAt` | 预览有效期 |
| `rowResults` | 行号、规范化身份、状态、错误码、消息、处理结果 |

提交时按固定顺序加锁：

```text
账户共享锁或独占锁 → 周期锁 → 活动锁 → 事务写入
```

现有 `adminTransaction`、`termTransaction`、活动锁已基本遵循该顺序，修复时保持，禁止反向嵌套。

提交必须重新核对：

- 会话未撤销、未过期、角色未变、未被强制改密；
- 批次属于当前操作人、未过期、未提交；
- 文件指纹和模板版本一致；
- 组织、班级、辅导员、周期阶段、活动状态未变；
- 学生身份、重复候选、业务状态未变；
- 行级错误为零，疑似重复均已处置；
- 同一 `requestId` 重放返回原结果，不重复创建。

### 4.5 模板设计

新增单一来源 `src/lib/imports/templates.ts`（名称可在实施时调整），由模板接口、解析器、预览和测试共同引用。

| 模板 | 版本 | 固定表头 |
| --- | --- | --- |
| 学生账号 | v2 | `学号,姓名,学院,专业,班级` |
| 成绩输入 | v3 | `学号,姓名,学院,专业,班级,成绩` |
| 参与名单·固定分 | v4 | `学号,姓名,学院,专业,班级` |
| 参与名单·逐人分 | v4 | `学号,姓名,学院,专业,班级,活动得分` |

规则：

- 账号模板表头保持五项；页面明确说明“学号同时作为登录账号”。
- 成绩模板仍按一个成绩模块导入；模块由页面选择，服务端校验模块属于当前周期且为成绩节点。模板文件名可带模块名，但表头保持稳定。
- 参与模板必须根据活动 `scoreMode` 生成：固定分不带得分列，逐人分带“活动得分”；页面文案与模板保持一致。
- 模板接口接收并校验 `kind`、`termId`、`activityId`（参与）、`nodeId`（成绩），权限与实际上传接口完全一致；不能只凭角色下载。
- 模板只输出表头和必要说明，**不放入可被误导入的示例学生行**。示例放在页面说明或独立说明文件，不放在首个工作表。
- 响应增加模板版本、文件名、`private, no-store`；不缓存。
- 旧模板仍可被识别时，给出明确“请下载最新模板”错误；不在服务端猜测旧列位置。

### 4.6 表头与文件安全

- 表头必须唯一、非空；拒绝重复表头、空表头、合并单元格表头、多行表头。
- 账号/成绩允许“系统模板列顺序不同但语义完整”的映射；参与名单沿用严格中文表头。任何映射都必须由服务端按语义字段解析，不能按客户端列号直接信任。
- 拒绝公式、宏、外部链接、损坏 ZIP、超 ZIP 条目/解压体积、非 UTF-8 CSV、列数不一致、超过行数/列数/大小的文件。
- 学号必须是文本单元格；保留前导零；数字单元格直接拒绝。
- 统一请求体上限：账号/成绩 1MiB；参与名单 5MiB；解析器行数上限分别为 100/100/2000。`boundedForm` 增加显式上限参数，不再固定 1.1MB。
- 错误信息面向用户，不返回数据库路径、堆栈、文件内容、密码或完整内部标识。
- 预览和日志不记录初始密码；账号导入的初始密码只在成功响应中返回一次。

### 4.7 审计

新增/补齐：

- `IMPORT_PREVIEWED`：批次、类型、范围、文件指纹、模板版本、行数、错误数。
- `IMPORT_COMMITTED`：批次、创建/跳过/更新/提交审核数量、耗时。
- `IMPORT_REJECTED`：拒绝原因（快照变化、重复未处置、越权、过期）。
- `DUPLICATE_IDENTITY_CONFIRMED`：管理员例外确认，含两个学号、班级、理由。
- `ACCOUNT_MERGED` / `ACCOUNT_DISABLED_DUPLICATE`：存量处置。
- 行级结果保留在批次中；不把完整文件、密码、证明文件二进制写入审计。

### 4.8 数据库与约束

保留现有唯一约束，新增建议（实施前需审批并做迁移）：

- 三个导入批次模型增加 `fileHash`、`templateVersion`、`scopeKey`、`requestId`、`rowResults`、`confirmations`、`committedAt` 等字段。
- 新增 `DuplicateIdentityException`：记录同班同名不同学号的例外确认。
- `User` 增加可选的 `mergedIntoId`（自关联）或等价的合并审计关系；不删除被合并账号。
- **不新增“同班同名”唯一索引。** 真实同名同班可能合法，数据库唯一索引会造成误伤；由服务端默认阻断 + 管理员例外解决。
- 对 `GradeInput`、`Participation` 的现有唯一约束继续作为最后防线；导入事务内仍逐行核对，不能只依赖数据库报错。

## 五、三类导入的具体设计

### 5.1 学生账号导入（`ADMIN`）

#### 流程

1. 管理员选择“学生账号导入”，下载 v2 模板。
2. 上传 CSV/XLSX；服务端解析并显示前 3 行样例，仅用于确认列映射；不创建账号。
3. 管理员确认五列映射（默认按模板自动映射），填写本批说明（例如“2026 级新生名单”）。
4. 预览表显示：行号、学号、姓名、学院/专业/班级、状态、说明。状态至少包括：
   - `新增`
   - `跳过：已存在`
   - `跳过：文件内重复`
   - `疑似重复：同班同名，学号不同`
   - `错误：学号/姓名/组织不一致`
5. 对每个疑似重复，管理员必须选择：
   - 跳过该行；
   - 使用已有账号（不新建）；
   - 确为两名不同学生（仅管理员、填理由、二次确认）。
6. 提交后整批事务创建；返回创建数、跳过数；初始密码只在成功结果中显示一次，提示立即保存，服务端不提供二次查看。
7. 提交失败不留下半批账号；重放不重复创建。

#### 身份与范围

- 账号导入仅 `ADMIN`；本轮不放开给学院或辅导员。
- 学院、专业、班级必须解析到唯一、启用、已配置辅导员的正式班级。
- 学号作为登录名和学生学号，必须全局唯一；已有学生档案的学号不允许通过账号编辑修改。
- 同班同名不同学号默认阻断；同班同名同学号冲突直接错误。
- 手动建号、账号编辑、学生资料修改使用同一套检查。

#### 存量处置

- 先提供只读“疑似重复账号”清单，按同班同名分组，显示每个账号的创建时间、学号、业务记录计数、是否停用。
- 处置顺序：
  1. 停用明显错误的账号，阻止继续登录和新数据写入；
  2. 对无业务记录的重复账号，确认后停用并记录 `mergedIntoId`；
  3. 对有业务记录的账号，逐项选择保留值，事务内迁移成绩、扣分、参与、申报、发布结果等关联记录；
  4. 不删除历史，不覆盖审计。
- 本地开发库这一组：较早账号承载业务记录，较晚导入账号暂无成绩/扣分/参与/申报/发布结果，适合先停用较晚账号；最终处置需用户审批后在隔离环境执行并记录。

### 5.2 成绩导入（`ADMIN`、`COUNSELOR`）

#### 流程

1. 选择周期和成绩模块；下载 v3 模板。
2. 上传文件；服务端解析六列。
3. 预览显示：学号、姓名、学院/专业/班级、原值 → 新值、状态（新增/相同/覆盖/错误/待提交审核）、说明。
4. 辅导员提交后生成待学院审核的变更，不直接改生效成绩；管理员按现有规则直接生效并审计。
5. 整批有任一错误则不能提交；重放不重复生成变更。

#### 身份与范围

- 六列全部核对：学号、姓名、学院、专业、班级、成绩。
- 辅导员只允许自己负责班级；服务端按当前班级辅导员关系过滤，不信任客户端班级筛选。
- 管理员在“沿用上期名单”策略下按已发布结果快照核对身份；其他情况按当前档案核对。
- 文件内学号重复：值相同跳过，值不同错误。
- 目标学生存在未处置的同班同名重复账号时，该行阻断，提示先处置账号身份；不能把成绩继续拆到两个账号。
- 成绩节点必须属于当前周期且为成绩输入模块；周期必须处于可录入阶段。
- 分数使用十进制字符串/精确有理数校验，禁止浮点误差；越界、负数、格式错误整批阻断。

#### 模板

- v3 表头固定六列；模块由页面选择并在预览中显示模块名。
- 模板不包含示例成绩行，避免误导入。
- 若后续需要一份文件导入多个模块，属于新需求，本轮不做。

### 5.3 参与名单导入（`ADMIN`、`COLLEGE`、`PUBLISHER`）

#### 流程

1. 选择周期和已确认活动；页面根据活动显示“首次名单”或“补录”。
2. 下载对应模板：固定分不带得分列；逐人分带“活动得分”。
3. 上传文件；服务端严格按中文表头读取。
4. 预览显示：学号、姓名、学院/专业/班级、活动得分、状态、说明；显示活动名称、分值、分制、名单是否已封存、证明是否有效。
5. 填写名单说明；补录更正必须填写理由。
6. 提交整批事务；首次名单保存后封存；后续只能补录新增或更正，删除仍走逐条原因流程。
7. 任一错误整批不写入；重放不重复登记。

#### 身份与范围

- 五列身份核对，且班级/专业/学院必须启用、班级必须有有效辅导员。
- 活动必须属于当前周期、已确认、当前角色可管理：
  - `ADMIN`：全部活动；
  - `COLLEGE`：本学院负责的活动；
  - `PUBLISHER`：本人历史活动；
  - `COUNSELOR`、`STUDENT`：不可导入。
- 学生必须在活动受众范围内（学院/班级/指定学生）；不在范围不能靠文件文本绕过。
- 文件内学号重复：整批错误，不静默去重。
- 目标学生存在未处置的同班同名重复账号时，该行阻断。
- 固定分活动不得填写个人得分；逐人分活动必须填写，且 `0 ≤ 得分 ≤ 活动分值`。
- 必须有有效活动证明；预览阶段就提示，不能等到提交才报错。
- 首次名单封存后，普通导入关闭；补录只能新增或更正，不能删除。

#### 模板

- 固定分：`学号,姓名,学院,专业,班级`
- 逐人分：`学号,姓名,学院,专业,班级,活动得分`
- 模板接口必须校验当前用户对该活动的管理权限和活动状态；不能只按角色发放。
- 页面“统一分值，得分列留空”的文案与模板保持一致。

## 八、实施顺序（审批后）

1. **冻结与备份**：确认迁移窗口，备份开发/目标数据库；不动生产数据。

9. **角色闭环测试**：按第七节矩阵用内置模板逐角色执行。
10. **用户验收**：用户自行浏览器/Excel/WPS 验收；agent 不在浏览器中代替操作。

## 九、验收标准

- 同班同名不同学号默认无法创建账号；例外必须有管理员理由和审计。
- 账号导入、手动建号、账号编辑、学生资料修改使用同一规则。
- 成绩/参与导入遇到未处置重复身份时阻断，不继续拆分数据。
- 三类内置模板与解析器、导入器完全一致；固定分/逐人分模板正确。
- 每个允许角色能用内置模板完成一次真实闭环导入；每个拒绝角色在页面和接口两层都被拒绝。
- 任一错误行导致整批不写入；重放不重复写入。
