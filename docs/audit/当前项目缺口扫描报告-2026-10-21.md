# 当前项目缺口扫描报告

日期：2026-10-21  
范围：当前工作树中的业务实现、API/服务端授权、Prisma模型、项目基线、最新学院流程规范、任务状态及已有验证记录。  
结论：核心业务已有较多可运行实现，但学院流程第 4–6 批、公式成绩导出和学院/辅导员独立工作台尚未交付；浏览器端及运行恢复验收也未完成。当前不能据已有构建或旧闭环测试宣称产品完整或可上线。

## 2026-10-22 进展（对下表的状态更新）

第 4 批已实施并留有实测证据，见[成绩扣分审核实施与验证](成绩扣分审核实施与验证-2026-10-22.md)：下表 P0 第 1 项（成绩/扣分没有辅导员提交—学院审核流程）与 P1 “成绩与扣分是覆盖式当前记录”已修复；另修正了数据库缺少 `DeductionInput.occurrence`、两张审核表未迁移、Prisma 客户端过期三处缺陷。仍未交付：公式成绩 XLSX 导出（P0 第 2 项）、学院/辅导员独立完整工作台（P0 第 3 项）、学院/辅导员授权导出（P1）、辅导员本班全部参与视图（P1，第六批）、个人申报重提须重新上传证明（P1）、组织配置真实数据验收（P1）、发布规模与 legacy 接口边界（P2）。浏览器、移动端、文件安全、备份恢复与部署就绪仍未验收。本报告其余内容保留为 2026-10-21 的盘点原文，不因单批完成而整体改写。

## 一、优先处理的功能缺口

| 优先级 | 缺口 | 当前源码/文档事实 | 影响与建议 |
|---|---|---|---|
| P0 | 成绩、扣分没有辅导员提交—学院审核流程 | `src/server/grades.ts`、`src/server/deductions.ts` 仅允许 `ADMIN` 在 ACTIVE 阶段直接写入当前值；`GradeInput`、`DeductionInput` 各自按学生/模块或项目唯一覆盖，没有待审修订及批准后替换状态。任务 04 尚未实施。 | 不能满足“辅导员录入或导入、学院审核后生效”；待审值、退回、重提、放弃及保留原有效值均无流程。按 `.scratch/college-workflow/issues/04-grades-deductions-and-returns.md` 实施并补服务端范围与状态约束。 |
| P0 | 详细成绩导出缺失，现有排名导出只有 CSV | `src/server/rankings.ts` 与 `/api/rankings/export` 提供管理员排名 CSV；没有班级/个人完整模块树 XLSX、制度参数区及派生分公式。辅导员和学生无正式详细成绩导出入口。任务 05 尚未实施。 | 用户无法按规范取得班级或本人完整公式成绩单；CSV 排名不能替代公式工作簿。需实现授权范围、发布版本冻结输入、缺录与零分区分、公式生成及 Excel/WPS 验证。 |
| P0 | 学院与辅导员没有独立完整工作台 | `src/app/(workspace)/page.tsx` 将 `COLLEGE`、`COUNSELOR` 直接重定向到 `/students`；`WorkbenchData` 在 `src/server/workbench.ts` 只有 ADMIN、PUBLISHER、STUDENT 三个分支。 | 新角色没有聚合待办、班级/学院审核队列、成绩扣分提交入口及完整职责概览；学生名录不能替代工作台。须在任务 06 内按职责实现真实工作台和导航，不以假统计补密度。 |
| P1 | 成绩与扣分是覆盖式当前记录，历史虽审计但没有完整版本实体 | `prisma/schema.prisma` 的 `GradeInput`、`DeductionInput` 唯一约束为周期+学生+模块/项目。服务端写入时更新同一行；原因和 before/after 进入 `AuditEvent`，读取历史依赖审计投影。 | 不能满足规范中的“新修订审核前保留原有效值、批准后原子替换”；异议、规则更正、发布快照与输入历史之间的可追溯性有限。应随 P0 审核流程设计版本记录，避免仅改写现值或假设审计表等同不可变业务版本。 |
| P1 | 学院/辅导员授权导出未实现 | 学生名录、成绩结果及排名相关API目前以 ADMIN/STUDENT 为主；导出路由 `src/app/api/rankings/export/route.ts` 只允许 ADMIN，筛选范围是查询过滤，不构成学院/班级授权。 | 学院只能导出本院、辅导员只能导出负责班级、学生只能导出本人尚未形成完整能力。实现导出时必须在服务端按已配置组织关系限域，不能信任请求里的学院/班级筛选。 |
| P1 | 学院/辅导员默认业务入口仍落到学生档案名录 | `/` 重定向至 `/students`，侧栏虽然包含审核入口，但没有工作台聚合；`src/server/workbench.ts` 亦没有这两类角色数据模型。 | 新角色需要自己寻找多个页面，无法看到所负责范围的全部参与、待审核成绩/扣分和退回事项。与完整、职责单一、高密度页面要求冲突。 |
| P1 | 学生活动审核范围与辅导员“本班全部参与”视图需复核 | 活动参与页、认定队列按活动/状态展示；规范要求辅导员能跨主办学院查看本人负责班级的全部参与记录，但只查看该班学生，并可按班级/活动/状态筛选。当前整体入口仍是学生名录跳转，未见独立辅导员工作台覆盖此任务。 | 第三批实现了活动两级审核和跨院数据最小化，但不能据此认定辅导员完整班级视图已交付。任务 06 应用真实组织数据验证外院主办活动与本人班级学生可见性。 |
| P1 | 个人申报重新提交要求重新上传证明 | 已有实施记录明确指出退回后重提要求至少重新上传一份证明，未预选原证明（`docs/audit/学院流程实施与验证-2026-10-20.md` §第二批未完成与后续）。 | 增加学生重复操作负担；需在不扩大证明访问权限、不改变证明引用和审核历史的前提下支持保留/重新选择现有证明。 |
| P1 | 组织配置与真实学院流程缺少可用数据验收条件 | 最近实施记录指出开发库只有 1 个学院、0 个班级、无学院账号，历史活动未归属主办学院（`docs/audit/学院流程实施与验证-2026-10-20.md` 第三批边界）。 | 服务层隔离测试不能证明真实组织配置下的完整业务流程。完成配置后需以学院、专业、班级、责任辅导员、跨院活动、名单和证明执行用户浏览器验收。 |
| P2 | 发布人数上限及规模能力有界 | 发布预览/锁定影响检查有 2000 人上限；活动参与导入每批有界（当前实现记录为最多 2000 条）。 | 当前设计会明确拒绝超限，不应静默截断；全校规模超过上限时需要明确产品处理策略。现阶段不应把异步批处理平台当作已实现能力。 |
| P2 | legacy API 与私有响应/错误契约仍有边界 | 现状台账记录部分旧列表API仍有 200 条限制，错误响应稳定 code/字段定位与所有成功写入 `no-store` 仍未全量统一（`docs/audit/现状与功能缺口.md` 最新实施增量、GAP-017/024）。 | 页面分页不代表所有旧调用方都完整；应逐接口盘点保留调用方，补有界分页或明确超限契约，避免静默截断及敏感响应缓存。 |

## 二、已实现但仍有验收/可靠性边界

| 优先级 | 项目 | 已知边界 |
|---|---|---|
| P0 | 浏览器/真实用户流程 | Agent 未操作浏览器或 Playwright；水合后按钮、表单、筛选、弹窗、拖动、图片/PDF呈现和真实业务流程尚待用户验收。当前所有视觉/交互完成度不能由 CLI 检查代替。 |
| P1 | 移动端与无障碍 | 有响应式源码和类型/lint/build 证据，但 320/375/390/768/1024/1440 实机/浏览器宽度、键盘焦点、触屏、溢出及屏幕阅读器均未验收。 |
| P1 | 文件安全 | 已有私有存储、对象权限、格式/大小校验和图片/PDF预览；没有完整恶意文件扫描/隔离流程。格式签名或预览成功不等于文件安全扫描。 |
| P1 | 备份恢复 | 迁移相关记录有数据库逻辑备份和隔离恢复证据；这不包含附件目录的一体化备份/恢复演练，也未形成完整灾备目标和恢复流程验收。 |
| P1 | 部署就绪 | `/api/health/ready` 本轮返回 200、`{"status":"ready"}`；源码只检查数据库连通、用户表查询及未完成迁移记录，不检查附件存储或尚未登记的待部署迁移，不构成完整生产就绪证明。Docker/生产部署未验收。 |
| P2 | 浏览器自动化 | 现状台账指出旧 Playwright 配置默认连接开发服务并可能创建/删除本地数据，不可直接作为隔离验收。当前未运行 E2E。 |
| P2 | UI术语统一 | 本轮进行了页面文案整理，但全仓还有技术性状态/历史名称及审核术语遗留；需完成逐页复核并由用户验收。不能只凭全局替换认定术语一致。 |

## 三、已完成且有近期技术证据的范围

- 第一批组织、账号与学生档案范围控制；第二批个人申报的学生提交、辅导员评分、学院终审、普通退回、评分重评、放弃和受控撤销；第三批活动主办学院、严格名单、补录更正、共享活动证明及活动参与两级审核。具体范围及迁移/测试边界见 `docs/audit/学院流程实施与验证-2026-10-20.md`。
- 结果发布、学生确认、成绩异议、排名 CSV、结算快照、理由重开和周期生命周期已有实现；它们不包含尚未完成的成绩/扣分审核和公式 XLSX。
- 最近运行记录：`npm run typecheck` 通过；`npm run lint` 通过；`npm test` 17 个测试文件、75 项通过；`npm run build` 通过并执行 standalone 静态资源同步；独立 HTTP 检查 `/api/health/ready` 与 `/login` 均返回 200。
- 上述是代码/隔离测试/构建/HTTP证据，不证明浏览器交互、生产部署、附件恢复或完整业务验收。

## 四、建议处理顺序

1. **第 4 批：成绩与扣分审核**——辅导员范围内录入/导入并提交，学院审核；退回原辅导员、修正新修订、放弃，批准前保留旧有效值。
2. **第 5 批：公式成绩导出与授权证据预览**——班级/学院/本人严格限域，生成模块树 XLSX 公式，完成初始对账、改值传播及 Excel/WPS 用户验收。
3. **第 6 批：全角色工作台、迁移与整体复核**——学院/辅导员独立工作台、本班参与视图、逐页模板核对、接口/授权复核、备份恢复及迁移证据。
4. **用户验收与运行恢复**——完成桌面及手机浏览器业务验收；补附件恢复演练和部署检查。未经这些验证不得作上线结论。
