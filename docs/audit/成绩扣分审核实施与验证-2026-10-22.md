# 成绩与扣分两级审核实施与验证

日期：2026-10-22。对应[学院职责与统一审核规范](../product/学院职责与统一审核规范.md)第 4 批、[有序任务](../../.scratch/college-workflow/issues/04-grades-deductions-and-returns.md)及[缺口扫描报告](当前项目缺口扫描报告-2026-10-21.md) P0 第 1 项。本记录只写本轮实际修改与实测结果，不把界面文案或构建通过当作浏览器验收。

## 一、本轮修复的缺口

1. 成绩、扣分此前只能由管理员直接写入当前值，没有辅导员提交—学院审核、退回、新修订、放弃的流程。
2. `GradeChange`、`DeductionChange` 两张表只存在于 schema，从未生成迁移，也没有任何读写实现。
3. `DeductionInput.occurrence` 与四列唯一约束同样只存在于 schema：数据库仍是“一项目一条”的三列唯一索引，成本地库与 schema 漂移；同一扣分项目的第二个事件会覆盖第一个事件。
4. Prisma 客户端由旧 schema 生成，`occurrence`、两张审核表在类型层不存在。
5. 成绩结果汇总把同一扣分项目的多个事件写成 `Object.fromEntries`，后一条会覆盖前一条。

## 二、数据模型与迁移

- 新增迁移 `20261022085000_deduction_occurrences`：为 `DeductionInput` 增加 `occurrence`（默认 0，既有记录即第一条事件），把三列唯一索引换为 `(termId, studentId, projectId, occurrence)` 四列唯一索引并保留三列查询索引。
- 新增迁移 `20261022090000_grade_deduction_review`：创建 `InputChangeStatus`、`DeductionChangeAction` 枚举与 `GradeChange`、`DeductionChange` 表及外键、状态/学生/提交人索引。
- `GradeChange`、`DeductionChange` 增加 `requestId` 与 `(termId, submittedBy, requestId)` 唯一约束，用于网络重试幂等重放，不以文件名或时间戳代替业务唯一性。
- 迁移前用逻辑行备份（NDJSON + 行数 + SHA-256）保存开发库：37 张业务表、174 行；迁移后 39 张表、174 行，原表行数不变，新增两张审核表为空。
- 迁移后以 `prisma/schema.prisma` 与 `information_schema` 逐表逐列比对，输出 `schema matches database`。

## 三、服务端流程

新增 `src/server/input-review.ts`（共用范围与历史记录）、`src/server/grade-changes.ts`、`src/server/deduction-changes.ts`：

| 动作 | 允许身份 | 规则 |
|---|---|---|
| 提交成绩修订 | 辅导员 | 仅本人责任班级学生；ACTIVE 且周期未归档/作废；分值须在最底层成绩模块范围内；同一学生同一成绩项只允许一条待审或退回修订；与当前有效值相同直接拒绝 |
| 修改扣分事件 | 辅导员 | 仅本人责任班级学生；扣分额必须为正数；同一项目的不同事件各自成条，不覆盖 |
| 申请撤销扣分 | 辅导员 | 必须指向本人范围内、未撤销、版本一致的事件；同一事件不能有第二条待审撤销申请 |
| 通过 | 学院 | 仅本院学生；仅待学院审核；批准前重新核对基线（输入 id 与修订号），有效值已变则拒绝并提示退回重提；批准时原子写入有效值并递增周期输入修订 |
| 退回 | 学院 | 仅待学院审核；理由必填（2–1000 字），交原提交辅导员 |
| 重新提交 | 原提交辅导员 | 仅退回修改中；刷新基线快照，回到待学院审核，保留全部历史 |
| 放弃 | 原提交辅导员 | 仅待审或退回修改中；记录放弃人与理由，不改有效值 |

- 并发与一致性：沿用周期级 advisory lock 与 `revision` 乐观校验；同一修订只能被处理一次，重复批准返回“仅待学院审核”。
- 待审不影响计分：`collectStudentResults` 只读取 `GradeInput`、未撤销的 `DeductionInput`，审核表不参与计算。
- 计分修正：`results.ts` 改为按扣分项目累加同一项目的多个事件，再交评分制度按项目系数折算，替换原先“后一条覆盖前一条”的写法。
- 留痕：每条修订保存 `history`，并写 `GRADE_CHANGE_SUBMITTED/CHANGED`、`GRADE_APPROVED`、`DEDUCTION_CHANGE_SUBMITTED/CHANGED`、`DEDUCTION_APPROVED`、`DEDUCTION_REVOKED_APPROVED` 等审计事件，含批准前后值、模块、系数与理由。
- 成绩导入：`grade-import.ts` 对辅导员开放，逐行校验本人班级范围与既有待审修订，提交后生成待学院审核的修订；管理员导入仍为受控直接写入。预览与提交都重算快照。
- 管理员例外更正：`saveGrade`、`saveDeduction` 保留为“直接生效并留痕”的例外入口，增加 `occurrence` 定位，用于组织或数据异常处理；它不是日常两级审核，也不由管理员代替学院终审。

## 四、接口

| 接口 | 身份 | 用途 |
|---|---|---|
| `GET /api/grades/roster` | 管理员/学院/辅导员 | 按范围与筛选分页返回学生、已录/应录、待审与退回计数 |
| `GET /api/grades/[studentId]` | 同上 | 学生成绩模块、有效值、待审修订与审核历史 |
| `POST /api/grade-changes` | 辅导员 | 提交成绩修订（含 `requestId` 幂等） |
| `GET /api/grade-changes` | 同上 | 待审/退回/已通过/已放弃队列与计数 |
| `PATCH /api/grade-changes/[id]` | 辅导员/学院 | 通过、退回、重提、放弃 |
| `GET /api/deductions/roster` | 同上 | 学生扣分事件数、待审与退回计数、项目目录 |
| `GET /api/deductions/[studentId]` | 同上 | 扣分事件、审核历史、项目与系数 |
| `POST /api/deduction-changes` | 辅导员 | 新增事件或申请撤销 |
| `GET /api/deduction-changes` | 同上 | 扣分审核队列与计数 |
| `PATCH /api/deduction-changes/[id]` | 辅导员/学院 | 通过、退回、重提、放弃 |

所有响应均 `Cache-Control: no-store`，写操作校验同源；范围在服务端按已配置班级、责任辅导员与学院判定，不信任请求里的组织字段。

## 五、页面

`/grades`、`/deductions` 由管理员专用页改为四类身份可进入的完整业务页，模板来源与保留结构见[模板来源与适配清单](../design/模板来源与适配清单.md)第 4 批一节：

- 顶部周期上下文与三张真实计数卡（待审、退回、本人待审或全校有效事件）。
- 审核队列：按状态筛选、20 条分页、通过/退回（退回必填理由 Dialog）、修正并重提。
- 学生名录：姓名/学号搜索、学院/专业/班级筛选、20 条分页，显示已录/应录、待审与退回计数。
- 学生详情 Sheet：逐模块有效值、待审修订、修订与审核历史；辅导员提交修订或重提，学院通过或退回。
- 扣分详情 Sheet：逐条事件（事件序号、扣分额、系数、状态）、登记事件、申请撤销（Dialog）、扣分审核历史与退回重提表单。
- 只读边界：非 ACTIVE 或周期已归档/作废时保留查询与历史，提交入口显示不可用原因。
- 侧栏为学院/辅导员补齐“成绩审核/成绩录入”“扣分审核/扣分管理”。

## 七、未完成与未验证

- 未操作浏览器或 Playwright；水合后的表单、Sheet、Dialog、筛选与 320–1440 宽度表现由用户自行验收。
- 登录后页面的 HTTP 复检未执行：现行登录需要图片验证码，agent 不绕过验证码，也不向开发库写入伪造验证码答案。页面已在构建中通过服务端渲染编译，`/grades` 未登录访问返回 307；授权后的真实呈现由用户浏览器验收。
- 真实组织规模（多学院、多班级、跨院活动）下的业务验收仍未执行，本地库仅 3 个学院、6 个班级。
- 成绩公式 XLSX 导出（第 5 批）、学院/辅导员独立工作台（第 6 批）仍未交付。
- 管理员例外更正仍是直接生效通道，本轮只保证其留痕与定位；是否需要在界面上与日常审核进一步区分，待用户确认。
- 迁移备份为行级逻辑导出（打包 PostgreSQL 未附带 `pg_dump`），不是完整物理备份；附件目录与本轮迁移无关，未做一体化恢复演练。
