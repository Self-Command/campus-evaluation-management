# 角色视角 UI 规范与页面改造分析

日期：2026-10-22  
范围：`src/app/(workspace)` 下全部角色可见页面、角色导航、页面标题/说明/按钮/状态文案、空态与重复入口。  
性质：只读分析，本轮不修改任何页面代码、接口或数据结构。

## 一、结论摘要

当前前端功能基本齐全，但页面是按“系统模块”组织的，不是按“这个角色今天要做什么”组织的。普通用户需要先理解系统内部概念，才能找到自己的任务。最突出的六个问题：

1. **学院和辅导员没有工作台。** 登录后直接进入“学生档案”，把行政名册当成了首页。他们每天真正要做的是审核、评分、录成绩、登记扣分和处理退回，却没有一个页面汇总“哪些事在等我”。
2. **同一件事有多个入口，而且名字不一样。** 学生同时看到“我参加的活动”“已发布活动”“活动参与”；辅导员看到“成果申报审核”，页面内部却写“辅导员评分”；管理员看到“活动参与审核”，实际上管理员只能查看、不能审核。
3. **权限和文案互相矛盾。** 管理员工作台把“待审核活动参与”“待审核成果申报”写成自己的待办，并提供“去处理”，但管理员在这两个页面没有审核按钮；辅导员页面写“活动管理”，但辅导员不能创建或维护活动；成绩页脚注引导学院/辅导员去看他们无权访问的“成绩查询/结果发布”。
4. **用内部流程词代替用户语言。** “修订、有效值、例外更正、事件、系数、方案版本、成绩版本、发布版本、映射、回收站、作废、归档、建档”等词大量出现在主界面，普通学生和辅导员很难第一眼理解。
5. **同一页面塞进多角色工作。** 成绩、扣分页面都是“审核队列 + 学生名册 + 详情抽屉”三合一，学院和辅导员看到的结构完全相同，只是默认位置和按钮不同；每个人都要越过与自己无关的区块。
6. **标题和信息层级重复。** 页面级 `PageHeading` 与列表组件的 `title/description` 同时出现，形成两个大标题、两段说明，有的还互相矛盾；活动详情右侧最多同时出现七八个操作按钮，没有“下一步”。

本报告的建议是：**先修文案和权限一致性，再做角色工作台和入口合并，最后重构成绩/结果等高频页面的信息层级。** 不建议直接把不同职责的业务页面合并成一个页面。

## 三、按角色分析

### 3.1 学生

**用户心智**

学生不关心“活动参与记录”和“成果申报”在数据库里是不是两张表。他关心的是：

- 学校发布了哪些活动给我？我需不需要报名？
- 我参加了哪些？审核通过没有？
- 我自己提交的成果到哪一步了？
- 我的总分、班级排名、每一项分数从哪来？
- 我需不需要确认？有错误怎么提？

**主要问题**

1. **三个活动入口，学生无法区分。**
   - “我参加的活动”（`/activities`）实际是已登记本人参与的活动；
   - “已发布活动”（`/activity-feed`）是面向本人范围发布的活动；
   - “活动参与”（`/recognitions`）是本人参与记录的审核状态。
   三者对用户都是“活动”，但被拆成三个一级导航。更严重的是 `activity-feed` 写“可参加的活动”，而当前学生没有报名入口，参与名单由主办学院登记或导入（`activity-detail.tsx` 中已移除学生自行登记）。这会让用户以为点进去可以报名，实际只能浏览。

2. **“浏览不代表已参加”解释不足。**
   现在只在页面说明里写“浏览不代表已参加，参与情况以后台登记和审核结果为准”。普通用户看不懂“后台登记”。应直接说清楚：**“活动名单由主办学院统一登记，你不需要在这里报名；名单有误请联系辅导员。”**

3. **成绩页信息过载且术语偏技术。**
   `result-view.tsx` 同时展示“成绩版本、评分方案第 N 版、成绩第 N 版、发布第 N 版、核对截止、确认本版、计分依据、成绩录入、当前扣分”。信息本身是必要的，但主界面应先回答“总分多少、班级第几、是不是正式成绩、我要不要做什么”，版本信息应折叠到“成绩说明”。

4. **“我的档案”和“个人设置”边界不清。**
   “我的档案”是学籍信息（只读，需管理员更正）；“个人设置”是账号密码。学生容易以为两边都能改姓名/班级。应改名为“我的学籍信息”和“账号与密码”。

5. **“测评周期”对学生没有行动价值。**
   学生不需要看生命周期、方案版本和归档状态。顶部已有周期选择器，侧栏再放“测评周期”只会增加一个看不懂的页面。建议学生侧栏移除，历史学期入口放到“我的成绩”。

6. **排名口径不一致。**
   结果页叫“班级名次”，工作台叫“发布名次”。应统一为“班级排名”，并说明“按本次发布名单计算”。

**建议改造页面**

| 优先级 | 页面 | 改造方向 |
| --- | --- | --- |
| P0 | 导航 + 活动相关三页 | 合并为一个“活动”入口，内部按“面向我发布 / 我已参加 / 审核记录”分栏；明确学生不报名 |
| P0 | 成绩页 `result-view.tsx` | 重排为“我的成绩 / 分数明细 / 需要我处理”三块；技术版本折叠 |
| P1 | 工作台 `student-workbench.tsx` | 统一“班级排名”等术语；删除重复的申报/活动入口；把“待补材料”做成明确任务 |
| P1 | 我的档案 / 个人设置 | 改名为“我的学籍信息 / 账号与密码”，补一句两者区别 |
| P2 | 成绩异议 | 保留独立页，文案改为“对哪次发布的哪一项有疑问”，不要突出“版本” |

**学生活动入口合并建议**

推荐一个页面、三个分栏：

- **面向我发布**：学校发布给本人学院/班级的活动，说明“名单由主办学院统一登记，无需报名”；
- **我已参加**：已登记本人参与的活动、登记时间、统一分值；
- **审核记录**：辅导员/学院审核状态、退回原因、证明。

这样既保留三种真实数据，又只占用学生一个心智入口。该合并需要选择模板中最接近的活动列表页作为改造起点，并在 `docs/design/模板来源与适配清单.md` 登记。

### 3.2 辅导员

**用户心智**

“我负责哪几个班？这学期还有哪些学生没录成绩？哪些活动参与、成果申报等我处理？哪些被退回要我修改？截止时间是什么时候？”

**主要问题**

1. **登录即学生档案，没有任务首页。**
   `/` 直接把 COLLEGE 和 COUNSELOR 重定向到 `/students`（`src/app/(workspace)/page.tsx:15`）。学生档案是低频行政查询，不是辅导员的日常起点。辅导员需要的是“我的待办 + 我的班级进度”。

2. **辅导员的“活动”页面写成“活动管理”。**
   页面标题和说明是“活动管理 / 维护活动、参加范围和活动分值”（`activities/page.tsx`），列表标题也是“活动管理”（`activity-list.tsx:151`）。但辅导员不能创建活动，也不维护分值。应改为“活动名单”或“活动参与”，说明“查看本院活动及负责班级学生的参与情况”。

3. **成果申报页标题与内部标题不一致。**
   页面标题和侧栏写“成果申报审核”，组件内部写“辅导员评分”。辅导员的动作是“核对材料 → 选择计分项 → 填分 → 提交学院”，不是终审。应统一为“成果评分”，按钮用“评分并提交学院”。

4. **成绩页和扣分页结构相同，辅导员要越过审核队列。**
   顶部的“成绩审核队列”主要面向学院，辅导员更关心“我的学生录入进度”和“被退回的修改”。建议同页改为两个分栏，并按角色设置默认：
   - 辅导员默认“我的学生 / 待我处理”；
   - 学院默认“待我审核”；
   - 管理员默认“全校进度”。

   这不是把成绩和扣分合并，而是在各自页面内按角色重排。

5. **术语系统化。**
   “成绩修订、有效值 → 修订值、修正并重提、放弃修订、例外更正、扣分事件、第 N 条事件、系数、折算”都要求用户理解版本和事件模型。应换成“当前成绩 → 修改后成绩、修改后重新提交、撤回本次修改、直接更正（会记录原因）、扣分记录、第 N 次扣分、折算比例”。

6. **被退回的颜色语义过重。**
   “已退回”使用 destructive（红色）样式，容易被理解为严重错误或惩罚。退回是正常流程，建议使用 warning/中性色，并在文案中说明“退回给谁、要改什么”。

7. **“测评周期”侧栏入口对辅导员无行动价值。**
   辅导员不管理周期。可以移除，改为在评分表单旁提供“评分标准”说明；如保留，只展示“当前学期 + 时间安排”，不展示生命周期管理。

**建议改造页面**

| 优先级 | 页面 | 改造方向 |
| --- | --- | --- |
| P0 | 新增“辅导员工作台” | 待我审核活动参与、待我评分成果、待提交成绩、被退回事项、班级完成度 |
| P0 | 活动页 | 标题/说明/按钮按辅导员权限改写，去掉“管理”暗示 |
| P0 | 成果申报页 | 统一为“成果评分”，突出“评分并提交学院” |
| P1 | 成绩 / 扣分页 | 分栏 + 角色默认视图；术语改写；页脚删除无权限引导 |
| P1 | 学生档案 | 改名为“我的学生”，保留班级/辅导员/学籍信息，增加本学期完成情况入口 |
| P2 | 测评周期 | 从侧栏移除，评分标准就近展示 |

### 3.3 学院

**用户心智**

“本院哪些活动要我主办？哪些参与、成果、成绩、扣分等我审核？名单导入了吗？成绩完整了吗？哪些学生被退回了？”

**主要问题**

1. **同样没有工作台。**
   学院登录也落到“学生档案”。学院的核心动作是四类审核 + 活动主办 + 名单导入 + 本院进度，应该有一个“学院工作台”。

2. **四类审核分散在四个一级入口。**
   活动参与审核、成果申报审核、成绩审核、扣分审核分别在四个侧栏项。对学院来说它们都是“待我审核”，但业务规则不同，不能简单合并成一个页面。推荐做法是：
   - 保留四个独立处理页（符合现行产品基线）；
   - 在工作台提供一个“待我审核”汇总卡片，按类型显示数量，点击进入对应页面；
   - 每个页面默认落在“待我审核”，而不是全部记录。

3. **活动页的范围说明不够清楚。**
   学院可以看到本院主办的活动，也可能看到其他学院活动中涉及本院学生的记录。但页面标题只写“活动管理”，没有说明“只能维护本院主办的活动；其他学院的活动只能查看本院学生参与”。这会造成“为什么这个活动我不能编辑”的困惑。建议标题改“本院活动”，并在列表上方加范围说明或“我主办的 / 涉及本院学生”筛选。

4. **成绩/扣分页的学院视图被名册淹没。**
   学院打开页面后先看到审核队列，下面是庞大的本院学生名册。名册对学院有用，但不是第一任务。建议默认“待我审核”分栏，名册作为第二分栏；顶部统计只保留“待我审核 / 被退回 / 本院完成度”。

5. **“组织架构”名称偏系统。**
   学院实际维护的是本院专业、班级和责任辅导员。建议改为“本院专业与班级”，并在页面说明中写清“学院信息由学校管理员维护”。

6. **“参与名单导入”入口孤立。**
   侧栏有全局“参与名单导入”，活动详情里也有“导入参与名单”。两个入口都合理，但文案不一致。建议统一为“导入活动名单”，并在全局页说明“先选择活动，再导入该活动的名单”。

**建议改造页面**

| 优先级 | 页面 | 改造方向 |
| --- | --- | --- |
| P0 | 新增“学院工作台” | 四类待审汇总、活动待确认、名单待导入、本院成绩完成度 |
| P0 | 活动页 | 改“本院活动”，补范围说明和筛选 |
| P1 | 成绩 / 扣分页 | 默认“待我审核”分栏；名册次之 |
| P1 | 组织架构 | 改“本院专业与班级”，说明权限边界 |
| P2 | 参与名单导入 | 统一名称与入口说明 |

### 3.4 管理员

**用户心智**

“周期配置好了吗？评分方案生效了吗？哪些活动还没确认分值？哪些学生成绩没录完？哪些记录卡在辅导员/学院？能不能发布？发布后谁有异议？数据导入和账号有没有问题？”

**主要问题**

1. **工作台把别人的工作写成了管理员的待办。**
   `admin-workbench.tsx` 的说明是“先处理待审记录和成绩异议，再发布本周期结果”，四个指标是“待审核活动参与 / 待审核成果申报 / 待确认分值的活动 / 待处理成绩异议”，每条都有“去处理”。但：
   - 活动参与审核只允许辅导员/学院审核（`src/server/recognitions.ts:527`）；
   - 成果申报只允许辅导员评分、学院终审，管理员仅能撤销已通过申报（`src/server/claims.ts:118,138,154`）。

   管理员点“待审核活动参与 → 去处理”后只能查看，不能处理。这会直接破坏用户对系统的信任。应改为“全校办理进度”，按责任角色显示“待辅导员处理 / 待学院审核”，动作写“查看进度”，只有管理员真正能做的事才写“去处理”。

2. **管理员缺少真正的“待我处理”。**
   管理员真正要处理的是：未确认分值的活动、成绩未录完的班级、发布前阻断项、待处理成绩异议、账号/组织异常。这些应该成为工作台的第一屏。

3. **“审核队列”与指标卡重复。**
   工作台同时有四个指标和“审核队列”，信息重叠但口径不同。建议合并为一个“全校待办”列表，按“需要我处理 / 等待他人处理”两组展示。

4. **“活动参与审核”这个导航名对管理员是错的。**
   管理员只能监督，不能审核。建议改为“活动参与记录”或“活动参与监督”，页面说明写“审核由辅导员和学院完成，管理员查看全过程和结果”。

5. **周期页混用“业务阶段”和“管理状态”。**
   “配置中/进行中/结果核对/已锁定”与“正常/已归档/已作废/回收站”同时作为两列，再加上“方案版本”，普通管理员需要理解两套状态机。建议：
   - 列表只显示一个“周期状态”，把管理状态合并进去；
   - “回收站 / 作废 / 归档”收进“更多操作”；
   - 说明文字改成“删除后可在已删除中恢复；作废保留记录但不能继续办理；归档表示只读保存”。

6. **结果发布页流程不够一眼可见。**
   页面有“发布前检查 / 当前发布 / 学生确认与锁定 / 发布历史 / 结算存档 / 重开更正”，功能完整，但主界面没有明确的 1-2-3-4 步骤。建议顶部固定一条状态流程：“检查 → 发布 → 学生确认 → 锁定”，每个步骤显示当前状态和阻断原因，历史与存档放到次级标签。

7. **导出入口分散。**
   成绩页、排名页、成绩详情页、结果页都有导出按钮。对管理员来说这不一定坏，但应统一命名和范围说明，例如“导出全校明细 / 导出本院明细 / 导出本人明细”，不要让用户猜当前导出的是什么范围。

**建议改造页面**

| 优先级 | 页面 | 改造方向 |
| --- | --- | --- |
| P0 | 管理工作台 | 区分“待我处理 / 等待他人”；修正“待审核/去处理”；增加成绩完整度和发布阻断项 |
| P0 | 活动参与导航/页面 | 改“活动参与记录/监督”，说明管理员只读 |
| P1 | 测评周期 | 合并状态列，低频生命周期操作收进更多菜单 |
| P1 | 结果发布 | 增加步骤条和阻断原因，历史/存档降级 |
| P2 | 排名与导出 | 明确“全校排名 + 全校明细导出”的范围 |
| P2 | 批量导入 | “映射”改为“核对表格列”，错误说明更口语化 |

## 四、可以合并与不建议合并

### 4.1 推荐合并（入口层或同页分栏，不改变业务边界）

| 合并项 | 现状 | 建议 | 风险 |
| --- | --- | --- | --- |
| 学生三个活动入口 | 我参加的活动 / 已发布活动 / 活动参与 | 合并为一个“活动”页，三个分栏 | 低；需要新的活动聚合页，保留原深链 |
| 管理员工作台指标 + 审核队列 | 两处重复 | 合并为一个“全校待办”，分“待我处理/等待他人” | 低；只改工作台 |
| 学院/辅导员四类审核的入口 | 四个侧栏项 | 保留四个页面，工作台增加“待我审核”汇总卡 | 低；符合现行独立页面要求 |
| 成绩页的队列 + 名册 | 上下堆叠 | 同页分栏，按角色设默认 | 中；不改接口，只改信息架构 |
| 扣分页的队列 + 名册 | 上下堆叠 | 同上 | 中 |
| 周期页“业务阶段 + 管理状态” | 两列状态 | 合并为一个“周期状态”，低频状态进筛选/更多 | 低 |
| 活动详情右侧操作区 | 最多 7-9 个按钮 | 一个“下一步”主按钮 + 更多操作菜单 | 中；需按角色梳理动作优先级 |

### 4.2 需要用户明确批准后才能做的页面级合并

以下合并会触碰 2026-10-20 已确认的产品基线：成绩录入、扣分管理、学生档案、账号管理必须独立；申报与异议保留各自完整处理页。**本报告不默认执行，只作为候选。**

| 候选 | 影响 | 建议 |
| --- | --- | --- |
| 把成绩、扣分合并为一个“学生业务”页面 | 违反独立页面约束；两类业务规则、审核链、审计语义不同 | 不建议 |
| 把成果申报与活动参与合并为一个“审核中心” | 两类材料、评分方式、退回对象不同 | 不建议；用工作台汇总即可 |
| 把成绩异议并入成绩页 | 异议有独立生命周期和发布版本关联 | 不建议；保留独立页，做好互链 |
| 把学生档案并入账号管理 | 学籍与登录账号是不同职责 | 不建议 |

### 4.3 明确不建议合并

- **成绩录入 vs 成绩查询**：一个是批量维护，一个是按学生查看结果；角色和心智不同。
- **扣分 vs 成绩**：扣分是事件累计后折算，成绩是模块输入；审核链相似但业务对象不同。
- **活动参与 vs 成果申报**：前者由学校登记名单，后者由学生提交材料；退回对象和评分方式不同。
- **结果发布 vs 排名导出**：一个是生命周期操作，一个是只读结果消费。

## 七、判断标准

改造后，用下面几个问题验收，而不是只看页面是否能打开：

1. **辅导员登录后 10 秒内**能说出“有多少事在等我、分别去哪里处理、哪个班还没完成”。
2. **学院登录后 10 秒内**能说出“四类审核各有多少、哪个活动还没导入名单、本院成绩是否完整”。
3. **管理员不会看到**自己无权执行的“去处理/审核”按钮。
4. **学生能分清**“学校登记的活动”和“我自己提交的成果”，并知道活动不需要自己报名。
5. **任一页面只有一个标题和一段说明**，导航名、页面名、按钮名指向同一件事。
6. **主界面不再出现**“修订、有效值、例外更正、事件、系数、映射、回收站”等内部词；这些词只出现在历史记录或帮助说明中。
7. **每个操作都写清对象和结果**，例如“退回学生补充材料”，而不是“退回”。
8. **移动端首屏**能看到当前状态和主要操作，不需要先滚过统计卡片或长说明。

## 八、实施边界与风险

- 本轮只出分析，不改页面、接口、数据库。
- 后续每个页面改造必须从指定完整模板的对应页面/业务组件开始，并在 `docs/design/模板来源与适配清单.md` 记录源文件、修改边界；不能自行拼装布局。
- 角色工作台属于新增页面，需先选定模板 dashboard 页面作为改造起点；如果模板中没有对应结构，应先取得授权再新增视觉结构。
- 学生活动三合一涉及新聚合页和导航调整，但仍保留原页面深链，避免破坏已有入口和权限。
- 成绩、扣分、学生档案、账号管理、成果申报、成绩异议继续独立；本报告只建议工作台汇总和同页分栏，不建议合并这些业务页。
- 任何涉及“谁能审核/谁能退回/退回给谁”的文案调整，必须与后端权限和审核链保持一致；不能只改文案造成新的误解。
- `PUBLISHER` 分支目前仍散落在导航和多处页面文案中，但当前四角色主流程没有完整发布者工作台。建议产品上明确是否保留该角色；若不保留，应清理入口和分支，避免出现第五套视角。

## 九、建议实施顺序

1. **第一轮（纯文案与一致性）**：导航名、页面标题/说明、按钮、状态词、页脚错误引导、退回语义。风险最低，能立即改善“看不懂”。
2. **第二轮（工作台与入口）**：学院/辅导员工作台、管理员工作台修正、学生活动三合一、成绩/扣分同页分栏。
3. **第三轮（高频页面重构）**：学生成绩页、活动详情操作区、周期状态、结果发布步骤条、导入向导。
4. **第四轮（验收与回归）**：按角色走一遍真实用户故事，检查权限、深链、筛选保留、移动端和空态；补充必要的集成测试和页面截图记录。
