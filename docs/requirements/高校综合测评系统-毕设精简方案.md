# 高校综合测评系统：毕设精简方案

实施与任务验收使用[正式开发规格](../../.scratch/comprehensive-evaluation/spec.md)；本文件保留需求讨论背景和详细示例。

更新：2026-10-19。根据用户要求精简业务范围，替代此前复杂方案；交付目标是按生产标准开发的完整版本，当前用于本机／局域网部署演示。目标是功能完整可用、管理员容易配置、能够较快完成开发。以下评分结构是设计建议和模拟示例，不是学校已经核准的具体制度。

最新确认：评分分类恢复原方案的可嵌套结构，不写死业务层数上限；角色、统一活动分值和每学期全体学生共用方案继续保持精简设计。

最新补齐：首版以本校附件表达的评分机制为预置模板，计算功能保持独立通用。支持直接累加、按比例汇总、任意节点封顶、可选满分折算和独立扣分。原表公式已只读提取核查；配置细节见[评分配置通用功能说明](../design/评分配置通用功能说明.md)，预置数据见[学校评分模板](../examples/学校评分模板.json)，原表差异见[学校评分模板-公式核查](../research/学校评分模板-公式核查.md)。

## 1. 简化后的产品范围

每套系统先服务一所学校，每学期所有学生使用同一套测评方案；同一活动对所有被认定参与的学生给予相同原始分。学校、学院、班级仍可登记和用于筛选排名，但不再为不同学生配置不同评分方案。

其他学校使用时，配置自己的模块名称、汇总方式、比例、上限、折算方式、扣分位置与活动分值；在这些通用操作支持的范围内不必修改代码。第一版不做多校入驻运营、学生方案匹配或复杂规则编排。

保留活动信息展示、个人申报、活动名单批量导入、共享证明、管理员审核与异议处理、学业等成绩导入、自动汇总、排名和Excel导出。活动不提供在线报名。

## 2. 角色建议：三个即可

| 角色 | 职责 |
|---|---|
| 学生 | 看活动、提交个人材料、查看本人记录和成绩、提出异议 |
| 活动发布者 | 发布活动、提出统一活动分值、CSV／XLSX导入名单、上传共享证明 |
| 管理员 | 配置测评方案、管理用户、确认活动分值、审核认定、处理异议、导入成绩、汇总导出 |

不再单独设置审核员、复核员、学院管理员和平台管理员。审核与异议都由管理员处理，可有多个管理员账号；是否由同一人处理不再设置复杂强制流程，操作和修改理由留记录。学生查看本人证明与名次，发布者管理自己发布的活动。

账号由管理员统一创建或批量导入，学生使用学号和密码登录。建号时生成初始密码，首次登录要求修改；忘记密码由管理员重置。密码变更、账号停用和角色调整后，后续受保护操作按最新账号状态与权限检查。

## 3. 评分结构：方案 → 评分模块 → 下级模块……→ 活动或成绩

评分结构采用一棵可继续向下扩展的树，允许模块、子模块、子子模块等任意实际需要的层级；不把业务限制写死为两层、三层或五层。所有节点使用同一种模块模型，层级由父子关系决定，不为每一层分别建一种模块。

本校方案的正向满分为100分。每个汇总模块可选择“直接累加”或“按比例汇总”；只有父模块选择按比例时，直接下级才填写相对父模块的比例。系统逐层汇总，管理员不写公式。

节点分为两种用途：有下级模块的节点负责汇总；最底层没有下级模块的节点负责接收活动或成绩。汇总节点不能另外直接录入一笔分数，防止父子重复计分。

| 配置位置 | 管理员填写 |
|---|---|
| 学期方案 | 学期名称、使用状态 |
| 最顶层模块 | 名称、汇总方式、占总分比例、可选上限，可继续添加下级模块 |
| 任意下级模块 | 名称、汇总方式、可选上限；父级按比例汇总时填占比 |
| 最底层模块 | 成绩来源、有效范围；上限和满分折算均为可选配置 |
| 活动／加分项目 | 名称、所属最底层模块、每位参与学生的统一原始加分 |
| 扣分项目 | 名称、扣减节点、系数；管理员录入扣分额和理由 |

最底层模块的数据来源首版只做两种：

1. 活动累加：审核通过的活动或个人申报项目加分合计；本项或上层配置上限时，在指定节点汇总后封顶。
2. 成绩录入／导入：管理员录入或导入学业、体育等原始分；值必须在该子模块的有效范围内。

每个最底层模块选择一种来源，避免成绩导入后又把活动加分叠上去。模块不需要继续拆分时可直接作为最底层节点，不必额外建立一个同名子模块。

### 管理界面与层级保护

管理员在树形目录中选中模块，执行添加子模块、设置比例、改名、排序或删除。深层内容按需展开，提供父级路径，计算结果按模块展开查看；界面不要求同时展开整棵树。

不设置固定业务层数不代表硬件可支持真正无限的数据。实现采用父级标识保存关系、迭代后序遍历逐层计算，避免依赖语言调用栈的递归深度；按需加载目录，处理耗时操作时提供进度和明确错误。实际容量由数据量、资源和验证结果决定，不以“无限层级”宣称无限承载能力。

必须禁止模块成为自己的子模块、把模块移动到自己的后代下、跨方案挂接以及没有输入来源的空节点发布。已有活动或成绩的最底层节点若要继续拆分，先明确迁移其数据到新的下级节点，再转换为汇总节点；不能直接改变类型并丢失原记录。

## 4. 汇总、比例、上限与折算分别配置

比例表示父模块按什么系数汇总子模块；上限表示本节点最多计多少分；折算基数表示是否把原始分换算为另一满分标准。这些是独立参数，不能把30分上限直接当成30%内部权重。

统一计算方式：

```text
输入节点：取已认定原始分
直接累加节点：取各直接子模块结果之和
按比例汇总节点：取各直接子模块结果×各自比例之和

在当前节点依次执行：
汇总 → 配置上限时封顶 → 明确启用时才进行满分折算
     → 减去本节点扣分 → 配置下限时应用下限
```

然后把结果交给父模块，继续同一流程。上限可设在最底层，也可设在多个子项合计后的中间层。本校模板保持原始分直接计算，不把全部节点自动换成百分制。

仅“按比例汇总”的节点要求直接下级比例合计100%；直接累加不要求子项比例。折算启用时基数必须大于0；输入来源、有效范围和缺失政策需明确。导入超出有效范围时提示错误，不通过封顶掩盖无效成绩。最终显示两位小数，中间不按显示位数提前舍入。

每个节点只汇总直接下级，不能再把其原始明细、小计和展示用比例分重复加入。输入、封顶前后、比例贡献、扣分和最终结果都可展开查看。

## 5. 本校首版模板与示例

首版提供套用模板，不要求管理员从空白配置。模板按附件表头和一致汇总结构建立，不复制原表中的漏公式与重复合计问题。

| 所属模块 | 汇总方式 | 原始上限 | 对父级贡献 |
|---|---|---:|---|
| 红色文化引领工程 | 四个子项直接相加 | 100 | 乘10%进入基础性素质 |
| 学业成绩 | 成绩录入／导入 | 按来源校验 | 乘80%进入基础性素质 |
| 体育素质 | 成绩录入／导入 | 按来源校验 | 乘10%进入基础性素质 |
| 基础性素质 | 上述三项按比例汇总 | 不额外配置 | 乘80%进入总分 |
| 志愿服务实践工程 | 三个子项直接相加 | 30 | 原分进入发展性素质 |
| 人文素质提升工程 | 三个子项直接相加 | 30 | 原分进入发展性素质 |
| 卓越工匠培养工程 | 三个子项直接相加 | 40 | 原分进入发展性素质 |
| 发展性素质 | 三个工程的封顶后原分相加 | 不额外配置 | 乘20%进入总分 |
| 法制与校规校纪扣分 | 管理员录入正数扣分额 | 依学校细则 | 在加权总分后按100%扣减 |

模拟某同学红色文化、学业、体育为80、90、70，三个发展工程封顶后分别为18、24、20，没有纪律扣分：

```text
基础贡献 = (80×10% + 90×80% + 70×10%)×80% = 69.60
发展贡献 = (18+24+20)×20% = 12.40
总分 = 69.60 + 12.40 = 82.00
```

具体列映射和原表差异见[学校评分模板-公式核查](../research/学校评分模板-公式核查.md)。模块名称、100／30／30／40上限和各比例均来自模板数据，不写进通用计算函数。

### 活动分值如何使用

“校园志愿服务”归属“志愿服务”子模块，每人统一加3原始分。导入50名学生、提交一份共享证明，审核后每个人的志愿服务原始分均增加3。

在本校配置下，这3原始分在志愿工程尚未触及上限时对综合成绩的贡献为：

```text
3×20% = 0.60
```

如果一名同学该项已满30分，再参加活动仍保留参与记录，但不再增加该项得分。同一活动规则对所有人一样；不同学生的已累计分数不同，所以封顶后的实际新增总分可能不同。

活动加3分不等于综合总分直接加3分。学生界面同时说明“原始加分”和“折算后计入分数”，避免误解。

### 更多层级的例子

```text
发展素质：占总分20%
├─ 社会实践：占发展素质60%
│  ├─ 志愿服务：占社会实践70%
│  │  └─ 活动记录或成绩，需要时明确启用满分折算
│  └─ 劳动实践：占社会实践30%
└─ 创新活动：占发展素质40%
```

以上是另一种通用配置例子，不是本校三个工程的实际汇总关系。若该例的志愿服务节点得分为80，其总分贡献为80×70%×60%×20%＝6.72分。若以后需要继续拆分，仍使用同一配置与逐层汇总方式。

## 6. 简单的配置与使用流程

管理员创建学期 → 套用本校模板或自建模块树 → 检查直接累加／比例汇总方式、上限及扣分位置 → 给最底层模块设置来源 → 输入测试分数预览 → 开启使用。

活动发布者填写活动及统一加分 → 上传名单与共享证明 → 管理员确认分值和认定名单 → 系统更新学生成绩。活动分值确认一次后适用于该活动全部认定参与者，不允许给名单中的个别人手工设另一分值。

个人申报选择管理员创建的加分项目并提供材料，项目绑定一个子模块和统一分值；学生不能自由填写想要的分数。管理员审核通过后计入。首版不做复杂的个人竞赛身份、奖项等级分值矩阵；需要不同分值时由管理员建立不同加分项目。

学业、体育等子模块由管理员通过CSV／XLSX导入，支持列对应、预览和逐行错误提示。必需成绩未导入时显示待录入，不能把缺失当成0分结算。

同一学生、同一活动重复导入不重复加分；个人申报若对应已有活动记录，关联到同一记录，不能重复计分。重复文件本身不直接认定为违规，共享证明本来就可被多人引用。

学期内允许管理员修改配置，保存前显示受影响人数与示例分数，确认后对本学期所有学生统一重算，不保留并行生效的多套规则。已有记录的子模块不能直接删除，需先迁移记录或保留该模块；改为不兼容的数据来源时阻止保存并提示原因。

期末发布成绩供学生核对，异议交管理员处理；完成后锁定学期并导出。需修正时，管理员填写理由、重新开放该期、修正后统一重算并再次发布锁定；保留修改日志与锁定时的结果备份，不做复杂更正审批系统。

## 7. 排名与可解释性

管理员可按学院、专业或班级筛选排名，所有人使用同一学期方案；学生查看自己的总分、分项及所在范围名次，不查看其他学生个人材料。

总分同分并列，名次采用1、2、2、4。尚有必需成绩缺失时结果标记不完整，不能混入最终排名。

成绩页逐项显示原始累计分、封顶前后、汇总方式、比例、扣分和对最终总分的贡献；只有启用折算时显示折算基数与折算分。参与记录显示活动名称、统一原始加分、审核状态及证明。

## 8. 为快速开发移除的能力

不做规则公式编辑器、任意条件编排、同校多套学生方案、规则版本迁移、可信组织免审授权、独立复核角色、跨校运营和复杂奖项互斥。多层模块嵌套已明确保留，采用统一节点结构，不写死业务层数。

独立扣分已纳入首版必需功能。本校模板由管理员登记总分扣分，记录数值和理由，不把扣分藏在普通加分模块中。总分是否最低0分由下限配置明确决定；原表未有0分下限公式，因此本校模板不擅自开启。

实现重点保留在模块配置、统一算法、角色权限、批量导入、共享证明、审核与汇总，而不是做一个通用规则引擎。具体技术栈和开发任务另行规划。

## 9. 生产交付质量与本地部署

用户已明确要求生产版本。以下是本业务范围的交付验收要求，当前演示部署也按同一实现执行：

1. **生产构建与部署**：采用 TypeScript＋Next.js 单项目应用，复用 shadcn/ui 组件与布局；用 Docker Compose 运行生产构建和 PostgreSQL。配置通过环境变量提供，提供环境配置示例、初始管理员建立、数据库迁移和启动说明。
2. **持久保存与恢复**：数据库与证明文件分别持久化，应用容器更新或重启后记录仍可使用。提供覆盖数据库、证明文件及其引用关系的备份与恢复流程，并实际演练恢复。
3. **服务端权限**：所有读写操作与证明文件下载检查登录、角色和数据归属。学生读取本人数据，发布者管理本人活动，管理员按既定职责管理；前端显示权限与服务端检查一致。
4. **账号与会话**：密码以成熟算法的哈希保存；落实初始密码、首次改密、管理员重置、登录限制及改密后的会话处理。账号停用或权限变化能够在受保护操作中生效。
5. **输入与附件**：在服务端验证导入数据、评分配置和请求参数；限制证明文件类型与大小，使用受控文件标识和鉴权访问路径。导入错误可定位到行，预览与正式导入采用一致规则。
6. **数据一致性**：通过数据库唯一约束和事务落实重复参与去重、审核认定、成绩更新与学期锁定。并发或重复提交不能重复加分；锁定状态在服务端阻止普通修改，明确更正流程继续有效。
7. **精确计分与可追溯**：沿用通用配置、明确舍入规则和过程明细；保留必要操作记录、修改理由与结算快照，日志能够用于定位失败且控制个人材料的暴露。
8. **自动化与业务验证**：覆盖核心计分、权限隔离、重复导入、审核状态变化、锁定更正和关键页面流程；运行类型检查、代码检查、生产构建与相关测试，记录验证环境和数据规模。现有Python计算验证只是评分模型证据，正式应用仍需独立验证。

技术与部署决定见[技术方案](../design/技术方案讨论.md)，架构原因见[单项目决策](../adr/0001-nextjs-application.md)及[本地生产部署决策](../adr/0002-local-production-deployment.md)。
