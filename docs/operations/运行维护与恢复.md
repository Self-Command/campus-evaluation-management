# 运行维护与恢复

更新：2026-10-24。本文件适用于本机开发与 standalone 运行；容器化生产部署见[容器化部署手册](../deploy/docker.md)。

## 1. 运行组件

| 组件 | 版本/位置 | 说明 |
|---|---|---|
| Node.js | 24 LTS，npm 11 | 仅监听回环地址 |
| Next.js | 16.4.2，`output: standalone` | 开发产物 `.next/`，生产构建 `.next-production/` |
| PostgreSQL | 18.4（embedded-postgres 锁定版本） | 默认 `127.0.0.1:55432`，数据目录 `%USERPROFILE%\.campus-evaluation-dev\postgres` |
| Prisma | 7.10.1 | 迁移目录 `prisma/migrations/`，当前 28 项 |
| 应用 | `http://127.0.0.1:3000` | `http://localhost:3000` 同协议同端口可写入，但 cookie 按主机隔离 |

## 2. 启动与停止

首次：

```bash
npm ci
npm run dev:setup     # 生成 .env，已存在则拒绝覆盖
npm run db:local      # 启动本机 PostgreSQL，保持终端运行
```

另一终端：

```bash
npx prisma generate
npm run db:migrate
npm run db:seed
npm run dev
```

日常只需 `npm run db:local` 与 `npm run dev`。停止顺序：先停 Next.js，再在数据库终端 Ctrl+C。不要同时启动多个数据库进程或开发服务器，不要手动删除数据目录。

## 3. 构建与生产运行

```bash
npm run build     # prisma generate + next build，输出 .next-production
```

`postbuild` 会把静态资源同步到 standalone 目录；跳过会导致 HTML 可打开但 JS/CSS 404。启动：

```bash
npm start         # next start，读取 .next-production
```

构建与热更新目录隔离，构建不会影响正在运行的开发服务。

## 4. 健康检查

| 地址 | 检查内容 | 失败表现 |
|---|---|---|
| `GET /api/health/live` | 进程存活 | 无响应 |
| `GET /api/health/ready` | 数据库连接、`User` 表可读、无未完成迁移 | 503 `{status:"not_ready"}` |

就绪检查不向匿名调用返回数据库诊断信息。新增迁移后应同步扩展迁移版本校验。

## 5. 备份

生产与验收优先使用管理员“数据库备份”页面：创建 PostgreSQL custom 格式备份、下载到独立存储、上传已有备份、按保留策略清理。应用通过 `BACKUP_DIR` 保存备份、上传暂存与恢复报告；standalone 本机运行时如果 `pg_dump`、`pg_restore`、`psql` 不在 `PATH`，需设置 `PG_DUMP_BIN`、`PG_RESTORE_BIN`、`PSQL_BIN` 指向 PostgreSQL 18 客户端。

开发库迁移前的命令行备份脚本为 `scripts/backup-before-migration.ts`：

- 仅允许 `127.0.0.1` 且库名以 `_dev` 结尾，防止误备份生产库。
- 输出到 `.local/migration-backups/<ISO 时间>/`：`database.dump`（pg_dump custom 格式，并用 `pg_restore --list` 校验）、`database-rows.json`（全表行快照，Decimal 以文本保存）、`database-rows.sha256`、`manifest.json`（行数、字节数、格式）。
- 备份只覆盖数据库，不复制附件；附件目录 `.local/evidence`、`.local/activity-attachments` 需单独备份。
- 备份失败时脚本以非零退出，禁止继续迁移。

## 6. 恢复

内置恢复适用于页面可访问、数据库仍可连接的情况：

1. 在“数据库备份”选择备份，填写理由并二次认证，执行预检；预检会在隔离候选库真实还原，检查迁移前缀/校验和、表行数、管理员与附件风险。
2. 预检后在当前库发生写入会使指纹失效，必须重新预检。
3. 确认恢复后站点进入维护模式；应用原子切换数据库，失败自动回滚，完成后所有会话失效、所有账号必须重新登录。
4. 恢复报告和恢复前审计旁路保存在 `BACKUP_DIR/restore-reports`，用于追责和人工复核。

应用无法启动或数据库不可连接时，按[容器化部署手册](../deploy/docker.md)第 10.3 节使用命令行恢复：

1. 停止应用写入，保留当前 `.env` 与附件目录。
2. 在隔离数据库（如 `campus_restore_*`）部署对应历史迁移后恢复：优先 `pg_restore`；只有行快照时按 `database-rows.json` 回填，并核对 `manifest.json` 的 `users/terms/evidence` 计数。
3. 校验关键计数、唯一约束、附件引用与哈希，再切换 `DATABASE_URL`。
4. 破坏性恢复不得在开发库直接演练；恢复完成后重跑 `npm test` 与就绪检查。
5. 恢复失败时保持原库不变，不用部分恢复的库对外提供服务。

容器启动时若 `BACKUP_DIR/restore-state.json` 仍是非终态，入口脚本会跳过自动迁移和管理员初始化，应用以维护页启动；不要删除状态文件，按恢复报告处理后再由管理员完成或回滚。

## 7. 常见故障

| 现象 | 排查 |
|---|---|
| 启动报数据库连接失败 | `db:local` 是否仍在运行；`.env` 的 `DATABASE_URL` 端口是否为 55432 |
| 页面 200 但样式/脚本 404 | 构建后未执行 `postbuild`，或启动目录不是 standalone 产物 |
| 登录后立即掉线 | 切换了 `localhost`/`127.0.0.1`；cookie 按主机隔离，重新登录 |
| 就绪检查 503 | 存在未完成迁移或数据库不可读，先 `npm run db:migrate` |
| 初始化数据库编码错误 | 项目路径含中文，数据库二进制与数据必须放在英文路径 |
| 端口被占用 | 只允许一个开发服务器与一个数据库进程，先停止旧进程 |
| 所有页面跳转到维护页 | 存在未完成的数据库恢复；查看 `BACKUP_DIR/restore-state.json` 与恢复报告，不要直接删状态文件 |
| 备份预检提示缺少客户端工具 | 设置 `PG_DUMP_BIN`、`PG_RESTORE_BIN`、`PSQL_BIN` 指向 PostgreSQL 18 客户端 |
| 上传备份接近上限时失败 | 反向代理 `client_max_body_size` 至少 70m；应用按 8 MiB 分块上传，并校验完整文件 SHA-256 |

## 8. 安全边界

当前仅监听回环地址，适用于本机开发与验收。公网或局域网发布前必须另行配置 HTTPS、可信反向代理来源限流、Cookie 安全属性、安全响应头与独立渗透验收；现有登录限流不覆盖公网代理场景。凭据文件、`.env`、数据库、附件与备份均不得提交仓库或对外分享。
