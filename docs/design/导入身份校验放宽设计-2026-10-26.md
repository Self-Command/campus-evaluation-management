# 导入身份校验放宽与学生活动证明查看设计

状态：已实施（2026-10-26，v0.4.0）  
日期：2026-10-26  
范围：活动参与名单导入、成绩导入、学生查看活动证明；不含学生账号导入  
文档构成：第 1–9 节为导入身份校验放宽；第 10–17 节为学生查看活动证明；第 18 节为实施与验证记录

## 1. 结论

建议把“参与名单”和“成绩导入”的学生身份确认改为：

> **学号 + 姓名**匹配系统有效学生档案；学院、专业、班级不再作为必须一致的校验条件。

学院、专业、班级仍可以出现在文件中，但只作参考：

- 留空：直接使用系统档案归属。
- 与系统档案不一致：在预览中显示提示，按系统档案归属处理，不阻断导入。
- 文件里的组织字段不能决定权限、活动范围或班级归属。

学生账号导入**不适用**这条规则，继续保持五字段严格校验。账号导入是在创建账号、学生档案和班级归属，不能仅凭学号 + 姓名判断一个新账号该放到哪个班级。

## 2. 现状盘点

| 导入 | 当前身份校验 | 能否放宽为学号 + 姓名 | 原因 |
| --- | --- | --- | --- |
| 活动参与名单 | 学号、姓名、学院、专业、班级逐项精确匹配；另校验账号、档案、班级/专业/学院启用状态、责任辅导员、活动范围、重复身份、已移除参与记录 | **可以放宽组织三列** | 学号唯一，姓名做二次确认；组织归属以系统档案为准，活动范围仍由系统判断 |
| 成绩导入 | 学号、姓名、学院、专业、班级逐项精确匹配；另校验辅导员班级范围、成绩格式与范围、待审修订、重复行 | **可以放宽组织三列** | 同上；辅导员范围已在服务端按班级限定，文件组织字段不参与授权 |
| 学生账号导入 | 学号、姓名、学院、专业、班级；同班同名不同学号需确认 | **不可以放宽** | 导入本身负责创建账号、学生档案和班级归属；新账号没有系统档案可回退，放宽会把学生建到错误班级 |

其他上传（证明、活动附件、品牌图片）不是学生名单导入，不适用本节的导入身份规则；其中学生查看活动证明的权限设计见第 10 节。系统目前没有扣分或申报的批量导入。

## 3. 新校验规则

### 3.1 身份匹配

1. 学号必填，按文本处理；使用现有 `identityNumberKey` 做 NFKC、去零宽、去首尾空白和大小写规范化。数字单元格仍拒绝，保留前导零。
2. 姓名必填，使用现有 `identityNameKey` 做 NFKC、去零宽、去空白和大小写规范化；显示仍用系统档案原文。
3. 先用学号匹配唯一学生账号，要求：
   - 角色为 `STUDENT`；
   - 账号未停用；
   - 已建立学生档案。
4. 再比较姓名。姓名不一致仍为错误，不降级为提示；提示语明确指出“学号与姓名不一致”，避免仅凭学号导错人。
5. 学号不存在、账号停用、档案缺失、姓名不一致，均保持整批阻断。

### 3.2 学院、专业、班级

| 文件中的组织字段 | 处理 |
| --- | --- |
| 未提供（模板无该列或单元格为空） | 不提示，直接使用系统档案 |
| 与系统档案一致 | 不提示 |
| 与系统档案不一致 | 预览显示黄色提示“文件中的学院/专业/班级与系统档案不一致，已按系统档案处理”，不阻断 |
| 系统档案内部不一致（档案组织与绑定班级不一致） | 仍为错误，需管理员先更正组织归属 |

匹配成功后，活动范围、辅导员班级范围、成绩归属、预览展示和最终写入全部使用系统档案，不使用文件文本。

### 3.3 继续保留的阻断项

以下规则不变：

- 文件内学号重复（参与名单整批阻断；成绩导入同一学号同分跳过、不同分报错）。
- 学号未匹配、账号停用、学生档案缺失。
- 学生所属班级、专业或学院已停用。
- 班级未配置有效责任辅导员，或辅导员与学院归属不一致。
- 学生档案组织与绑定班级不一致。
- 同班同名不同学号且未完成重复账号确认。
- 学生不在活动面向的学院/班级范围（参与名单）。
- 参与事实已移除、活动未发布、缺少有效活动证明、活动名单已封存。
- 成绩格式错误、超出模块范围、该学生该模块已有待审或退回修订。
- 预览后数据变化、批次过期、非本人批次、越权角色或跨范围操作。

### 3.4 提示与提交

- 预览返回新增 `warnings` 数量和每行提示文本；提示不影响 `errors` 统计和提交条件。
- 有提示时，提交按钮文案显示“确认导入（含 N 条组织提示）”，让操作人看到差异，但不增加逐行确认。
- 提交结果和审计详情记录提示条数，便于事后追溯；不新增数据库字段，沿用现有 JSON 结果字段。

## 4. 模板设计

建议本版同时简化模板，让“学号 + 姓名”规则直接体现在文件格式上：

| 模板 | 新版本 | 表头 | 旧文件兼容 |
| --- | --- | --- | --- |
| 活动参与名单 | `participation-v6` | `学号,姓名` | 旧五列文件继续接受；学院/专业/班级列可保留、可留空、可忽略 |
| 成绩输入 | `grades-v4` | `学号,姓名,成绩` | 旧六列文件继续接受；用户只映射学号、姓名、成绩三列 |
| 学生账号（学生） | 保持 `accounts-v2` | `学号,姓名,学院,专业,班级` | 不变 |
| 学生账号（辅导员/学院） | 保持 `accounts-staff-v1` | 登录账号、姓名、学院编码、学院名称 | 不变 |

兼容原则：

- 旧模板文件不要求重新制作，服务端按表头识别需要的列。
- 参与名单只强制要求“学号、姓名”表头；其余列存在时读取，不存在时忽略。
- 成绩导入的列映射只强制“学号、姓名、成绩”，且三者必须是不同列；旧文件的组织列可以不映射。
- 新模板不放入示例学生行。

## 5. 页面与预览

- 成绩导入的列映射只显示学号、姓名、成绩三个必选映射；旧文件多出的列不参与导入。

- 预览筛选增加“有提示”入口；错误仍单独统计。
- 结果页显示“写入 N 条，含 M 条组织提示”，不把提示描述成失败。

## 7. 测试与验收

在隔离 PostgreSQL 上执行，不接触生产库：

1. 参与名单：学号、姓名正确，学院/专业/班级与档案不一致 → 预览无错误、有提示，提交成功，参与事实落到正确学生。
2. 参与名单：新两列模板、旧五列表头；组织列留空、缺失、匹配、不匹配四种情况。
3. 参与名单：姓名错误 → 整批阻断；学号不存在、账号停用、无档案、班级停用、无辅导员 → 仍阻断。
4. 参与名单：活动范围外学生 → 仍阻断；同班同名重复账号未确认 → 仍阻断；已移除参与事实 → 仍阻断。
5. 成绩导入：新三列模板和旧六列文件；组织不一致提示但成功；姓名错误、成绩越界、待审修订、辅导员跨班 → 仍阻断。
6. 账号导入：原五字段严格校验和同班同名确认测试保持不变。
7. 旧版本未提交的预览批次：在新规则下重新校验，仍受快照、有效期和权限保护。
8. 质量门禁：`npm run typecheck`、ESLint、`npm test`、`npm run build` 全部通过；用户自行完成浏览器验收。

## 8. 风险与取舍

- **导错整份文件的风险上升。** 组织字段不一致不再阻断，若管理员上传了学号、姓名都正确但属于其他班级的名单，系统只会提示。缓解措施：预览显示系统组织与提示条数，提交按钮带提示数量，审计记录提示数，活动范围和辅导员范围仍由系统判定。
- **姓名仍是硬条件。** 学生改名后文件旧姓名会被阻断；需要先更新档案或使用补录，这是有意的防错边界。
- **账号导入不放宽。** 它负责创建组织归属，无法用学号 + 姓名替代班级、专业和学院。
- **旧模板长期存在。** 旧五列/六列文件继续可用，因此“组织列可随便填”的旧习惯可能延续；页面说明和新模板会逐步引导。

导入部分的改动范围、风险和待审批决策已分别列在第 3–8 节和第 17 节；本节不再重复决策清单。

## 10. 学生查看活动证明：结论与范围

**结论：已登记参加某活动、且参与记录未被移除的学生，应能在该活动详情查看并预览/下载当前有效的活动证明，不再要求等到成绩发布。**

本期边界：

- 只读：学生不能上传、更换或删除活动证明，也不能查看历史版本。
- 只展示当前有效版本：主办学院更换证明后，学生看到新版本，旧版本不可再下载。
- 只对参加者开放：仅符合活动范围但尚未登记的学生不可见。
- 不改变活动参与审核链、成绩计分规则、导入规则和现有主办学院维护流程。
- 复用现有活动证明数据、文件读取接口和预览组件，不需要数据库迁移。

## 11. 现状分析

### 11.1 学生当前能看到什么

| 入口 | 学生能否看到活动证明 | 实际行为与原因 |
| --- | --- | --- |
| 活动详情 → 活动证明 | 否 | `activity-detail.tsx` 的 `canSeeParticipation` 排除了 `STUDENT`，整个证明标签不渲染 |
| 活动详情 → 我的参与 | 基本看不到 | `activity-participants.tsx` 的 `OwnParticipation` 只汇总 `source.evidence`（个人来源附件），没有读取共享的 `activityEvidence`；导入名单通常没有个人附件 |
| 活动参与页 `/recognitions` | 否 | `recognitions/page.tsx` 把学生重定向到 `/my-activities`，学生侧栏也没有该入口 |
| 我的成绩 → 来源明细 | 通过并发布后可以 | `results.ts` 只统计 `APPROVED` 且未移除的参与，`source-records.tsx` 才会展示 `activityEvidence` |
| 文件读取接口 `/api/evidence/[id]` | 有条件可以 | `evidence.ts` 的 `downloadEvidence` 通过 `activityEvidence.sources` 判断学生是否为参与来源，但没有校验参与是否已移除、证明是否仍有效 |
| 活动详情服务端返回 | 所有可见学生都会收到证明元数据 | `getActivity` 无条件把 `activity.evidence` 传给所有可见角色，只是页面没有渲染 |

### 11.2 根因

1. **页面把“证明”与“参与名单管理”绑定。** 证明标签沿用 `canSeeParticipation`，学生被一并排除。
2. **学生“我的参与”数据不完整。** 学生详情只加载了认定来源的个人附件，没有加载活动共用证明；因此即使审核已开始，学生也只能看到状态，看不到主办学院上传的证明。
3. **没有学生侧只读展示。** 现有证明标签面向主办学院/审核人员，包含上传按钮和版本历史；学生需要的是只读的当前版本。
4. **服务端权限口径与页面口径不一致。** 下载接口按“是否存在认定来源”授权，而不是按“是否存在有效参与”授权；已移除参与、历史证明版本仍可能被知道文件 ID 的人读取。
5. **时间上过晚。** 成绩页要等认定通过并发布结果后才出现证明，无法在审核过程中查看。

### 11.3 可复用的基础

- `ActivityEvidence` 与 `RecognitionSource.activityEvidenceId` 已能表达“活动共用证明”，无需改表。
- `getActivity` 已返回活动证明（非管理员只返回当前有效版本），页面只需增加学生可见条件。
- `EvidenceViewer` 和 `/api/evidence/[id]` 已支持图片、PDF 的预览、新窗口打开和下载，可直接复用。
- 文件接口已有 `private, no-store`、文件签名和哈希校验，不需要新建下载通道。

## 12. 可见性与权限规则

### 12.1 学生可见条件

以“是否存在有效参与记录”为准，不以活动范围为准：

| 学生状态 | 活动详情“活动证明”标签 | 文件读取接口 |
| --- | --- | --- |
| 已登记参加，参与未移除 | 可见，显示当前有效版本 | 允许读取当前有效版本 |
| 已登记参加，后来被移出名单 | 不可见 | 拒绝 |
| 符合活动范围，但未登记参加 | 不可见 | 拒绝 |
| 参与来源处于待辅导员审核、待学院审核、已退回、已通过或未通过 | 可见（只要参与未移除） | 允许读取当前有效版本 |
| 活动已结束 | 可见 | 允许 |
| 活动被撤回 | 可见（建议保留，见 17 节决策 6） | 允许 |
| 学生查看历史证明版本 | 不可见 | 拒绝，只允许 `active=true` 的版本 |
| 非学生的审核、管理角色 | 维持现状 | 维持现状 |

说明：

- 学生参加了活动，就应该能核对主办学院上传的活动证明材料，而不是只能看到审核状态。
- 参与被移除后，参与事实和计分都已撤回，活动证明访问同时收回。
- 学生只应看到当前有效版本；旧版本可能已过期或已被替换，不应继续向学生开放。
- 活动撤回后，已登记且未移除的学生仍能打开活动详情和自己的参与记录，因此建议证明也保持可见；若审批时要求撤回即隐藏，则改为同时检查 `publishedAt`。

### 12.2 数据最小化

- `getActivity` 对“未参加该活动的学生”不再返回证明元数据（文件 ID、名称、说明、上传时间）。目前这些数据虽未渲染，但已经进入页面数据。
- `downloadEvidence` 对学生的活动证明授权改为直接检查：该证明所属活动存在本人 `registeredAt` 非空、`removedAt` 为空的参与记录。
- 学生只能读取 `active=true` 的活动证明版本；历史版本仅保留给有管理或审计需要的角色。
- `canReadActivityEvidence` 目前未被任何路由调用，且规则与下载接口不完全一致；实施时同步收敛或删除，避免出现两套权限口径。

### 12.3 不变的部分

- 主办学院、学院管理员、管理员、经办人上传/更换证明和查看历史版本的规则不变。
- 辅导员、学院审核人员按现有学生范围查看证明的规则不变。
- 学生本人上传的个人证明、申报材料、异议材料读取规则不变。
- 学生查看活动证明不写审计日志（与当前学生读取材料的行为一致）；管理人员下载仍按原规则记录。

## 13. 页面与交互设计

### 13.1 活动详情标签

学生参加活动后，活动详情显示：

- 活动详情
- 活动证明
- 我的参与

未参加活动的学生仍然只有“活动详情”（以及符合条件时的其他内容），不会出现证明标签。

### 13.2 只读证明标签

学生看到的证明标签复用现有卡片结构，但：

- 只显示当前有效版本及“当前有效”标记。
- 显示版本号、证明说明、上传时间和文件预览/下载按钮。
- 不显示“上传新证明”“更换证明”等管理按钮。
- 不显示历史版本列表。
- 说明文案改为：“活动证明由主办学院统一上传；仅参加该活动的学生可查看当前有效版本。”
- 没有有效证明时显示：“主办学院尚未上传活动证明，可稍后再查看。”
- 支持通过 `?tab=evidence` 直接打开；`initialTab` 的允许条件同步改为学生参与者也生效。
- 移动端沿用现有可横向滚动标签栏，不新增控件。

### 13.3 主办学院侧提示

## 16. 风险与取舍

- **证明内容可能包含其他学生信息。** 活动证明可能是签到表、合影或名单；开放给参加者属于活动内部共享，但未参加者仍不可见。主办学院应避免上传与活动无关的敏感材料。
- **证明说明可能被学生看到。** 这是有意的透明化；上传对话框明确提示不要填写内部备注。
- **撤回活动后的可见性需要取舍。** 保留可见便于学生核对历史，但会延长材料可见时间；隐藏更保守，但学生将无法核对自己参加过的活动材料。
- **移除参与后立即失去证明访问。** 这符合“参与事实已撤回”的语义，但学生如需申诉，需要联系主办学院或通过成绩异议流程处理。
- **学生读取不写审计。** 与当前学生查看个人材料一致，避免大量浏览日志；如果后续需要证明访问留痕，可单独增加。
- **只开放当前版本。** 学生会失去对旧版本的访问，旧版本仅保留给管理和审计；这与“更换证明后按新版本重新审核”的业务规则一致。
