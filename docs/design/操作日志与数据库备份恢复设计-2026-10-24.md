日期：2026-10-24  
状态：**已批准，实施中（0.3.0）**  
适用系统：综合测评管理系统（Next.js 16 / Prisma 7 / PostgreSQL 18 / Docker Compose）  
关联文档：[管理员设置中心](../features/15-管理员设置中心.md)、[Docker 部署与服务器验证](../audit/Docker部署与服务器验证-2026-10-24.md)、[部署手册](../deploy/docker.md)、[模板来源与适配清单](模板来源与适配清单.md)

## 0. 结论摘要（先看这一页）

本报告建议把两个需求拆成两条能力，并明确边界：

| 能力 | 建议方案 | 关键取舍 |
| --- | --- | --- |
| 操作日志 | 扩展现有 `AuditEvent`，统一记录成功/失败、操作者快照、IP、User-Agent、请求 ID；提供管理员筛选、详情、CSV 导出、保留期清理 | 记录所有**有权限的写操作和高风险数据读取**，不记录普通页面浏览，避免日志表和磁盘被无效流量撑爆 |
| 数据库备份 | 管理员页创建 PostgreSQL 自定义格式快照，校验、下载、按保留策略清理；恢复时先还原到**独立新库**做迁移与校验，再原子切换数据库名 | 任意数据库 dump 的行级合并不可靠，不提供“伪合并”；`pg_restore --clean` 不会清除备份中不存在的新表，因此不做原地覆盖 |
| 冲突处理 | 恢复前给出影响报告（数据量、时间差、迁移校验和、登录管理员可用性、设置差异），明确“整库替换”；合并导入作为后续独立能力 | 把“冲突”定义清楚：整库恢复的冲突就是覆盖，必须让管理员在替换前看到会丢失什么、恢复后用什么账号登录 |
| 恢复安全 | 恢复后清空全部 `AuthSession`、递增所有 `User.authVersion`、清空登录失败/验证码临时状态；恢复前的审计事件写入旁路 JSONL 并在恢复后回导 | 备份中的旧会话必须视为不可信；审计表随库回滚，不做旁路就会留下“恢复前操作无记录”的空档 |
| 附件 | 第一版数据库备份**不包含**证明与活动附件文件；新增只读“附件管理”页，按活动聚合查看/下载，并支持学生证明、活动附件按范围导出 | 附件导出是人工取数，不能替代一致性备份；数据库恢复后文件仍可能缺失，完整归档作为第二阶段 |
| 权限 | 仅 `ADMIN`；恢复、删除备份、下载备份、清理日志、修改保留期、导出日志、批量导出证明/附件需重新输入当前密码并填写理由 | 高风险操作不能只依赖已登录会话 |
| 默认保留 | 操作日志 180 天，可设 30–3650 天；备份保留最近 14 份；恢复前旧数据库保留 7 天、安全快照至少保留 7 天 | 兼顾审计追溯与磁盘占用，管理员可调整 |

建议作为一个 `0.3.0` 版本交付，包含数据库迁移。批准后按第 10 节顺序实施，并在隔离 PostgreSQL 上完成“备份→破坏→恢复→校验”演练后才允许推送和更新服务器。

### 0.1 对三个具体问题的直接回答

- **系统设置的修改理由会不会进日志？** 会。新设计把理由从 `details.reason` 提升为独立 `reason` 字段；凡是界面要求填写理由的保存动作（设置、账号、学期部分操作等），日志列表、详情、CSV 导出都能直接看到。**当前版本**的理由只写进了数据库 `AuditEvent.details`，管理端没有日志页面，所以填完在界面上看不到；类似缺口见 1.4 表。
- **证明和附件能导出吗？能按全校/学院/专业/班级吗？** 能。学生证明按学生**当前**学院/专业/班级导出；活动附件按活动**真实受众覆盖**导出。`ALL` 活动会出现在每个学院/班级的导出中，`COLLEGE` 看 `audienceColleges`，`CLASS` 看精确班级键；活动归属学院是另一个独立筛选，不能拿来代替受众。
- **附件管理能一个活动只显示一条吗？** 能。`/attachments` 按活动聚合，一个活动一行，显示附件数、图片/文件数、总大小、最近上传；展开后再看单个附件。只读查看/导出，删除仍回原活动，避免第二套删除权限。

## 1. 现状与差距

### 1.1 操作日志现状

- 已有 `AuditEvent` 表：`id`、`actorId`、`action`、`targetId`、`details`、`createdAt`。
- 业务代码中已有 **59 处** `src/server` 审计写入，覆盖账号、组织、学期、活动、参与、成果、成绩、扣分、结果发布、异议、设置、导入导出等主要动作（Prisma 生成文件中的示例不计）。
- 但当前只有“写入”，没有面向管理员的查询、详情、筛选、导出、保留期和清理能力。
- 字段不足：没有操作者角色/姓名快照、成功/失败、IP、User-Agent、请求 ID、路由、目标类型；账号被删除或改名后难以还原操作现场。
- 理由没有独立字段：多数理由塞在 `details.reason`，无法稳定筛选、导出或在列表直接展示；旧日志与新日志的读取方式不一致。
- 动作代码存在动态拼接（如 `TERM_${data.action.toUpperCase()}`）和同义动作（锁定、重开、发布、确认等各自命名），缺少集中动作目录，前端筛选和统计容易漏项。
- 没有索引，数据量上来后按时间、操作者、目标查询会明显变慢。
- 没有保留策略，表会无限增长；也没有“导出/清理本身也要被审计”的闭环。

### 1.2 备份恢复现状

- 只有部署手册中的手工命令：数据库容器内 `pg_dump --format=custom`、卷打包、`pg_restore --clean --if-exists`。
- 应用运行镜像只安装了 `ca-certificates`、`dumb-init`、`openssl`，**没有 `pg_dump` / `pg_restore`**，因此当前 Web 管理端无法直接执行数据库备份。
- 数据库在 `db-data` 卷；证明文件在 `evidence-data` 卷；活动附件在 `attachments-data` 卷；品牌资源在数据库 `BrandAsset.bytes` 中。数据库备份与文件备份不是同一件事。
- 没有备份清单、校验和、版本/迁移信息、恢复前安全快照、恢复影响报告和回滚流程。
- 没有恢复期间的维护锁。恢复会删除并重建表，若仍有请求写入，可能产生不可预期结果。
- JWT 会话最终会查询数据库中的 `AuthSession`；整库恢复会把备份时间点的 `AuthSession` 一并带回来，**备份时仍有效、之后已撤销的旧令牌可能重新生效**。不能依赖“恢复后自然失效”，必须显式全量失效。
- 恢复后登录凭据也回到备份时状态：管理员密码、启用状态、角色都可能与恢复前不同；当前操作的管理员甚至可能不在备份中。恢复前必须检查备份内是否仍有可用管理员，并提示操作者准备备份时的登录凭据。
- 整库恢复会把审计表也回滚到备份时间点，备份之后、恢复之前的审计记录会丢失；当前没有保留这段审计旁路证据的机制。
- 恢复会带回旧的 `LoginFailureState`、`LoginCaptcha`、`LoginAttempt` 和 `SiteSettings` 登录策略，可能恢复过期的锁定、验证码或限流计数，需要恢复后清理。
- 手册中的 `pg_restore --clean --if-exists` 只清理 dump 中存在的对象；**备份之后新增、但不在 dump 里的表会残留**，造成“旧结构 + 新表”混合状态。整库切换必须使用独立新库，不能只靠 `--clean`。
- 当前没有从备份中读取迁移校验和、管理员账号、设置差异的能力，也没有恢复前审计旁路、数据库切换或旧库保留流程。

### 1.3 现有可复用能力

- 隔离恢复脚本 `scripts/verify-migration-recovery.ts` 已证明“临时数据库 + 迁移 + 逐表行数/内容比对”的做法可行；本设计沿用其校验思想，但不把脚本直接暴露给 Web。
- `scripts/backup-before-migration.ts` 已有自定义格式 dump、行级 JSON、SHA-256 清单、行数校验的雏形。
- 认证会话有数据库版本校验（`AuthSession` + `User.authVersion`），适合在恢复后强制重新登录。
- 管理端已有账号、导入、结果发布等完整列表/筛选/确认交互，可复用其模板结构。

### 1.4 代码核对后的具体缺口

以下为逐项核对代码后的结论，不是泛泛而谈：

| # | 缺口 | 代码现状 | 影响 | 本报告处理 |
| --- | --- | --- | --- | --- |
| 1 | 审计只写不读 | `AuditEvent` 只有 Prisma 写入，没有列表、详情、导出、保留期 API 或页面 | 管理员无法追责、无法查理由 | 第 3、5、6 节新增完整日志中心 |
| 2 | 理由埋在 JSON 里 | 系统设置 `SETTINGS_CHANGED.details.reason`；账号更新/删除/重置密码、学号更正等也只写入 `details.reason` | 理由填了但界面看不到，无法筛选/导出 | 新增独立 `reason` 字段，所有要求理由的动作必填并展示 |
| 3 | 理由可见性不一致 | 成绩修改、扣分变更、成果历史、导入撤销、活动参与历史、周期作废/归档有业务页展示；系统设置、账号修改/删除/重置密码、学号更正、结果重开、确认期限延长、活动负责人变更/撤回等只进审计表或后台历史表 | 同样是“修改理由”，有的能查、有的查不到 | 新日志页统一展示；业务页保留原有历史，不互相替代 |
| 4 | 登录失败无审计 | `src/server/auth.ts` 只写成功 `LOGIN`；失败次数与锁定写在 `LoginFailureState`，没有审计事件 | 无法调查暴力尝试、锁定原因 | 新增登录成功/失败/锁定/退出审计（不记录密码和验证码） |
| 5 | 文件操作无审计 | 活动附件上传、删除、下载没有 `auditEvent`；证明下载也没有 | 附件/证明被谁取走、何时删除无法追查 | 新增附件上传/删除/下载、证明特权下载审计 |
| 6 | 动作目录缺失 | 动作为散落字符串，存在动态拼接与同义命名 | 筛选、统计、导出、前端文案容易漏项 | 集中动作目录 + 编译期校验 |
| 7 | 无请求元数据 | `AuditEvent` 没有姓名/登录名/角色快照、IP、User-Agent、请求 ID、路由、结果 | 无法定位一次操作、无法区分成功与拒绝 | 扩展字段；统一请求上下文采集 |
| 8 | 无索引、无保留期 | `AuditEvent` 只有主键；没有清理任务 | 日志无限增长、查询变慢、占满磁盘 | 5 个组合索引 + `requestId` 索引 + 默认 180 天保留 + 分批清理 |
| 9 | 审计详情无上限 | 账号导入等 `details` 可能包含大量行数据 | 单条日志过大、导出和页面卡顿 | 白名单、16 KiB 截断、敏感键过滤 |
| 10 | 备份不可在 Web 执行 | 运行镜像没有 `pg_dump`/`pg_restore`，只有手工部署命令 | 管理员无法自助备份，易漏备 | 镜像安装 PostgreSQL 18 客户端 + 独立备份卷 |
| 11 | 备份不含文件 | 证明/附件在独立卷；数据库 dump 不包含它们 | 恢复后文件可能缺失，不能宣称整站恢复 | 明确边界；附件管理支持人工取数；完整归档列为第二阶段 |
| 12 | 恢复会复活旧会话 | `AuthSession` 随库恢复；`getCurrentSession` 只校验撤销/过期/版本 | 备份时有效、之后撤销的旧 Cookie 可能重新可用 | 恢复后全量撤销会话并递增所有用户 `authVersion` |
| 13 | 恢复会丢审计段 | 整库替换会覆盖备份之后的审计事件 | 恢复前发生的操作无记录 | 恢复前全量导出当前审计到旁路 JSONL，并回导新库 |
| 14 | 无维护锁与回滚 | 没有恢复任务、维护模式、安全快照 | 恢复中写入导致不一致；失败可能半套数据 | 候选库试恢复 + 原子切换 + 安全快照 + 自动回滚 + 维护模式 |
| 15 | 附件/证明无统一视图 | 只能在单个活动或业务详情里看；没有跨活动聚合 | 管理员无法按学院/班级/专业盘点材料 | 新增只读附件管理页与学生证明导出 |
| 16 | `--clean` 不是整库替换 | `pg_restore --clean` 只删除 dump 内对象；备份后新增的表会残留 | 形成旧数据 + 新表混合结构，后续迁移与查询异常 | 还原到独立新库，校验后原子重命名切换 |
| 17 | 恢复后可能无法登录 | 备份中的管理员账号/密码/启用状态与当前不同；当前操作者可能不在备份中 | 恢复成功却无人能登录，只能改环境变量重建管理员 | 预检检查备份内可用管理员，展示登录名，强制知悉 |
| 18 | 清单行数可能不可信 | 现有脚本先 dump 再单独查行数，两次读取不在同一快照 | 校验误报或掩盖真实差异 | `pg_export_snapshot()` + `pg_dump --snapshot` 同一快照内取行数 |

> 说明：1.1 中的“59 处”只统计 `src/server` 的写入点；测试、脚本和 Prisma 生成文件不计入。现有页面里出现的 `action: "preview"` 等是前端提交参数，不是审计动作代码。

## 2. 设计原则

1. **审计不可静默丢失**：状态变更与审计写入尽量在同一数据库事务内；审计写入失败时，高风险业务操作应失败而不是“改了但没记录”。
2. **只记必要信息**：不记录密码、密码哈希、Cookie、Token、验证码、数据库连接串、完整请求体、附件内容；敏感字段按动作白名单记录差异。
3. **恢复必须可回退**：任何破坏性恢复前先生成并校验安全快照；切换在独立候选库校验后原子完成，失败不留下半套数据；校验失败自动回滚旧库。
4. **冲突必须可见**：恢复前展示“会覆盖什么、会丢失什么、迁移是否兼容”，由管理员确认，不用模糊文案掩盖风险。
5. **数据库备份不等于整站备份**：第一版明确数据库边界；附件完整性单独提示，完整归档另行交付。
6. **不引入不可审计的旁路**：不提供任意 SQL 或命令输入，不调用 Docker socket，不允许任意命令。上传的 dump 只由 `pg_restore` 还原到隔离候选库，绝不在当前库直接执行；候选库失败即丢弃。所有恢复只接受校验过的 PostgreSQL 自定义格式 dump。
7. **与现有部署约束一致**：不改 Nginx、不影响其他 Compose 项目、不操作真实开发库；备份存独立命名卷，权限最小化。
8. **页面真实可操作**：列表、筛选、导出、恢复向导均接真实 API 和真实进度；空库/无备份时展示真实空态，不放假统计或占位按钮。

## 3. 操作日志设计

### 3.1 数据模型

在现有 `AuditEvent` 上做增量迁移，不删除旧数据：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `actorId` | `String?` | 保留原字段；操作者 ID，系统任务为空 |
| `actorName` | `String?` | 操作时姓名快照，避免账号改名/删除后无法辨认 |
| `actorLogin` | `String?` | 操作时登录名快照；账号可改名，不能只靠当前 `User.login` 反查 |
| `actorRole` | `String?` | 操作时角色快照（ADMIN/COLLEGE/COUNSELOR/STUDENT/PUBLISHER/SYSTEM） |
| `action` | `String` | 稳定动作代码，统一为大写下划线，如 `ACCOUNT_CREATED` |
| `category` | `String` | 分类：AUTH/ACCOUNT/ORG/TERM/ACTIVITY/PARTICIPATION/CLAIM/GRADE/DEDUCTION/PUBLICATION/APPEAL/IMPORT_EXPORT/SETTINGS/BACKUP/LOG/SYSTEM |
| `targetType` | `String?` | 目标实体类型，如 `User`、`Term`、`Claim`、`Backup` |
| `targetId` | `String?` | 目标 ID；保留原字段 |
| `targetLabel` | `String?` | 目标名称快照（账号姓名、学期代码、活动名等），目标删除或改名后日志仍可读；最长 200 字符 |
| `reason` | `String?` | **修改/操作理由一等字段**，最长 1,000 字符；要求理由的动作必须写入，列表、详情、筛选和导出直接读取，不再从 `details` 猜测 |
| `result` | `String` | `SUCCESS` / `FAILURE` / `DENIED` |
| `requestId` | `String?` | 单次请求关联 ID，同一次请求的多条日志可串联 |
| `route` | `String?` | 请求路由或服务动作标识，如 `POST /api/admin/accounts` |
| `method` | `String?` | HTTP 方法；后台任务为空 |
| `ip` | `String?` | 客户端 IP，最长 45 字符（兼容 IPv6） |
| `userAgent` | `String?` | 截断至 512 字符 |
| `details` | `Json?` | 结构化差异、原因、导入批次、失败错误码等；单条序列化后上限 16 KiB |
| `createdAt` | `DateTime` | 保留原字段，作为保留期与查询主键 |

建议索引：

```prisma
@@index([createdAt, id])
@@index([actorId, createdAt])
@@index([category, createdAt])
@@index([action, createdAt])
@@index([targetType, targetId, createdAt])
@@index([requestId])
```

`createdAt + id` 组合索引用于游标分页（`createdAt` 相同按 `id` 排序），不再单独建 `createdAt` 索引。`requestId` 只用于精确定位一次请求。关键词模糊检索不做全表任意扫描，见 3.5。

迁移兼容：`category` 与 `result` 给旧行默认值（`SYSTEM` / `SUCCESS`），`reason`、`actorName`、`actorLogin`、`actorRole`、`targetType`、`targetLabel`、请求元数据允许为空；旧行不回填猜测值，详情按空值降级。`action` 仍保留原值，新动作按目录写入。

第一版不做表分区。按学校规模估算，即使每年 50 万条、平均 1 KiB，年增约 500 MiB；180 天保留配合索引足以支撑。若以后单表超过约 500 万行，再评估按月分区或归档表，不在本轮制造复杂度。

### 3.2 动作目录与记录边界

新增 `src/server/audit-actions.ts`，集中定义动作代码、分类、中文标签、目标类型、风险级别和允许写入的 `details` 键。调用方只能引用目录项，避免再出现自由字符串。

| 分类 | 典型动作 | 是否记录 |
| --- | --- | --- |
| 认证 | 登录成功、登录失败、账号锁定、退出、改密 | 记录；不记录密码与验证码；失败只记录掩码账号 |
| 账号 | 创建、更新、停用、删除、重置密码、导入/撤销导入 | 记录全部；密码只记录“已重置”标记 |
| 组织/学期 | 学院、专业、班级创建/修改/删除；学期创建/改名/回收站/作废/归档、结算锁定、结果重开 | 记录全部；有理由的动作把理由写入 `reason` |
| 活动 | 创建/修改/结束/重开/负责人变更、发布/撤回、证明替换、附件上传/删除 | 记录全部 |
| 参与/成果/成绩/扣分 | 提交、审核、退回、撤回、评分、更正、导入 | 记录全部，保留前后值摘要 |
| 发布/异议 | 发布、撤回、范围变更、异议处理 | 记录全部 |
| 设置 | 保存设置、上传/移除品牌资源、登录策略 | 记录字段差异与理由，不记录密钥 |
| 导入导出 | 各类导入提交/提交完成/撤销；成绩、报表、日志、备份、证明、活动附件下载 | 记录筛选条件、条数、文件哈希；不记录导出内容本身 |
| 日志/备份 | 导出日志、清理日志、创建/下载/上传/删除备份、开始/完成/失败恢复 | 记录全部；恢复审计写入恢复后的数据库，并保留旁路报告 |
| 普通读取 | 打开列表、查看详情、翻页 | **不记录**，避免无效膨胀 |
| 高风险读取 | 下载证明、下载活动附件、导出成绩明细、导出日志、下载备份、批量导出证明/附件 | 记录；数据外带必须可追溯 |

说明：用户提出“记录管理员的每个操作”。本设计将“每个操作”定义为**每个有业务影响或数据外带的操作**，而不是每个页面点击。这样既满足审计目的，也避免日志被浏览行为淹没。若需要更细的页面访问审计，应使用独立的访问日志/网关日志，不写入业务审计表。

运维与导出使用固定动作代码，便于筛选和测试：

| 动作代码 | 含义 | 结果 |
| --- | --- | --- |
| `AUDIT_LOG_EXPORT_STARTED` / `AUDIT_LOG_EXPORTED` / `AUDIT_LOG_EXPORT_FAILED` | 导出审计 CSV | 开始/成功/失败 |
| `AUDIT_LOG_PURGED` / `AUDIT_RETENTION_CHANGED` | 手动清理、修改保留期 | 成功 |
| `BACKUP_CREATED` / `BACKUP_UPLOADED` / `BACKUP_DOWNLOADED` / `BACKUP_DELETED` | 备份生命周期 | 成功/失败/拒绝 |
| `DATABASE_RESTORE_PREFLIGHTED` | 完成预检并生成候选恢复报告 | 成功 |
| `DATABASE_RESTORE_STARTED` | 管理员确认后开始切换 | 成功 |
| `DATABASE_RESTORE_COMPLETED` / `DATABASE_RESTORE_FAILED` | 切换完成或失败 | 成功/失败 |
| `DATABASE_RESTORE_AUDIT_IMPORTED` / `DATABASE_RESTORE_SECURITY_RESET` | 旁路审计回导、会话与临时登录状态清理 | 成功 |
| `STUDENT_EVIDENCE_EXPORTED` / `ACTIVITY_ATTACHMENTS_EXPORTED` | 批量导出证明/活动附件 | 成功/部分失败/失败 |
| `EVIDENCE_DOWNLOADED` / `ACTIVITY_ATTACHMENT_DOWNLOADED` | 特权角色单个下载 | 成功/失败 |

防止日志被洪水撑爆：

- 登录失败、权限拒绝等安全事件按 `IP + 动作` 每分钟最多写 60 条，超出后每分钟只写一条汇总并带 `suppressedCount`；锁定、拒绝本身照常执行，不因降采样放宽。
- 同一请求内多条业务审计共享一个 `requestId`，但不重复写相同的“开始/完成”记录。
- 普通列表、详情、翻页、健康检查、静态资源不写业务审计。

### 3.3 采集方式

- 新增统一写入函数 `recordAudit(tx, input)`：
  - 自动补 `actorName`、`actorLogin`、`actorRole`、`requestId`、`route`、`method`、`ip`、`userAgent`；
  - 校验 `action` 必须在动作目录中；要求理由的动作必须提供 `reason`；有目标实体的动作同时提供 `targetType`、`targetId`、`targetLabel`，确实无法取得名称时才只写 ID；
  - `details` 经过白名单、敏感键过滤与 16 KiB 截断；
  - 默认 `SUCCESS`；
  - 在业务事务内调用时使用传入的 `tx`，与业务变更同成败。
- 失败语义按风险分级，不能一刀切：
  - 业务写操作、发布、导入撤销、备份/恢复、日志清理、批量导出：审计写入失败即整体失败，不出现“做了但没记录”；
  - 登录失败、退出：安全控制优先，锁定与拒绝照常执行，审计失败时写结构化服务器日志兜底；
  - 单个文件下载：先写审计再开始流式响应；审计失败返回错误，不发出文件；
  - 物理文件删除在数据库删除 + 审计事务提交之后执行；若物理删除失败，记录错误并保留审计，不反向恢复数据库行。
- 新增请求上下文：在统一的 API/Server Action 包装器中建立 `AsyncLocalStorage`，一次请求只生成一个 `requestId`，并回写 `X-Request-Id` 响应头；客户端传入的请求 ID 只在符合安全字符和长度限制时沿用，否则重新生成。后台任务和脚本显式传入系统上下文。没有上下文时字段留空，不阻断脚本运行。
- 客户端 IP：
  - 生产由本机 Nginx 反代，配置固定的可信代理层数（当前为 1），只从 `X-Forwarded-For` **右侧可信跳**取值；绝不直接取客户端可伪造的最左侧值；
  - `TRUST_PROXY=true` 仅在确认反代 topology 时开启，层数变化必须同步修改配置；
  - 开发环境无可靠 socket 地址时写空，不伪造；写入前校验 IPv4/IPv6 格式与 45 字符上限；
  - 不把 IP 用于展示以外的用途，不写进导出文件名。
- 失败记录：
  - 业务事务回滚后，由 API 边界在事务外写入 `result=FAILURE/DENIED`，记录稳定错误码，不记录异常堆栈中的敏感值；
  - 登录失败只记录掩码后的账号标识、IP、结果，不记录尝试的密码；连续失败达到锁定阈值时写 `AUTH_LOGIN_LOCKED`；
  - 二次认证失败（密码错误、理由缺失、确认短语错误）写对应动作的 `result=DENIED` 审计，只记录动作与掩码账号；密码错误同时计入登录限流，达到阈值锁定并写 `AUTH_LOGIN_LOCKED`；
  - 登录成功、退出、改密分别写入；退出采用 best-effort，不因审计失败阻断登出。
- 文件操作：
  - 活动附件上传在数据库事务内写 `ACTIVITY_ATTACHMENT_UPLOADED`；删除时先完成数据库删除+审计事务，再删除物理文件，避免审计失败导致文件先丢；
  - 管理员、学院、辅导员下载证明/附件写 `EVIDENCE_DOWNLOADED` / `ACTIVITY_ATTACHMENT_DOWNLOADED`；学生下载自己的材料不逐次记录，避免噪声；
  - 批量 ZIP 导出单独写导出审计，不按每个文件重复写日志。
- 迁移策略：
  - 第一批替换高风险写操作（账号、权限、设置、发布、导入、备份恢复）；
  - 第二批替换成绩/扣分/审核类；
  - 第三批补齐文件、登录、导出事件，并清理不再有业务意义的旧动作；
  - 旧行没有新字段时，查询与详情按空值降级显示，不做破坏性回填。

### 3.4 脱敏与防泄漏

- 键名黑名单（大小写不敏感）：`password`、`passwordHash`、`token`、`secret`、`cookie`、`authorization`、`captcha`、`session`、`databaseUrl`、`connectionString`、`apiKey`、`privateKey`。
- `details` 只允许动作目录声明的键；账号密码、密钥值永远不进入日志，只记录“已变更”布尔标记或字段名。
- **所有界面要求填写“理由/原因”的写操作，理由都是必填审计字段**，包括系统设置、账号修改/删除/重置密码、活动负责人变更/撤回、评分更正、扣分变更、导入撤销等；理由必须出现在日志详情和导出中，不能只做前端校验却不落库、不展示。
- 字符串值统一截断：`reason` 最多 1,000 字符，普通字段 2 KiB，`details` 整体 16 KiB；超出部分截断并标记 `truncated: true`。
- 日志会包含姓名、学号、IP、文件名等个人信息，属于受控审计数据：仅管理员可读，不做公开检索页，不进入公开设置接口，不写入浏览器本地存储。
- 导出 CSV 防公式注入：以 `= + - @`、制表符、回车开头的单元格前置单引号；所有字段加引号并转义。
- 详情页以纯文本/结构化 JSON 渲染，不使用 `dangerouslySetInnerHTML`。
- 日志查看、导出、清理均仅 `ADMIN` 可访问；`COLLEGE`、`COUNSELOR`、`STUDENT`、`PUBLISHER` 不可见。
- 批量导出日志、下载备份、批量导出证明/附件属于数据外带，要求重新输入当前密码并填写理由；单条日志查看和单个文件下载不要求二次认证，但会记录管理员下载行为。
- 二次认证与导出使用 **POST 表单提交**：密码、理由、确认短语放在请求体，响应为流式附件；不使用 `GET` 查询参数传密码，避免进入浏览器历史、Nginx 日志和 Referer。
- 备份清单、恢复报告、审计旁路文件都包含个人信息或运行信息，权限 0600、仅管理员可读，不进入公开静态目录、不发送到第三方。

### 3.5 查询与详情

管理端新增 `/audit-logs`，放在“数据与账号”分组，位于“账号管理”之后：

- 顶部筛选：时间范围（默认最近 7 天，最大 366 天）、操作者（可搜索姓名/账号，取 `actorName`/`actorLogin` 快照）、角色、分类、动作、结果、目标类型/ID、请求 ID、理由关键词。
- 关键词检索范围限定为操作者姓名/账号、动作标签、目标 ID、请求 ID、`reason`；**不对 `details` 任意 JSON 做全表模糊搜索**，避免大表扫描和把个人材料内容变成搜索入口。需要查差异时进入详情。
- 关键词查询必须带时间范围且跨度不超过 31 天；超过时要求先缩小时间范围。这样用 `createdAt` 索引先裁剪，再对裁剪集做 `ILIKE`，不依赖额外全文检索扩展。
- 列表列：时间、操作者（姓名+账号+角色）、动作、目标（类型+名称/ID）、**理由摘要**、结果、IP、请求 ID；默认按时间倒序。理由过长时截断，详情显示全文。
- 分页：服务端分页，默认每页 20/50/100；使用 `createdAt + id` 的游标分页，避免深页 offset 变慢；页面保留筛选条件。
- 详情抽屉/对话框：完整字段、理由全文、格式化 `details`、前后值差异、错误码、请求元数据；不提供编辑或删除单条日志。
- 账号、学期、活动等管理详情页可为管理员提供“查看操作记录”链接，跳转到带 `targetType + targetId` 的日志页；不复制一套业务历史，也不向非管理员展示。
- 空态：无匹配记录时显示当前筛选条件和“清除筛选”；数据库无日志时提示尚未产生操作记录，不显示假数据。
- 导出入口：按当前筛选导出，弹窗显示预计条数与范围；超过上限时要求缩小范围，不静默截断。

### 3.6 导出

- 格式：CSV（UTF-8 BOM，Excel 直接打开不乱码）；第一版不提供 JSON，避免多一套格式与测试面。
- 流式导出：按批次查询并写响应流，不把全部结果加载进内存。
- 上限：单次 100,000 条或 366 天；超限返回明确错误，要求缩小时间范围/增加筛选条件。
- 列：时间、操作者姓名、操作者账号、角色、分类、动作、目标类型、目标名称、目标 ID、**理由**、结果、IP、请求 ID、路由、详情摘要。理由直接取 `reason` 字段，旧行回退读取 `details.reason`。
- 下载响应：`Content-Disposition` 使用安全 ASCII 文件名 + UTF-8 文件名，`Cache-Control: no-store`。
- 导出需二次输入当前密码并填写导出理由；使用 `POST` 表单提交，密码与理由在请求体，响应仍为流式 CSV，客户端直接下载，不把文件读入浏览器内存。
- 导出行为本身写入审计：开始时写 `AUDIT_LOG_EXPORT_STARTED`，正常结束写 `AUDIT_LOG_EXPORTED`；客户端中断或服务端异常时在流的 `finally` 中写 `AUDIT_LOG_EXPORT_FAILED`，记录已写字节数。审计只记录筛选条件、条数、耗时、文件哈希前缀，不记录导出内容。
- 频率限制：同一管理员同时只允许一个导出任务；失败后允许重试，避免重复点击放大数据库压力。

### 3.7 保留与清理

- 新系统策略（建议新表 `SystemPolicy`，单行或键值结构）保存：
  - 读取时若表为空则创建默认行；恢复旧备份后若缺少新增策略字段，按默认值补齐，不阻断启动。
  - `auditRetentionDays`：默认 180，范围 30–3650；
  - `auditAutoPurgeEnabled`：默认开启；
  - `backupRetentionCount`：默认 14，范围 1–100；
  - `backupSafetyRetentionDays`：默认 7，范围 1–30；
  - `previousDatabaseRetentionDays`：恢复前旧库保留天数，默认 7；
  - `restoreReportRetentionDays`：恢复报告与审计旁路保留天数，默认 180；
  - `restoreCandidateTtlMinutes`：候选恢复库保留时间，默认 30；
  - `lastPurgeAt`、`lastPurgeCount`、`lastPurgeResult`、`lastRestoreAt`。
- 自动清理：应用启动后延迟 10 分钟，之后每 24 小时执行一次；使用**当前数据库内**的 PostgreSQL advisory lock 保证多实例只有一个执行者。按 `createdAt < now - retentionDays` 分批删除，每批 5,000 条，批次间停顿 200–500 ms，避免长事务和锁表。清理完成后写一条 `AUDIT_LOG_PURGED`（`trigger: "AUTO"`，只含条数/时间范围/结果）并更新 `SystemPolicy` 摘要。
- 恢复保护：`lastRestoreAt` 在 24 小时内时跳过自动清理。恢复会把策略和日志一起回退到备份时间点，预检页必须展示“当前保留期 → 恢复后保留期”；不允许恢复后立即按旧策略大批删除。
- 清理前预览：显示将删除条数、最早/最晚时间、表与索引实际占用、预计释放空间；管理员可先按筛选导出再清理。
- 保留硬下限：最少 30 天；**不允许删除最近 7 天日志**；清理不会删除刚刚写入的清理审计本身。清理摘要同时写入 `SystemPolicy`，即使该审计行以后按保留期删除，仍能查到“何时清理过多少条”。
- 手动清理：需重新输入当前密码、填写理由、输入确认短语；使用 `POST`，执行后写 `AUDIT_LOG_PURGED`（记录删除条数、时间范围、原因，不记录被删内容）。
- 磁盘保护：
  - 管理页展示 `pg_total_relation_size('"AuditEvent"')`、数据库总大小、备份卷占用、恢复报告占用和磁盘剩余空间；
  - 达到预警阈值（建议审计表 2 GiB 或所在磁盘使用率 80%）时显示真实警告，但不自动删除保留期内日志；
  - 不使用 `VACUUM FULL` 做日常清理，依赖 autovacuum；需要回收磁盘时由运维在维护窗口处理；
  - 日志写入本身有单条 16 KiB 上限和失败降采样，避免日志洪水把磁盘打满。
- 保留期修改需二次认证、填写理由，并审计旧值/新值；修改不会追溯删除或恢复已有日志。
- 如果保留期大于 366 天，日志导出必须分时间窗口执行，不能一次导出超过 3.6 节上限。

## 4. 数据库备份与恢复设计

### 4.1 备份范围

第一版明确为“**数据库快照**”：

- 包含：全部 PostgreSQL 表结构、数据、`_prisma_migrations`、数据库中的 `BrandAsset` 字节；
- 不包含：`.env.docker`、`NEXTAUTH_SECRET`、证明文件（`evidence-data` 卷）、活动附件（`attachments-data` 卷）、服务器 Nginx 配置、证书、日志文件；
- 页面、文件名、清单和恢复确认页都必须显示“不含证明与附件文件”，避免管理员误以为整站可完整还原；
- 完整归档（数据库 + 两个文件卷 + 清单校验）作为第二阶段独立设计，不在第一版冒充完成。

### 4.2 技术路线

- 在应用运行镜像中安装 **PostgreSQL 18 客户端工具**（`pg_dump`、`pg_restore`、`psql`）。Debian 基础镜像默认没有 18 版客户端，实施时通过 PGDG 仓库安装 `postgresql-client-18`，只固定主版本 18，并在启动/预检时比较 `pg_dump --version` 与服务器 `server_version_num`；客户端低于服务器时拒绝备份/恢复。不要在运行镜像里使用与数据库不同主版本的客户端。
- 应用已有 `pg` 依赖，可用于维护连接（`CREATE DATABASE`、`ALTER DATABASE ... RENAME`、`pg_terminate_backend`、统计查询），只有 dump/restore 需要子进程调用 `pg_dump`/`pg_restore`。数据库名必须来自服务端生成的白名单/标识符转义，不能拼接用户输入；连接参数从 `DATABASE_URL` 解析，不写日志。
- 新增独立命名卷 `backup-data` 挂载到 `/data/backups`，目录权限 0700，文件 0600；存放 dump、清单、恢复报告和审计旁路，不与其他项目的卷混用。
- 备份格式：`pg_dump --format=custom --compress=6`，单文件 `.dump`。
- 每个备份配一个同名 `.json` 清单，包含：
  - 备份 ID、文件名、创建时间、创建人 ID/姓名、理由；
  - 应用版本、Git 修订、PostgreSQL 客户端/服务器版本；
  - 迁移目录列表（名称 + SHA-256 校验和 + 完成时间）；存在失败迁移则备份失败；
  - dump 字节数、SHA-256、快照标识；
  - 备份时数据库大小、全部用户表行数（与 dump 同一快照）、序列数量；
  - `includesFiles: false`、`evidenceRows`、`activityAttachmentRows`，用于恢复后缺失检查；
  - `rowCountsSource: "snapshot"`，明确计数可信来源。
- 文件命名：`campus-evaluation_20261024T153000Z_v0.3.0_<shortsha>.dump`；只允许服务端生成，上传文件也重命名，禁止用用户输入拼接路径。
- 文件系统即备份清单来源：恢复数据库后，备份目录仍可列出旧快照；不把“备份列表”只存在数据库里，避免恢复后列表丢失。
- 恢复报告和审计旁路放在 `/data/backups/restore-reports/<restoreId>/`，与备份分开保留；报告不写数据库连接串、密码或密钥。

### 4.3 创建备份流程

1. 管理员在 `/backups` 点击“创建备份”，填写理由（2–500 字符）。
2. 服务端检查：管理员权限、`mustChangePassword=false`、当前无恢复任务、备份 advisory lock 可用。
3. 磁盘预检：读取数据库大小与备份卷可用空间，要求可用空间 ≥ max(数据库大小 × 1.2, 512 MiB)；不足则拒绝并显示真实数字。
4. 启动后台任务，写入真实状态文件（queued/running/succeeded/failed、字节数、错误码），前端轮询展示真实进度；不使用假进度条。
5. **一致性快照**：
   - 在一条 `REPEATABLE READ` 事务中执行 `SELECT pg_export_snapshot()`，保持该事务打开；
   - 以 `pg_dump --snapshot=<exported> --format=custom --compress=6` 导出；
   - 在同一个导出事务内查询全部用户表行数、数据库大小与迁移记录，写入清单；
   - dump 完成后结束导出事务。这样清单行数与 dump 内容来自同一数据库快照，不用事后估算。
6. 执行 `pg_restore --list` 校验文件可读，计算 SHA-256，生成清单。
7. 若任一步失败：删除不完整文件，状态置失败，记录审计；不保留半成品供下载。
8. 成功后按保留策略清理旧备份；审计 `BACKUP_CREATED`。
9. 下载：仅管理员，`POST` 表单二次认证后流式响应，禁止缓存；每次下载审计 `BACKUP_DOWNLOADED`。备份文件包含个人数据，页面提示应存放在受控位置并考虑离线加密。

并发控制：同一时间只允许一个备份任务；使用数据库 advisory lock + 任务状态文件双重保护。若应用重启导致任务中断，启动时把超过 10 分钟仍为 running 的任务标记为失败并清理临时文件；已完成的 dump 不删除。

### 4.4 保留与磁盘管理

- 默认保留最近 **14 份成功备份**，可配置 1–100 份；恢复前安全快照单独标记，至少保留 7 天。
- 自动保留只统计应用创建的备份；**管理员上传的备份默认标记为 pinned，不自动删除**，只能手动删除并需二次认证。页面显示 pinned 占用，避免误以为系统会自动清理。
- 每次新建成功后自动清理超额的最旧非 pinned 备份；正在下载或正在恢复的快照不可删除。
- 手动删除：需重新输入密码、填写理由；审计 `BACKUP_DELETED`，记录文件名与哈希前缀，不记录文件内容。
- 备份卷容量限制：建议服务器预留至少 5 GiB；页面上限可通过环境变量设置（如 `BACKUP_MAX_BYTES`），超过上限时拒绝创建并给出当前占用。
- 磁盘占用真实展示：备份数量、pinned 数量、总字节、最后成功时间、剩余空间；不使用估算代替实际 `statfs`。
- 重要限制：**同机备份不能防止服务器或磁盘整体损坏**。页面明确提示管理员定期下载并异地保存；自动异地复制（S3/对象存储）不在本版范围。

### 4.5 上传备份

- 仅接受 `.dump`（PostgreSQL custom format）及可选同名 `.json` 清单；单文件最大 2 GiB（可配置）。上传的备份默认 pinned，不参与自动清理。
- **上传会话，避免 2 GiB 文件被缓冲进内存**：
  1. `POST` 创建上传会话，提交文件名、大小、SHA-256、当前密码与理由；服务端校验管理员、`mustChangePassword=false`、空间和扩展名，返回一次性 `uploadId + token`（30 分钟有效，绑定当前管理员会话）。
  2. `PUT` 用 `application/octet-stream` 原始流写入临时文件，token 放请求头；边写边算 SHA-256，超过大小上限立即中止并删除临时文件。密码不参与这一步。
  3. `POST` 完成上传：核对 SHA-256/大小、`pg_restore --list` 与 `_prisma_migrations` 存在性，移入备份目录、生成/补全清单并标记 pinned；失败只显示稳定错误码，不回显路径、SQL 或服务器内部信息。
- 未完成的上传会话 30 分钟后清理临时文件；上传行为审计 `BACKUP_UPLOADED`。上传成功不等于可恢复，页面在预检通过前不显示“可恢复”标签。
- 基础校验：文件头必须是 `PGDMP`；`pg_restore --list` 必须可解析且包含 `_prisma_migrations`；若同时上传清单，SHA-256、文件大小、迁移名称与校验和必须一致；更高主版本或未知归档格式直接拒绝。
- **预检即试恢复**：上传后的“可恢复性”不靠文件头猜测。管理员发起恢复预检时，服务端创建候选库并实际 `pg_restore`，读取 `_prisma_migrations` 的 `migration_name/checksum/finished_at/rolled_back_at`、表行数和设置差异。没有清单的上传备份也能得到真实报告，但迁移历史必须完整；若没有 `_prisma_migrations`、存在失败迁移或校验和不匹配，拒绝恢复。
- 试恢复失败只显示稳定错误码，不回显路径、SQL 或服务器内部信息；临时库和文件清理记录在报告中。

### 4.6 恢复：整库替换与冲突处理

#### 4.6.1 为什么不做“任意 dump 行级合并”

数据库 dump 是物理结构+数据+迁移历史的整体，不是为合并设计的业务文件。直接对两份 dump 做行级合并会遇到：

- 主键/外键冲突（同一 ID 指向不同业务对象）；
- 唯一键冲突（登录名、学号、学期代码、活动编号）；
- 迁移版本不同导致列不存在/类型不同；
- 触发器、序列、审计历史、发布快照的一致性；
- 合并顺序与循环依赖；
- 附件存储键与数据库记录不匹配。

因此本设计明确：

- **整库恢复 = 替换**，冲突处理策略只有一个：用备份覆盖当前数据库；恢复前必须让管理员看到覆盖影响并确认。
- **业务数据合并**不使用数据库 dump，继续使用现有账号导入、成绩导入、活动参与导入等有明确字段映射、校验、批次撤销的流程。
- 若未来确实需要跨系统迁移，单独设计“业务归档合并”格式（带自然键、字段映射、逐实体冲突策略、ID 重映射、干跑报告），不与整库恢复混在一起。

#### 4.6.2 恢复前影响报告（真实试恢复）

恢复不是“读一遍清单就开干”。预检会在 PostgreSQL 上创建一个**候选恢复库**，实际执行 `pg_restore`、迁移和校验，再把真实结果展示给管理员。预检不修改当前库，也不进入维护模式；候选库保留 30 分钟供确认复用，过期自动删除。

| 检查项 | 内容 |
| --- | --- |
| 备份基本信息 | 创建时间、大小、SHA-256 校验结果、应用版本、创建人、是否 pinned |
| 试恢复结果 | 候选库创建/还原/迁移是否成功；失败阶段与稳定错误码 |
| 迁移兼容性 | 备份 `_prisma_migrations` 的名称、校验和、完成状态；是否为当前迁移前缀；是否有未知、更高版本、失败或校验和不匹配的迁移 |
| 数据量对比 | 当前库与备份的 User/StudentProfile/Term/Activity/Publication/Claim/Evidence/ActivityAttachment 等行数；迁移前后行数 |
| 时间差影响 | 备份时间之后的审计事件数、按分类统计；明确这些改动会被备份覆盖，但审计事件会通过旁路保留 |
| 设置差异 | 站点名称、登录失败策略、附件限制等非密钥设置当前值 → 恢复后值；不展示密码/密钥 |
| 管理员可用性 | 备份内启用状态的 ADMIN 登录名列表、是否具备密码哈希、是否仍需强制改密；当前操作者是否在备份中；密码是否正确无法在不知道明文密码的情况下验证 |
| 会话与临时状态 | 备份内有效 `AuthSession` 数（恢复后一律作废）；`LoginFailureState`、`LoginCaptcha`、`LoginAttempt` 行数（恢复后清空） |
| 审计连续性 | 当前全部审计事件导出的旁路 JSONL 预计条数/字节、写入空间；超过上限则拒绝恢复 |
| 附件风险 | 当前与备份的证明/附件行数；文件卷实际文件数、缺失数、孤儿数（只读扫描） |
| 磁盘空间 | 当前库大小、候选库预计大小、安全快照预计大小、旧库保留占用、备份卷和数据库卷剩余空间 |
| 结构差异 | 当前存在但备份不存在的表；其中不在当前迁移历史中的表将在切换后消失，必须明确列出 |
| 恢复方式 | 候选库验证后原子切换数据库名；旧库保留 7 天；不是原地 `--clean`，不能行级合并 |

拒绝恢复的硬条件：

- 备份没有完整 `_prisma_migrations`，或存在失败/回滚中的迁移；
- 备份包含当前应用没有的迁移名（更新版本或来路不明）；
- 共同迁移的 SHA-256 校验和不一致（说明备份 schema 被手工改过）；
- 备份中没有启用状态且具备密码哈希的 ADMIN；
- 试恢复失败、候选库迁移失败、审计旁路无法写入、空间不足或当前数据库角色没有 `CREATEDB`。

预检完成后、确认切换前，如果当前库又发生业务写入，预检指纹会失配；此时**不进入切换**，必须重新预检，不能用过期报告覆盖新数据。

若备份较旧但迁移名称和校验和是当前迁移的前缀：允许恢复，并在候选库执行 `prisma migrate deploy` 前向迁移，记录实际应用的迁移列表。若迁移失败，当前库完全不受影响，直接终止。

预检指纹：记录当前库的 `pg_database_size`、关键表行数、最新审计事件 `id/createdAt`、设置 revision。管理员确认时再次核对；任何一项变化都要求重新预检，避免拿旧报告做破坏性操作。应用启动时扫描并删除超过 `restoreCandidateTtlMinutes` 的候选库；删除失败写入服务器日志并在备份页提示，不影响当前库。

#### 4.6.3 恢复执行流程

**阶段 A：预检（不改当前库）**

1. 管理员选择备份，填写预检理由；服务端完成权限、advisory lock 和磁盘预检（预检不要求密码，确认切换时必须二次认证）。
2. 校验 dump 头、TOC、SHA-256；以 `template0`、与当前库一致的编码/locale 创建 `campus_restore_<timestamp>` 候选库。
3. `pg_restore --single-transaction --exit-on-error --no-owner --no-privileges --dbname=<候选库> <dump>`。
4. 读取迁移、全部表行数、设置、管理员、会话与文件统计，生成影响报告。
5. 若是旧版本前缀，使用指向候选库的独立 `DATABASE_URL` 执行 `prisma migrate deploy`（绝不复用当前库连接），记录实际应用的迁移列表；迁移失败只丢弃候选库，当前库不受影响。
6. 计算预检指纹与报告 SHA-256，写入 `/data/backups/restore-reports/<restoreId>/preflight.json`；审计 `DATABASE_RESTORE_PREFLIGHTED`。候选库保留 30 分钟。

**阶段 B：确认与切换（进入维护）**

1. **二次认证与确认**：重新输入当前密码、填写理由、输入确认短语（如“替换数据库”）；勾选已知悉“所有用户会被登出、需使用备份内的管理员账号登录”。
2. **复核**：dump 哈希未变、候选库未过期、预检指纹仍匹配；否则退回预检。
3. **维护模式**：进程内维护标记生效；所有登录、业务页面、写接口返回 503/维护页；`/api/health/ready` 直接返回 503 且不查询业务库；等待在途请求结束；停止定时清理和其他后台任务。
4. **恢复锁**：在维护库（`postgres`）持有一个 advisory lock。当前库稍后会被重命名，锁不能只放在当前库。
5. **安全快照**：用 4.3 的一致性快照方法对当前库生成安全 dump 并校验；失败则终止，当前库不动。
6. **审计旁路**：先写 `DATABASE_RESTORE_STARTED`，再把当前**全部** `AuditEvent` 流式导出为 JSONL（含 `details`、reason、请求元数据），写 `manifest.json`（条数、首尾时间、SHA-256），确保开始动作本身也在旁路中。默认上限 1 GiB；超过时拒绝恢复并提示先导出/清理日志。
7. **断开连接**：`prisma.$disconnect()`，并通过控制连接 `pg_terminate_backend` 清掉当前库和候选库的其余连接。
8. **候选库收尾**：
   - 执行安全重置：`UPDATE "User" SET "authVersion" = "authVersion" + 1;`、清空 `AuthSession`、`LoginFailureState`、`LoginCaptcha`、`LoginAttempt`；
   - 分批回导审计旁路，按主键 `ON CONFLICT (id) DO NOTHING`，记录 imported/skipped；
   - 再次核对候选库行数、迁移、管理员可用性、外键/唯一约束；失败则丢弃候选库，当前库不动。
9. **原子切换**：重命名前再次查询 `pg_stat_activity`，确认当前库和候选库都没有其他连接；新库名必须不超过 PostgreSQL 的 63 字节标识符上限，超长时改用“短前缀 + 哈希”，不能依赖数据库自动截断。然后在维护库连接上执行一个事务，把当前库重命名为 `<current>__prev_<timestamp>`，把候选库重命名为 `<current>`：
   ```sql
   BEGIN;
   ALTER DATABASE "<current>" RENAME TO "<current>__prev_<timestamp>";
   ALTER DATABASE "<candidate>" RENAME TO "<current>";
   COMMIT;
   ```
   两次重命名必须在同一事务内保证切换原子性。本报告已在隔离 PostgreSQL 18.4 实例验证：同一事务内两次 `ALTER DATABASE ... RENAME` 成功，`ROLLBACK` 后库名完全恢复；实施时在 CI 或隔离实例保留该验证。若目标环境不允许，禁止上线恢复功能，改用有状态的两阶段切换并保留可恢复的旧库，不能退化成原地覆盖。
10. **重连与校验**：Prisma 重新连接同一个 `DATABASE_URL`（现指向新库），清理进程内设置/主题缓存；核对迁移、关键表行数、审计旁路回导数、管理员账号、外键、设置与文件缺失/孤儿统计。无需依赖 Docker 重启。
11. **完成**：在恢复后的库写入 `DATABASE_RESTORE_SECURITY_RESET`、`DATABASE_RESTORE_AUDIT_IMPORTED` 和 `DATABASE_RESTORE_COMPLETED`（操作者姓名/角色快照、备份哈希前缀、迁移列表、旁路回导数、文件缺失数、耗时），更新 `SystemPolicy.lastRestoreAt`，追加恢复报告；清除维护模式，健康检查恢复 200。所有旧会话已失效，页面跳转登录。
12. **旧库与快照保留**：旧库保留 7 天（可配置），页面显示库名、大小、自动删除时间；提前删除需二次认证 + 理由并审计。安全 dump 同样至少保留 7 天。恢复报告与审计旁路按 `restoreReportRetentionDays` 自动清理，不提供单条编辑；删除行为写入审计。

**失败与崩溃处理**

- 切换前失败：丢弃候选库，当前库保持不变；清除维护模式；写 `DATABASE_RESTORE_FAILED` 和报告。
- 切换事务失败：数据库名保持切换前状态；当前库不变，终止并报告。
- 切换后校验失败：在新的回滚事务中把新库改回候选名、旧库改回当前名，重新连接旧库，保持维护模式直到人工确认；写失败报告。若回滚也失败，保持维护模式并输出明确的人工恢复步骤，绝不显示成功。
- `SystemPolicy.lastRestoreAt` 或完成审计写入失败：不解除维护模式；恢复数据已切换，但必须由管理员确认策略状态，避免自动清理立即按旧保留期删日志。
- 进程崩溃：状态文件记录 `preflight/staging/confirmed/snapshot/exported/swapping/swapped/completed/failed`。启动时先读取状态：若尚未切换，保留当前库并中止；若已切换，按状态和数据库名核对后完成校验或回滚。入口脚本检测到未完成恢复时**跳过自动迁移**并以维护模式启动，避免在恢复中再次改库。
- 审计闭环：成功时恢复前审计在旁路和新库中都可查；失败时旧库仍保留全部审计；恢复报告独立于数据库保存，数据库再次损坏时仍能说明发生过什么。

#### 4.6.4 冲突矩阵（供管理员理解）

| 场景 | 处理方式 | 说明 |
| --- | --- | --- |
| 当前库有数据，恢复备份 | 候选库验证后整库切换 | 备份是目标状态；报告列出将丢失的时间段改动，审计事件通过旁路保留 |
| 当前库为空，恢复备份 | 同样走候选库与切换 | 仍保留旧空库和安全快照，便于回退 |
| 备份来自更新版本 | 拒绝 | 存在当前应用不认识的迁移 |
| 备份来自旧版本 | 允许且前向迁移 | 仅当迁移名称/校验和是当前迁移的前缀，且候选库迁移成功 |
| 备份 schema 被手工改过 | 拒绝 | `_prisma_migrations` 校验和不匹配 |
| 备份没有迁移历史 | 拒绝 | 无法证明结构与当前应用兼容 |
| 当前库有备份中不存在的新表 | 切换后消失 | 新表若来自备份之后的迁移，会在候选库前向迁移中重建，但备份之后写入的数据不会回来；手工表会消失。报告逐项列出表名与预计丢失行数 |
| 恢复后当前管理员不在备份中 | 允许但强提示 | 必须使用备份内管理员登录；无可用管理员则拒绝 |
| 只想补几个账号/成绩 | 不使用整库恢复 | 使用现有导入功能，支持校验与批次撤销 |
| 两个学校数据合并 | 本版不支持 | 需要独立业务归档合并设计，避免 ID/唯一键破坏 |

### 4.7 附件一致性

- 第一版恢复完成后执行“附件缺失检查”：分页比对 `Evidence.storageKey` / `ActivityAttachment.storageKey` 与文件卷中的实际文件，报告缺失数量和孤儿文件数量；不自动删除数据库记录，也不自动删除孤儿文件。
- 恢复前影响报告和恢复结果都显示：数据库备份不含证明/活动附件；恢复后数据库中的文件引用与卷内容可能不一致，缺失文件需要从文件备份或原上传人处补回。
- 旧数据库同样不含文件；保留旧库只能回退数据库，不能回退文件。
- 第二阶段完整归档建议：
  - 备份包 = dump + 两个文件卷 tar + 清单 + 哈希；
  - 恢复时先恢复数据库，再把文件解压到临时目录、校验哈希、原子替换目录；
  - 文件恢复不是数据库事务的一部分，必须设计失败回滚和空间预检；
  - 不在第一版草率实现，避免“数据库恢复成功但文件半套”的更坏状态。

### 4.8 服务器与运行环境变更

| 项 | 变更 | 影响 |
| --- | --- | --- |
| Dockerfile | 通过 PGDG 安装 PostgreSQL 18 客户端（`pg_dump`、`pg_restore`、`psql`） | 镜像增大约几十 MB；固定主版本，启动/预检比较客户端与服务器版本 |
| compose.yaml | 新增 `backup-data:/data/backups`，以及 `BACKUP_DIR`、`BACKUP_MAX_BYTES`、`BACKUP_RETENTION_COUNT`、`RESTORE_REPORT_RETENTION_DAYS`、`TRUST_PROXY` | 环境变量只提供初始默认值与硬上限，运行期以 `SystemPolicy` 为准；两者冲突时取更保守值。仅应用容器变更；不动数据库容器、现有卷、端口和 Nginx |
| 数据库权限 | 应用使用的数据库角色需要 `CREATEDB`（当前 Compose 的 `POSTGRES_USER` 是超级用户，满足）；恢复时需要终止本库连接和重命名数据库 | 预检检查权限；外部托管数据库若不满足，只提供备份，不提供 Web 恢复 |
| 备份目录 | 归 `nextjs` 用户，0700/0600；Dockerfile 预创建 `/data/backups` 并 chown，命名卷首次挂载继承权限 | 容器仍 `cap_drop: ALL`，不需要额外特权；不依赖运行时 root chown |
| 启动流程 | 入口脚本在迁移前检测未完成恢复状态；存在时跳过迁移，以维护模式启动 | 避免恢复中途重启后自动迁移把库改乱 |
| 健康检查 | 维护/切换期间 `/api/health/ready` 直接返回 503，不查询业务库 | 不修改 Nginx 探活配置；Docker 不会误判后重启循环 |
| 旧库清理 | 每日任务删除超过保留期的 `__prev_` 旧库；提前删除需二次认证和理由 | 旧库占用数据库卷；页面展示名称、大小和计划删除时间 |
| 回滚 | 应用镜像可按 tag 回退；数据库回退使用旧库或安全 dump | 部署手册补充恢复演练、失败诊断和人工回滚步骤 |

当前 Compose 的 `db-data` 与 `backup-data` 在同一宿主机磁盘，应用通过备份卷 `statfs` 和数据库逻辑大小做空间预检。若未来把两个卷拆到不同磁盘，应用无法从 SQL 读取数据库宿主机剩余空间，页面必须显示该限制并要求运维确认，不能假装空间检查仍然完整。

当前 Compose 为单应用副本，进程内维护标记和状态文件足以覆盖现有部署；若未来横向扩展多副本，维护模式、任务锁和恢复状态必须改为数据库/共享存储，并重新评审后才能启用 Web 恢复。

## 5. 权限、认证与审计闭环

| 操作 | 权限 | 二次认证 | 理由 | 审计动作 |
| --- | --- | --- | --- | --- |
| 查看日志列表/详情 | ADMIN | 否 | 否 | 不记录普通查看 |
| 导出日志 | ADMIN | 是 | 是 | `AUDIT_LOG_EXPORT_STARTED/EXPORTED/EXPORT_FAILED` |
| 修改日志保留期 | ADMIN | 是 | 是 | `AUDIT_RETENTION_CHANGED` |
| 手动清理日志 | ADMIN | 是 | 是 + 确认短语 | `AUDIT_LOG_PURGED` |
| 备份预检（试恢复） | ADMIN | 否 | 是 | `DATABASE_RESTORE_PREFLIGHTED` |
| 创建/上传备份 | ADMIN | 否（创建）/是（上传） | 是 | `BACKUP_CREATED` / `BACKUP_UPLOADED` |
| 下载/删除备份 | ADMIN | 是 | 是 | `BACKUP_DOWNLOADED` / `BACKUP_DELETED` |
| 恢复数据库 | ADMIN | 是 | 是 + 确认短语 | `DATABASE_RESTORE_STARTED/COMPLETED/FAILED` |
| 查看/筛选附件与证明 | ADMIN | 否 | 否 | 不记录普通查看 |
| 单个下载证明/附件 | ADMIN/学院/辅导员 | 否 | 否 | `EVIDENCE_DOWNLOADED` / `ACTIVITY_ATTACHMENT_DOWNLOADED` |
| 批量导出证明/附件 | ADMIN | 是 | 是 | `STUDENT_EVIDENCE_EXPORTED` / `ACTIVITY_ATTACHMENTS_EXPORTED` |

补充：

- 所有接口要求 `mustChangePassword=false`，避免初始密码账号执行高风险操作。
- 现有 API 的来源校验、CSRF 防护、会话校验继续保留；新增接口不得绕过。导出/下载使用同源 POST 表单，密码只在请求体。
- 恢复成功后**所有旧会话必定失效**：`AuthSession` 被清空且 `User.authVersion` 全部递增；页面明确提示使用备份中的管理员凭据重新登录，不尝试保留旧令牌。
- 恢复前的审计事件导出到旁路 JSONL，并在切换前回导到候选库；成功与失败都保留恢复报告，避免“恢复把审计抹掉”。
- 审计日志只允许追加，不提供单条编辑/删除接口；清理只能按保留期批量执行。
- 备份、恢复、清理、批量导出是重型操作：恢复与所有任务互斥；备份、上传校验、清理三者互斥；恢复期间禁止导出。使用独立 advisory lock，并在页面显示当前任务占用者。
- 恢复、备份、日志相关动作本身必须进入审计；恢复完成审计写在恢复后的数据库中，同时写一份恢复报告文件，防止数据库再次损坏时丢失证据。

- 任务接口只返回稳定状态码、阶段、字节/条数进度和脱敏错误码；不返回 SQL、连接串、路径或原始异常。

### 6.4 附件管理与证明/附件导出（补充设计）

结论：**可以做，且不改变数据库备份边界**。附件管理是独立的只读管理页；数据库备份仍不含文件，完整归档仍属第二阶段。

#### 6.4.1 活动附件列表

- 数据源：`ActivityAttachment` 中已绑定活动的附件（`activityId` 非空）；活动草稿中尚未绑定的临时上传不进入“活动附件”列表，仍在活动编辑流程内处理。列表只显示至少有一个附件的活动；无附件活动仍在活动管理中查看，不用空行凑数。
- 聚合规则：**按活动分组，一个活动只显示一行**，行内展示附件总数、图片/文件数量、总大小、最近上传时间和上传人；展开行或详情抽屉再列出每个附件。这样既有活动级总览，也不会把多个附件拆成多行。`uploaderId` 没有外键关系，上传人姓名需手工关联 `User`，账号已删除时显示 ID 或“已删除账号”，不阻塞列表。
- 筛选：
  - 学期、活动状态、关键词（活动名/组织者/附件名）；
  - 范围：全校、指定学院、指定专业、指定班级；
  - 归属学院（含“未指定”）、受众类型（ALL/COLLEGE/CLASS）、上传时间范围。
- 范围口径（按真实受众规则，避免把“归属学院”误当“可见范围”）：
  - 活动归属学院是 `Activity.collegeId`，只表示活动由哪个学院管理，可以为空；它是独立筛选和展示列，不决定学生能否看到活动。
  - **全校**：不限制范围，所有带附件的活动。
  - **学院 X**：覆盖 `ALL` 活动 + `audienceColleges` 包含 X 的 `COLLEGE` 活动 + `audienceClasses` 中学院字段为 X 的 `CLASS` 活动。`ALL` 活动会在每个学院的导出中出现，这是受众语义，不是重复数据。
  - **专业（X 学院 + Y 专业）**：覆盖 `ALL` + `audienceColleges` 包含 X 的 `COLLEGE` 活动 + `audienceClasses` 中 `[X, Y, 班级]` 的 `CLASS` 活动。
  - **班级（X 学院 + Y 专业 + Z 班）**：覆盖 `ALL` + `audienceColleges` 包含 X 的 `COLLEGE` 活动 + `audienceClasses` 精确包含 `JSON.stringify([X, Y, Z])` 的 `CLASS` 活动。`classKey` 就是该三元组 JSON，与 `src/server/activity-policy.ts` 一致。
  - 不按报名名单、参与记录反向扩大范围；受众是活动发布时的可见范围，参与名单是另一回事。
  - 历史 `audienceColleges` 保存的是发布时学院名称，`audienceClasses` 使用发布时的学院/专业/班级名称生成；如果后来学院或班级改名，旧值无法匹配当前目录。页面显示“未匹配受众学院/班级”数量，不静默丢弃；需要按历史名称找人时，用活动详情查看原始受众。
  - 归属学院为空的活动仍出现在“全校”和受众覆盖结果中；归属学院筛选可选“未指定”。
- 范围预览：选择范围后先显示活动数、附件数、总字节、匹配的受众键数量与“含全校活动”提示，再允许导出；不先下载再发现范围不对。
- 行操作：查看附件明细、逐个下载、按当前活动导出 ZIP；批量导出按当前筛选执行。
- 只读边界：管理页不直接删除附件；删除仍回到活动详情的既有权限与审计流程，避免出现第二套删除逻辑。

#### 6.4.2 学生证明列表与导出

- 数据源：`Evidence`；`ownerId` 在 schema 中没有外键关系，查询时按 `ownerId` 手工关联 `User` 与 `StudentProfile`，关联不到或所有者不是 `STUDENT` 时按“档案缺失/非学生”处理，不猜测学院。
- 筛选：全校、学院、专业、班级、上传时间、来源类型（成果认定/个人申报/异议/活动）、是否已被引用；来源类型由 `EvidenceReference`、`ClaimEvidence`、`AppealEvidence`、`ActivityEvidence` 关系判定，一条证明可同时被多处引用；可按学生学号/姓名搜索。
- 展示：一条证明一行，列出文件名、学生、学号、学院/专业/班级、大小、上传时间、引用情况；支持单个下载和批量导出。
- 范围口径：按证明所有者的 `StudentProfile.college`、`major`、`className`/`classId` 筛选；全校为不限制。不能通过查询参数越权查看范围外证明。
- 所有者或学生档案缺失、所有者不是学生的历史证明显示“档案缺失/非学生”，只在“全校”结果中出现，不猜测学院/专业/班级；导出清单标明该状态，不静默分配。

#### 6.4.3 导出格式与限制

- 活动附件 ZIP：

  ```text
  activity-attachments_20261024_1530.zip
  manifest.csv
  errors.csv            # 仅在存在失败文件时生成
  activities/<activityId>_<安全活动名>/
    0001_<安全文件名>
    0002_<安全文件名>
  ```

- 学生证明 ZIP：

  ```text
  student-evidence_20261024_1530.zip
  manifest.csv
  errors.csv            # 仅在存在失败文件时生成
  evidence/<evidenceId>_<安全文件名>
  ```

- 每个文件写入 ZIP 前校验 `storageKey` 格式、大小与 SHA-256；单个文件失败不中断整批：
  - 跳过损坏/缺失文件，写入 `errors.csv`（附件 ID、活动 ID、错误码，不含服务器路径）；
  - ZIP 仍包含 `manifest.csv`，列出活动、附件、学生（证明）、大小、哈希、状态；
  - 导出结果标记为 `PARTIAL`，页面明确显示“成功 N、失败 M”，不能把部分失败显示成全部成功。
- 预检后再流式打包：先统计匹配活动数、文件数、总字节，超过上限或磁盘读取异常时直接拒绝，不生成半成品。
- 流式 ZIP（新增一个维护中的轻量服务端压缩依赖，实施前核验 MIT 等许可证与多架构可用性）；不把全部文件加载进内存，使用 ZIP64 兼容实现或把单次上限控制在 2 GiB 内。
- 上限：单次 2 GiB 或 2,000 个文件，超过则拒绝并要求缩小范围；响应头 `no-store`，文件名使用 ASCII 安全名。`manifest.csv` 同样做 CSV 公式注入转义。
- 文件名清理路径分隔符、控制字符、`..`、盘符和保留字；ZIP 内使用附件/证明 ID 前缀防止重名覆盖。
- 导出写入审计：`ACTIVITY_ATTACHMENTS_EXPORTED` / `STUDENT_EVIDENCE_EXPORTED`，记录筛选条件（学院/专业/班级/受众/归属）、活动数、文件数、总字节、失败数、耗时；不记录文件内容或学生材料文本。
- 权限与认证：仅 `ADMIN`；批量导出需二次输入当前密码并填写理由，使用同源 `POST` 表单，密码只在请求体。单个文件下载不要求二次认证，但管理员/学院/辅导员下载证明或附件会写审计；学生下载自己的材料不逐次记录。
- 导出包含学生个人材料，页面提示妥善保管，不生成公开链接、不写入浏览器长期缓存。

#### 6.4.4 与备份的关系

- 附件管理解决“查看和按范围取数”，不是数据库一致性备份；
- 数据库恢复后仍可能缺文件，恢复页继续显示附件缺失检查；
- 完整归档（数据库 dump + 两个文件卷 + 清单 + 哈希）仍作为第二阶段单独设计，不能用附件导出冒充整站备份。

## 7. 容量、性能与失败处理

### 7.1 容量估算

| 项 | 估算 | 措施 |
| --- | --- | --- |
| 审计事件 | 每年 10–50 万条，单条约 0.5–2 KiB | 180 天保留、索引、批量清理 |
| 审计表大小 | 约 100–500 MiB/年 | 页面展示实际大小；2 GiB 预警 |
| 审计旁路 | 恢复前全量导出，约等于审计表大小，另加 JSONL 开销 | 默认上限 1 GiB；恢复预检检查空间；随恢复报告保留 |
| 数据库快照 | 压缩后约为数据库大小的 30–60% | 保留 14 份；磁盘预检；超过上限拒绝 |
| 恢复候选库 | 解压后约等于当前数据库大小（含索引） | 预检/切换期间临时占用；成功后删除，失败后清理 |
| 恢复旧库 | 约等于当前数据库大小，保留 7 天 | 页面展示预计释放时间；到期自动删除 |
| 恢复报告 | 通常几 MiB，旁路另计 | 随审计保留策略，默认 180 天；限制报告数量 |
| 备份卷 | 建议 ≥5 GiB，独立卷 | 真实占用展示、手动删除、自动保留策略 |

### 7.2 失败与边界

- **审计写入失败**：高风险写操作、备份/恢复、清理、批量导出整体失败并返回错误；登录失败/退出为 best-effort，安全控制优先，同时写结构化服务器错误日志（不含敏感值）。
- **日志洪水**：登录失败与权限拒绝按 IP + 动作降采样；单条 16 KiB 截断；普通浏览不记录。
- **备份时磁盘满**：pg_dump 失败 → 删除临时文件 → 明确提示可用空间；不生成半成品。
- **恢复预检失败**：候选库还原/迁移失败 → 丢弃候选库，当前库不受影响，退出预检，不进入维护模式。
- **恢复时磁盘/权限不足**：预检阶段检查 `CREATEDB`、数据库卷和备份卷空间；不足直接拒绝，不进入维护模式。
- **切换重命名失败**：重命名事务回滚，当前库名与数据保持原状；保持维护模式，显示稳定错误码和人工检查建议。
- **恢复中进程崩溃**：状态文件记录阶段；启动时跳过自动迁移并以维护模式启动。未切换则保留当前库；已切换则核对数据库名后完成校验或回滚。维护模式不会自动解除。
- **审计旁路写失败或超限**：拒绝恢复，当前库不动；提示先导出/清理日志或增加备份卷空间。不能先切换再补审计。
- **恢复后附件缺失/孤儿**：显示缺失与孤儿数量，不自动删除数据库记录或文件；由管理员从文件备份恢复或重新上传。
- **恢复后管理员登不进**：预检已列出备份内管理员并要求确认；若无可用管理员直接拒绝。仍失败时由运维使用 bootstrap 流程重置，页面不假装成功。
- **并发恢复/备份/清理**：独立 advisory lock + 状态文件；第二个请求直接拒绝并显示当前任务。
- **跨版本不兼容/迁移校验和不匹配**：预检拒绝；不尝试“尽力恢复”导致 schema 损坏。
- **预检后数据变化**：确认时指纹不匹配 → 要求重新预检，不能用过期报告覆盖新数据。
- **时区**：页面按服务器时区（默认 Asia/Shanghai）展示，数据库存 UTC；导出 CSV 使用 ISO 8601 并附时区说明。

- 测试期间不得把真实学生材料、备份 dump、数据库连接串或密码复制进仓库、日志或汇报。

## 9. 风险与明确不做

### 9.1 主要风险

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| 恢复会覆盖备份时间之后的全部业务改动 | 业务数据丢失（审计可通过旁路保留） | 真实试恢复报告、二次认证、确认短语、安全快照、旧库保留 |
| 恢复带回旧会话 | 已撤销令牌重新可用 | 清空 `AuthSession` + 递增所有 `User.authVersion`，强制重新登录 |
| 恢复后管理员无法登录 | 系统恢复成功但无人可用 | 预检检查备份内 ADMIN、展示登录名、强制知悉；无管理员直接拒绝 |
| 恢复把设置/保留策略回退 | 登录策略、附件限制、日志保留期变回旧值 | 预检设置差异；恢复后 24 小时暂停自动清理；管理员复核 |
| 恢复前审计被覆盖 | 关键追责证据丢失 | 全量审计旁路 JSONL、哈希、回切库回导、恢复报告 |
| 同机备份无法防止整机/磁盘损坏 | 灾难恢复失败 | 页面提示下载异地保存；后续可评估对象存储 |
| 候选库 + 旧库 + 快照占用空间 | 磁盘不足或挤占数据库卷 | 预检精确计算并要求空间；候选库失败即清理；旧库 7 天自动删除 |
| 数据库角色无 `CREATEDB`/重命名权限 | Web 恢复不可用 | 预检检查；不满足时只提供备份，明确提示由运维处理 |
| 数据库切换窗口 | 短时 503、所有用户重登 | 维护模式、真实进度页、状态机与原子重命名；选择低峰期 |
| 数据库恢复后附件文件不匹配 | 证明/附件无法下载 | 明确范围、缺失/孤儿检查、第二阶段完整归档 |
| 日志表增长 | 磁盘与查询变慢 | 索引、180 天默认保留、批量清理、容量展示、失败降采样 |
| 恢复期间请求进入 | 数据不一致 | 维护模式、健康检查断库、advisory lock、终止其余连接 |
| pg_dump/restore 版本不匹配 | 备份/恢复失败 | PGDG 安装 PostgreSQL 18 客户端，预检比较版本 |
| 恢复后应用重连失败 | 服务中断 | 原子切换 + 回滚事务 + 恢复报告；不在未验证前解除维护 |
| 审计旁路/恢复报告含个人信息 | 二次泄漏 | 仅 ADMIN、目录 0700/文件 0600、不进入公开目录、不发送第三方 |
| 上传 dump 含恶意 DDL 或异常膨胀 | 候选库异常或抢占磁盘 | 仅 ADMIN 可上传；只在隔离候选库还原，绝不在当前库直接执行；预检空间、TTL 清理、失败即丢弃；不开放匿名或非管理员上传 |

### 9.2 明确不做

- 不提供任意 SQL 执行、脚本上传或 Docker socket 操作。
- 不把两份数据库 dump 做自动行级合并。
- 不用 `pg_restore --clean` 原地覆盖当前库；必须走候选库 + 校验 + 原子切换。
- 不在第一版备份证明/附件文件；不宣称“整站一键恢复”。

### 12.3 复检中发现并修复的问题

| 问题 | 影响 | 修复 |
| --- | --- | --- |
