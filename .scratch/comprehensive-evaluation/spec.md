# 高校综合测评管理系统：生产版本开发规格

Status: ready-for-agent

日期：2026-10-19。业务范围采用已经确认的毕设精简方案，交付质量按生产版本执行，当前部署目标为本机／局域网演示。测试边界已由用户确认。本规格描述待实现与待验收的行为。

## Problem Statement

学校需要把活动参与、个人成果、学业体育成绩和纪律扣分汇总为学期综合测评结果。依赖人工收集材料、汇总名单和维护 Excel 时，容易出现同一事实重复加分、证明材料难以追溯、公式漏填、重复汇总和修改后结果不一致。学生也难以解释自己的原始分如何经过封顶、比例和扣分形成最终成绩。

本校参考表已经暴露行间公式不一致、缺少部分小计公式和表头上限未执行的问题。新系统需要表达学校规则并统一计算，不能逐格复制这些缺陷，也不能把本校模块名称、权重和分值写死在计算逻辑中。

用户希望用国外主流技术和可复用界面快速完成开发，同时交付具备服务端权限、数据一致性、持久化、备份恢复和自动化验证的生产版本。精简的是业务范围；本地演示使用同一套生产构建与真实数据库。

## Solution

提供面向一所学校的综合测评 Web 应用。每个学期所有学生使用同一套生效测评方案，同一活动对所有被认定参与的学生给予相同原始分。学院、专业和班级用于档案与排名筛选，不形成不同评分方案。

| 角色 | 主要能力 |
| --- | --- |
| 学生 | 浏览活动、提交个人申报、查看本人认定记录和证明、解释成绩、核对结果并提出异议 |
| 活动发布者 | 管理本人活动、提出统一分值、导入参与名单、提交共享证明并跟踪处理结果 |
| 管理员 | 管理账号和学期、配置及试算评分树、确认活动分值、审核认定、导入成绩、登记扣分、处理异议、发布锁定并导出 |

管理员可套用学校模板，也可在通用操作支持的范围内自行配置评分树。评分模块允许继续向下嵌套；直接累加、比例汇总、任意节点封顶、可选满分折算、节点扣分和可选下限分别配置。独立评分功能只接收经过校验的配置与原始输入，返回完整计算明细。

应用采用 TypeScript 与 Next.js 单项目方案，复用 shadcn/ui 组件和后台布局，以 PostgreSQL 保存业务数据，证明文件保存在受控的持久化目录中。Docker Compose 运行生产构建与数据库，并交付环境配置、迁移、初始化、备份和恢复流程。

完整业务链为：管理员建号并配置学期，发布者或学生提供参与事实和材料，管理员审核并导入必需成绩，系统统一计算，学生核对并提出异议，管理员处理后发布、锁定和导出；确需更正时填写理由，重新开放、计算并再次发布锁定。

## User Stories

### 账号与学生档案

1. **US-001** 作为部署维护者，我希望建立首个管理员账号，以便在没有预置公开密码的情况下初始化系统。
2. **US-002** 作为管理员，我希望统一创建学生、活动发布者和管理员账号，以便按职责分配系统访问权限。
3. **US-003** 作为管理员，我希望通过名单批量建立学生账号并保留学号前导零，以便减少建号工作且准确识别学生。
4. **US-004** 作为学生，我希望用学号和密码登录，以便无需自行注册或依赖外部邮箱服务使用系统。
5. **US-005** 作为新建账号的使用者，我希望首次登录必须修改初始密码，以便建立个人密码后再访问业务功能。
6. **US-006** 作为管理员，我希望为忘记密码的用户生成重置凭据，以便帮助其恢复使用并使旧会话失效。
7. **US-007** 作为管理员，我希望停用账号或调整角色后权限及时生效，以便控制继续访问和数据修改。
8. **US-008** 作为用户，我希望退出登录或密码变化后旧凭据无法继续执行受保护操作，以便保护账号和本人材料。
9. **US-009** 作为管理员，我希望维护学生所属学院、专业和班级，以便按学校组织范围管理名单与排名。

### 学期、方案与试算

10. **US-010** 作为管理员，我希望创建学期并为所有学生启用同一套方案，以便保证同学期计分口径一致。
11. **US-011** 作为管理员，我希望直接套用学校模板，以便核查现有分类和比例后快速开始配置。
12. **US-012** 作为管理员，我希望自由命名评分模块并继续添加下级模块，以便表达不同学校需要的实际层级。
13. **US-013** 作为管理员，我希望在树形目录中按需展开、查看父级路径、改名、排序和移动模块，以便维护深层结构。
14. **US-014** 作为管理员，我希望系统阻止循环、跨方案挂接和无输入来源的空节点生效，以便发布可计算的完整方案。
15. **US-015** 作为管理员，我希望每个最底层模块选择活动累加或成绩输入来源，以便避免同一模块混合重复计分。
16. **US-016** 作为管理员，我希望选择直接累加或比例汇总，并只在比例汇总时检查下级比例合计100%，以便正确表达汇总方式。
17. **US-017** 作为管理员，我希望在任意节点单独设置上限，以便先合计相关子项再执行封顶。
18. **US-018** 作为管理员，我希望按需启用满分折算和最低分，以便适配其他计分口径并保留未启用时的原始规则。
19. **US-019** 作为管理员，我希望把扣分项目绑定到明确的节点和系数，以便在正确位置扣减并解释扣分影响。
20. **US-020** 作为管理员，我希望规定成绩输入的有效范围和缺失政策，以便区分无活动记录与必需成绩尚未录入。
21. **US-021** 作为管理员，我希望输入测试分数后查看逐层试算明细，以便在启用方案前核对汇总、上限、折算和扣分。
22. **US-022** 作为管理员，我希望修改生效方案前看到受影响人数与示例差异，以便确认后为本学期全体学生统一重算。
23. **US-023** 作为管理员，我希望删除或拆分已有数据的模块前明确迁移记录，以便保留历史事实且避免无效引用。

### 活动与组织批量认定

24. **US-024** 作为学生，我希望浏览活动内容、时间和参与要求，以便了解校园活动而无需通过系统在线报名。
25. **US-025** 作为活动发布者，我希望创建和维护本人活动，以便发布信息并向管理员提交认定依据。
26. **US-026** 作为活动发布者，我希望为活动选择最底层模块并提出统一原始分，以便所有获认定参与者使用同一规则。
27. **US-027** 作为管理员，我希望确认活动所属模块和统一分值，以便活动分数由服务端认可的配置决定。
28. **US-028** 作为活动发布者，我希望导入 CSV 或 XLSX 参与名单，以便一次提交多人参加同一活动的事实。
29. **US-029** 作为名单导入者，我希望对应列、预览处理结果并看到逐行错误，以便修正未知学号、重复行或不合法字段后提交。
30. **US-030** 作为活动发布者，我希望为一份参与名单上传共享证明，以便每名参与者引用同一依据而无需重复上传。
31. **US-031** 作为管理员，我希望审核组织提交的名单与证明，以便仅将有效认定计入学生成绩。
32. **US-032** 作为活动发布者，我希望查看本人提交的处理状态和理由，以便补充或更正记录。
33. **US-033** 作为管理员，我希望重复导入同一学生的同一活动时复用参与记录，以便避免重复加分。
34. **US-034** 作为管理员，我希望活动统一分值的更正影响该活动全部有效参与者，以便不出现对同一活动逐人任意设分。

### 个人申报与审核

35. **US-035** 作为学生，我希望选择管理员创建的加分项目并提交本人材料，以便按照明确项目申请认定。
36. **US-036** 作为学生，我希望看到项目对应模块和统一原始分，以便了解申报价值且无需自行填写想获得的分数。
37. **US-037** 作为学生，我希望查看本人申报状态、处理理由和已提交材料，以便了解认定进度并更正问题。
38. **US-038** 作为管理员，我希望同时查看事实、证明、评分归属和已有认定，以便作出有依据的审核决定。
39. **US-039** 作为管理员，我希望通过或不予认定的决定保留操作人和理由，以便追溯分数来源与后续更正。
40. **US-040** 作为学生，我希望个人申报对应已有活动参与时关联同一事实，以便获得正确记录且不会重复计分。
41. **US-041** 作为管理员，我希望批量处理明确选中的待审核记录并查看每条处理结果，以便提高效率且不把失败操作显示为成功。
42. **US-042** 作为学生和管理员，我希望未通过的记录保留处理状态但不计分，以便待审核或无效事实不会提前形成正式成绩。

### 成绩与扣分输入

43. **US-043** 作为管理员，我希望手工录入或通过 CSV、XLSX 导入学业和体育等成绩，以便将外部成绩纳入同一学期方案。
44. **US-044** 作为管理员，我希望导入预览区分新增、相同值与已有成绩变更，以便确认覆盖行为且不把成绩重复累加。
45. **US-045** 作为管理员，我希望超出有效范围、缺失必填项或无法识别学生的行被明确拒绝，以便封顶设置不会掩盖无效成绩。
46. **US-046** 作为学生，我希望必需成绩缺失时显示待录入和不完整状态，以便不把未知成绩误认为零分。
47. **US-047** 作为管理员，我希望登记扣分额、节点和理由并保留变更记录，以便纪律扣分独立可追溯。
48. **US-048** 作为导入操作者，我希望重复提交、网络重试或过期预览不会重复写入或覆盖新数据，以便安全完成批量操作。

### 计算、明细与异议

49. **US-049** 作为学生，我希望查看综合成绩和各评分模块明细，以便核对已认定输入与最终结果。
50. **US-050** 作为学生，我希望分清原始分、封顶前后、比例贡献、折算和扣分，以便理解活动原始加分如何影响综合总分。
51. **US-051** 作为学生，我希望达到上限后仍能看到参与记录，以便活动事实不会因不再增加成绩而丢失。
52. **US-052** 作为管理员，我希望每名学生都由同一通用计算功能处理，以便不同数据行和不同学校配置遵循一致机制。
53. **US-053** 作为管理员，我希望不完整结果无法混入最终排名，以便最终成绩只比较具备必需输入的学生。
54. **US-054** 作为学生，我希望只查看本人记录、本人可引用的证明和本人名次，以便其他学生的个人材料受到保护。
55. **US-055** 作为学生，我希望在成绩核对期间确认结果或提交异议，以便纠正遗漏参与、错误输入或认定问题。
56. **US-056** 作为管理员，我希望查看异议依据并记录处理结论，以便完成纠错并反馈给学生。
57. **US-057** 作为学生，我希望成绩改变后能识别先前确认所对应的结果，以便旧确认不会冒充对新结果的认可。

### 发布、排名、结算与更正

58. **US-058** 作为管理员，我希望明确切换学期的配置、进行、核对和锁定阶段，以便各类操作遵循学期状态。
59. **US-059** 作为管理员，我希望发布成绩供学生核对，以便在结算前完成结果检查与异议处理。
60. **US-060** 作为管理员，我希望在必需成绩缺失或待处理事项尚未解决时收到结算阻断原因，以便不把未完成结果锁定为最终结果。
61. **US-061** 作为管理员，我希望按学院、专业或班级筛选排名，以便在同一学期方案下比较相应学生群体。
62. **US-062** 作为学生和管理员，我希望同分按1、2、2、4并列排名，以便清楚理解名次规则。
63. **US-063** 作为管理员，我希望锁定时保存配置和结果快照，以便以后仍能还原当时的结算口径。
64. **US-064** 作为管理员，我希望锁定后的普通修改在服务端被阻止，以便页面以外的请求也无法悄悄改变最终成绩。
65. **US-065** 作为管理员，我希望填写理由后重新开放错误学期并修正、重算、重新发布锁定，以便以简单而可追溯的方式完成更正。
66. **US-066** 作为管理员，我希望保留过去的锁定结果和修改日志，以便对照更正前后发生了什么。
67. **US-067** 作为管理员，我希望导出 Excel 成绩、分项和排名，以便提交学校需要的汇总成果。
68. **US-068** 作为管理员，我希望学校导出列读取既有节点结果与展示系数，以便小计和展示分不会反向重复参与计分。
69. **US-069** 作为导出操作者，我希望导出记录明确学期、范围与结果状态，并安全处理文本字段，以便文件与页面一致且不把用户文本作为公式执行。

74. **US-074** 作为部署维护者，我希望在隔离环境实际恢复备份并核对记录、材料和结算结果，以便确认恢复流程可用。

76. **US-076** 作为使用者，我希望未授权请求、非法参数和附件访问受到服务端限制，以便通过页面以外的请求也无法越权。
77. **US-077** 作为使用者，我希望失败操作说明原因且不留下部分计分结果，以便修正问题后安全重试。
78. **US-078** 作为使用者，我希望页面有清晰的加载、空数据、错误和提交完成提示，以便准确判断业务处理状态。
79. **US-079** 作为维护开发者，我希望通过稳定业务入口和评分输入输出运行自动化测试，以便修改内部实现时仍能验证真实行为。
80. **US-080** 作为维护开发者，我希望类型检查、代码检查、关键测试与生产构建有可复现命令，以便后续修改保持可交付状态。
81. **US-081** 作为交付验收者，我希望看到实际测试环境、数据规模、结果与适用边界，以便判断系统在什么条件下完成了验证。
82. **US-082** 作为演示维护者，我希望使用虚拟演示数据和完整操作说明走通关键流程，以便演示生产版本而无需泄露真实学生材料。

## Implementation Decisions

### D-01 交付范围与技术基线

1. 一套部署先服务一所学校。每学期全体学生使用一套生效方案，排名筛选不改变计分口径。独立部署的其他学校可配置自己的模块、参数和项目。
2. 三个角色为学生、活动发布者和管理员；审核与异议处理均由管理员承担，可存在多个管理员账号。
3. TypeScript＋Next.js 单项目承载页面与服务端业务，使用 shadcn/ui 组件及后台布局。目标主版本为 Node 24 LTS、Next.js 16 和 React 19。
4. PostgreSQL 保存业务数据，Prisma ORM 7 管理数据库访问与迁移；认证使用 NextAuth.js v4 Credentials 和应用维护的用户数据。声明依赖相容性已有官方资料依据，具体补丁版本在实际构建和关键流程验证后固定，并保留依赖锁定信息。
5. Docker Compose 运行生产应用与数据库，证明文件使用独立持久存储。首版按生产质量交付，在本机／局域网部署演示。

### D-02 模块职责与公开业务契约

| 模块 | 对外职责与结果 |
| --- | --- |
| 身份与档案 | 身份验证、账号生命周期、角色、学生标识与组织归属；返回可授权使用的当前身份 |
| 学期与方案 | 学期阶段、评分树校验、试算、变更差异和统一生效；返回配置状态与修订标识 |
| 活动与认定 | 活动、加分项目、名单、个人申报与审核；返回同一事实的当前有效认定 |
| 成绩与扣分 | 成绩输入、导入预览及提交、节点扣分与理由；返回有效原始输入与逐行处理结果 |
| 证明文件 | 受控上传、关联、读取与引用保护；通过文件标识和业务授权提供材料 |
| 通用评分 | 校验后的评分树、原始输入与显示精度转换为完整节点明细、完整性状态和总分 |
| 核对与结算 | 异议、确认、发布、排名、锁定、更正及导出；返回与结果口径一致的成果 |
| 审计与运行 | 操作记录、迁移、初始化、健康检查、持久化和备份恢复 |

页面与 HTTP 调用共同使用经过授权和校验的业务操作。普通表单写入可用 Server Actions，文件与导出可用 Route Handlers；二者都不能绕过同一业务规则。此处固定行为契约，不把测试绑定到内部函数名称或文件布局。

### D-03 数据关系与业务不变量

1. 用户保存唯一登录标识、密码哈希、角色、停用状态、首次改密要求和会话有效性信息。学生档案绑定唯一学号及学院、专业、班级；学号按字符串处理，保留前导零。
2. 学期关联统一的生效方案。评分模块归属方案，通过父子关系、排序和节点配置形成树；原始输入关联学生、学期与最底层模块。每名学生在同一学期的同一成绩输入模块只有一个当前有效成绩值，变更历史可追溯。
3. 活动和个人加分项目绑定最底层模块与统一原始分。活动参与关联活动和学生，数据库约束保证同一活动、同一学生只有一条有效参与事实；重复来源记录可引用该事实。
4. 个人申报、组织提交与审核决定保留来源及历史。一个事实可对应多份证据或提交来源，但最多贡献一次当前有效加分。文件哈希或文件名不能替代事实身份。
5. 证明文件保存受控标识、类型、大小和业务引用；共享证明被多名参与者引用时，每名学生的查看权限仍来自其本人有效关联。
6. 扣分记录关联学生、学期、目标节点、正数扣分额、系数及理由。核对与异议关联所针对的结果，结算快照保存当时配置、输入依据、结果、排名范围信息及必要展示数据。
7. 发布与计算使用修订标识防止过期提交、混合读取和并发覆盖。这些标识用于一致性控制，不能发展为同时对不同学生生效的多套规则或复杂规则版本迁移功能。

### D-04 账号、会话与权限

1. 首个管理员通过受控初始化流程建立；业务账号由管理员创建或批量导入。学生用学号登录，其他角色使用管理员分配的唯一登录名。首版无需开放学生自助注册或要求学生真实邮箱。
2. 初始及重置密码安全生成，经受控方式交给授权管理员，仅在必要时展示。持久化只保存成熟密码哈希；日志、演示数据及版本控制材料不包含实际密码或密钥。
3. 首次登录和管理员重置后强制改密。在完成改密前，仅允许改密及退出等必要操作。管理员重置、用户改密、账号停用和相关权限变化后，后续受保护操作检查当前账号及会话有效性；旧令牌不能继续沿用已失效权限。
4. Credentials 处理凭据验证和 JWT 会话；应用负责用户存储、密码哈希、首次改密、会话失效和业务权限。不能只依靠页面隐藏或令牌中长期缓存的角色。
5. 学生只能读取本人档案、申报、参与、成绩、异议、核对及授权证明；活动发布者只能管理本人活动及相应名单与证据；管理员按管理职责访问。每个业务操作和文件读取都验证身份、角色、数据归属和学期状态。
6. 登录与密码重置执行频率限制，反馈避免泄露不必要的账号信息；写入遵循框架的请求来源与跨站请求保护机制。部署配置处理代理、HTTPS、会话 Cookie 和密钥，生产构建不等于已完成传输安全配置。

### D-05 学期阶段与结果一致性

| 阶段 | 允许的主要业务 |
| --- | --- |
| 配置 | 建立与校验方案，设置来源、输入范围及试算，准备学生名单 |
| 进行 | 发布活动、申报、导入、审核和维护成绩，查看当前计算结果 |
| 核对 | 发布结果供学生确认与提出异议，管理员处理异议和必要更正 |
| 锁定 | 读取最终结果与快照、查看记录和导出；普通业务修改被阻止 |

1. 阶段转换由管理员执行并记录。方案未校验通过不能开启使用；核对阶段需要恢复普通申报、导入或大规模配置调整时，管理员先明确重新开放。锁定后更正必须填写理由，重新开放后按统一流程修正、重算、发布和再次锁定。
2. 待审核记录、未解决异议和必需成绩缺失均须在锁定前处理，阻断信息能定位学生或事项。不能通过把缺失改成零、把未确认改成已确认或把待处理事项隐藏来结算。
3. 学生核对记录绑定当时结果；相关结果变化后旧确认仍可追溯，但不能代表对新结果的确认。未点击确认始终显示未确认，不伪造状态。
4. 输入变化、认定变化及方案调整使相关结果重算。全学期配置变化在统一重算完成后生效；失败时保留上次完整有效结果并说明原因，不能让部分学生使用新规则、部分学生使用旧规则。
5. 发布、排名、页面明细与导出读取同一结果口径；重算中、不完整和已锁定状态明确区分。管理员对已生效业务数据的更正保留修改前后、操作人、时间和理由。

### D-06 评分树配置与结构校验

1. 模块使用统一节点模型，通过父子关系表达实际层级，不按两层、三层或五层写死业务限制。计算采用迭代后序处理，管理界面按需展开并显示路径；实际可承载规模以验证结果说明。
2. 有下级的节点为汇总模块，仅接收直接下级计算结果；没有下级的节点为最底层模块，选择活动累加或成绩录入／导入之一。汇总模块不得再直接接收额外原始分。
3. 汇总方式为直接累加或比例汇总。比例只在父模块采用比例汇总时生效，直接下级的比例合计必须为100%；直接累加没有这一约束。
4. 任意节点可独立配置封顶分；满分折算默认关闭，启用时原始满分必须大于零，目标满分和其他数值需通过合法性校验。最低分可空缺，封顶与下限、折算配置之间不能互相矛盾。
5. 最底层模块明确输入来源、有效范围和缺失政策。活动累加没有有效认定时按零处理；必需成绩缺失时保留待录入状态，不能作为完整结果结算。
6. 校验覆盖唯一节点标识、方案归属、单一根关系、无循环、无游离或重复挂接、有效父子关系、非空汇总、输入来源和所有数值参数。节点不能移到自身或后代之下，不能跨方案挂接。
7. 只有没有业务引用的模块可直接删除。已有数据的最底层模块继续拆分时，先把记录迁移到明确的新下级节点；来源类型不兼容或迁移不完整时阻止保存。
8. 调整生效配置前给出变更摘要、受影响人数和示例成绩差异。保存校验通过并经管理员确认后，在同一学期统一生效；记录修订依据和操作日志。

### D-07 独立评分输入输出与计算顺序

1. **输入契约**：一套已校验的评分树、每个最底层模块的当前有效原始输入、各目标节点的扣分输入及显示精度。节点包含汇总方式、比例、可选上限、可选折算、可选下限和缺失政策。
2. **输出契约**：总分、完整性状态、缺失必需输入清单及逐节点明细。明细包括原始汇总、封顶前后、折算参数与结果、节点扣分、下限应用前后和传递给父级的结果。
3. **处理顺序**：最底层读取有效原始分；汇总节点先按直接累加或比例汇总取得数值，随后依次执行本节点封顶、明确启用的满分折算、本节点扣分、明确配置的最低分，最后把本节点结果交给父级。
4. **扣分契约**：管理员录入正数扣分额，乘扣分项目系数后在目标节点扣减。目标位置和系数来自配置，不因节点名称或学校名称选择特殊计算分支。
5. **精度契约**：输入和配置使用确定的十进制表示与运算，避免普通二进制浮点误差改变分数或名次。中间计算不按展示两位小数提前舍入；展示总分及分项采用两位小数、四舍五入口径，最终页面和导出一致。输入精度、可接受范围与计算精度在实现中明确并验证，不能静默截断原始数据。
6. **贡献解释**：父级的上限、下限或扣分可能影响子项对总分的实际增量。界面区分按比例形成的节点贡献与某条活动实际增加的总分；需要展示活动实际增量时，通过相同规则的前后结果比较得出，不能仅把原始分乘比例后宣称已实际增加。
7. **职责边界**：评分功能不处理登录、审核决定、数据库读写、Excel 解析和文件存储，不识别具体学校名称。业务层先整理有效输入，再调用同一评分契约；模板和导出展示列均为数据。
8. **失败契约**：非法结构、非法参数或无法解释的输入明确报错，定位对应模块；必需输入缺失以不完整结果返回，不以猜测值补齐。失败计算不得替换上次有效发布结果。

### D-08 学校首版模板与原表适配

| 模块 | 原始汇总与上限 | 进入父级的方式 |
| --- | --- | --- |
| 红色文化引领工程 | 四个子项直接相加，封顶100 | 乘10%进入基础性素质 |
| 学业成绩 | 成绩输入，必需 | 乘80%进入基础性素质 |
| 体育素质 | 成绩输入，必需 | 乘10%进入基础性素质 |
| 基础性素质 | 上述三项比例汇总 | 乘80%进入总评 |
| 志愿服务实践工程 | 三个子项直接相加，封顶30 | 原分进入发展性素质 |
| 人文素质提升工程 | 三个子项直接相加，封顶30 | 原分进入发展性素质 |
| 卓越工匠培养工程 | 三个子项直接相加，封顶40 | 原分进入发展性素质 |
| 发展性素质 | 三个工程封顶后的原分直接相加 | 乘20%进入总评 |
| 法制与校规校纪扣分 | 管理员登记扣分额 | 在加权总评后按100%扣减 |

1. 红色文化四子项为思想引领活动、培训学习经历、学生入党和道德品质；志愿工程为社会实践、劳动实践和社会公益；人文工程为基础素养、文体素养和心理素养；工匠工程为职业素养、双创精神和管理能力。
2. 30、30、40是节点原始分上限，不是强制内部权重。本校模板不启用百分制归一化，不默认添加总分最低零分。
3. 原表的输入列、小计列、比例展示列及最终列作为模板映射数据保留。计算只读取有效输入和直接子模块结果；小计与展示用比例分不再次作为加分输入。
4. 适配目标是覆盖该表表达的学校评分机制。统一补齐漏小计、避免部分行重复合计，并按表头执行红色文化100分上限；不逐格复刻原表的错误公式行为。
5. 汇总表没有提供具体活动每次加分、证书分值和单次违纪扣分，这些值由管理员按学校制度配置。本规格不编造学校已经批准的制度。

### D-09 活动、加分项目与认定

1. 活动展示包含名称、组织者、时间、内容和参与要求。活动展示不产生报名、报名人数或候选名额等业务。
2. 发布者维护本人活动并提出评分归属与统一原始分；管理员确认后，该值适用于全部被认定参与者。客户端提交的逐人自定分值不能决定正式得分。
3. 管理员创建个人加分项目，项目关联一个最底层模块和统一分值；不同分值使用不同项目表达，不做复杂奖项身份和分值矩阵。
4. 个人申报、组织名单及其材料从待审核进入有效或无效认定；补充材料、重新提交或更正时保留来源和处理记录。任何未通过审核的来源都不产生有效分数。
5. 管理员的认定与更正记录操作人、时间和必要理由；不予认定和会改变既有有效结果的决定必须说明原因。批量处理返回逐条结果，不能用一个成功提示掩盖失败记录。
6. 组织提交和个人申报属于同一活动时，关联同一学生参与事实；可补充证据，不能形成第二次加分。无法确定是否同一事实时呈现冲突供管理员核对，不能凭重复附件直接认定违规或无条件新增分数。
7. 活动或项目分值更正按当前学期状态授权，展示影响范围，确认后统一作用于相关有效认定并重算；锁定学期先走重新开放与更正流程。

### D-10 名单、成绩与账号导入

1. 首版处理 CSV 与 XLSX。流程为选择目标学期和业务对象、上传、对应字段、服务端预览、显示逐行错误与重复结果、确认提交、查看导入结果。Excel 中的已计算小计不能自动当成原始输入。
2. 服务端保留学号字符串并校验真实学生身份与目标范围；不能只按姓名匹配。重复行、未知学号、缺少必填字段、非法数字和范围错误都给出定位与原因。
3. 活动名单导入只建立或引用参与事实，不直接信任文件携带的任意分值。相同活动与学生已有记录时合并来源或提示已存在，不重复加分。
4. 成绩导入采用同学期、同学生、同成绩输入模块的唯一当前值。相同值重复提交不累加；修改已有值先展示差异并确认覆盖，保留更正记录。
5. 账号导入验证唯一学号／登录标识和组织字段；已存在账号不再次生成一个重复用户，也不因重复导入而静默重置密码。
6. 预览和提交使用同一服务端校验规则。提交时重新检查权限、目标对象、修订状态和学期锁定状态；过期预览提示重新生成，不能覆盖期间发生的更新。
7. 批次存在校验错误时阻止该批正式写入，修正后重新预览；预览明确区分错误与可安全跳过的重复行。确认后的批次使用事务执行，失败不留下半批账号、半批成绩或部分有效加分。
8. 重复点击、请求重试和并发提交通过批次标识、唯一约束及事务保护获得一致结果。导入日志记录操作者、目标、成功／跳过／错误数量和失败原因。

### D-11 证明文件、输入与输出安全

1. 证明上传在服务端检查允许类型、实际可识别格式、大小和文件数量。允许类型和限制形成明确配置及页面说明，不把任意客户端声明当作可信文件类型。
2. 使用受控文件标识生成存储位置，原始文件名只作显示元数据。上传材料不能覆盖应用文件、指定任意路径或被当作可执行页面服务。
3. 证明文件保存于持久化受控存储，通过业务鉴权读取或下载；不能依靠可猜测静态链接控制访问。学生访问本人记录的材料，发布者访问本人活动相关材料，管理员按审核职责访问。
4. 共享证明保存一份或可复用存储，多个业务引用独立保存。移除某条关联不能删除其他有效记录正在使用的文件；清理失败上传或无引用临时文件不得破坏有效证明。
5. 用户输入在请求与数据库边界验证；导出文本按文本处理，防止以公式前缀开头的姓名、活动名等被电子表格软件执行。上传解析器与导出工具使用维护中的依赖并锁定兼容版本。
6. 错误响应给出可处理的信息，日志保留可追踪标识及必要上下文，控制密码、会话令牌和个人证明内容的泄露。

### D-12 学生核对、异议、排名与导出

1. 学生看到本人活动及申报记录、原始输入、计算路径、扣分和结果状态；共享证明授权不扩展为查看同批其他人的个人记录。
2. 核对阶段允许对具体记录或结果提出异议，管理员记录处理结论及必要更正。处理失败或仍在待办中的异议不能伪装成已解决。
3. 排名仅比较同一学期、同一结果口径、所选学院／专业／班级范围中的完整学生结果；不完整结果单列。学生只读取本人名次与相应范围信息，管理员可读取管理范围名单。
4. 最终对外成绩统一按两位小数和四舍五入形成排序比较值，相同对外成绩并列，名次为1、2、2、4，避免显示同分却名次不同。内部计算明细继续保留计算精度，不提前逐层舍入。
5. Excel 导出包含学期、筛选范围、结果状态、学生标识、分项、扣分、总分与名次。未锁定结果明确标注；锁定后的正式导出读取对应结算快照，并与页面展示一致。
6. 学校格式导出从输入与节点结果映射小计和展示列。展示系数只生成输出列，不能反向成为重复计分来源；不要求复刻源文件的全部版式与错误公式。

### D-13 结算快照、锁定与事务

1. 锁定前检查必需输入、待审核记录、待处理异议及重算状态。锁定与相应快照创建作为一致操作完成；失败时学期保持可识别的原状态，不能显示已锁定却缺少快照。
2. 快照保存当时方案、学生范围、有效输入依据、节点明细、最终成绩及排名信息，确保后续配置或档案变化不改写旧锁定结果。
3. 学期锁定保护放在服务端写入边界并与事务结合；已打开的页面、未过期会话或已生成的导入预览都不能绕过锁定。
4. 更正需要管理员提供理由，明确重新开放、修正、统一重算、重新发布及锁定；旧快照继续可追溯。首版不增加独立复核角色或多层更正审批。
5. 审核、更正、导入与结算对同一业务数据的并发操作检查当前状态，使用唯一约束、事务和修订检查防止重复计分与丢失更新。操作结果与审计记录保持可对照关系。

### D-14 部署、数据生命周期与运行验证

1. 交付 Docker Compose 所需的生产构建、运行配置与操作说明；提供环境变量示例，实际密码、会话密钥和数据库凭据由部署环境注入。
2. 数据库迁移与首个管理员初始化可在干净环境按说明执行，并能判断成功或失败。迁移失败阻止依赖新结构的应用被报告为可用，提供诊断和恢复步骤。
3. 应用与数据库有可判断的健康状态、启动顺序与重启行为；生产运行使用构建产物，演示数据单独初始化且不把真实学生材料公开分发。
4. 数据库与证明文件分别使用持久卷或明确持久目录，容器更新、重建和服务重启保留有效业务数据；常规升级步骤不执行清空数据操作。
5. 备份流程覆盖数据库、证明文件及引用一致性。首版可以在维护窗口暂停业务写入后备份，在全新隔离环境恢复并核对账号、材料与锁定结果；记录备份版本和恢复步骤。
6. 提供从配置、迁移、初始化、启动、备份到恢复的完整说明。反向代理、TLS、可信来源与 Cookie 配置根据访问环境验证；首次实际公网部署仍需按部署条件验收，不能仅凭本地演示宣称已完成公网容量或安全验证。
7. 类型检查、代码检查、相关测试和生产构建提供可复现命令，并接入持续检查。测试结果记录运行环境、数据规模与限制，不承诺未经验证的并发人数或真正无限层级。

## Testing Decisions

### T-01 已确认的测试边界

用户已确认以下方案，测试行为而非内部函数调用次数或文件组织：

1. **主要边界为完整业务操作**：以真实登录身份执行页面与接口共用的公开业务入口，连接独立 PostgreSQL 测试库和隔离附件存储，断言返回结果及用户可观察的持久状态。覆盖权限、状态变化、重复提交、事务失败、会话变化和锁定。
2. **独立评分边界**：直接测试通用评分公开输入输出。该功能已明确独立复用，因此保留这一稳定边界；预期值来自人工可核对样例、独立控制公式与另一套配置。
3. **关键浏览器流程**：用少量完整用户流程验证页面、表单、鉴权、下载和业务操作接线；评分组合和所有非法参数主要在前两层验证，避免用大量脆弱页面用例重复穷举。
4. **生产运行边界**：在真实生产构建及隔离环境中验证迁移、启动、重启持久性和备份恢复。

### T-02 评分先例与回归样例

现有 Python 配置验证已通过1068项检查，包括1000组独立控制公式对照、51行当前原表输入对账、固定边界、另一配置、导出映射和1500层树。原表51行只有1行非零输入，对账不能单独证明边界正确；这些是评分模型先例，不是正式应用测试通过的证据。正式实现应复用行为样例与独立控制口径，不照抄 Python 内部结构作为测试目标。

| 样例 | 已认定原始输入与配置 | 预期总分 |
| --- | --- | --- |
| 零分 | 学业和体育明确录入0，其余无活动、无扣分 | 0.00 |
| 单项志愿10分 | 学业体育为0，社会实践10，其余为0 | 2.00 |

### T-04 具体测试方法

1. **评分契约**：固定边界、独立随机对照和另一套模板；覆盖权重合计、零及满分、上限与折算独立性、扣分顺序、可选下限、深层树、非法结构、缺失输入和舍入边界。深度样例证明相应算法可处理该样本，不变成界面无限容量承诺。
2. **业务集成**：真实测试数据库执行账号、导入、审核、方案变更、异议、发布、锁定与更正，测试唯一约束、事务回滚、状态检查和并发冲突。业务数据读取与写入不依赖把数据库操作全部替换成模拟返回值。
3. **认证与请求权限**：从实际登录入口验证 Credentials、Cookie 与会话读取；通过页面以外的受保护请求验证访问限制、首次改密拦截、旧会话失效、角色变化和数据归属。
4. **文件与导出**：使用虚拟学生及模拟附件核对共享引用、下载授权、格式与大小校验、存储路径限制、失败上传清理和公式文本处理；测试产物使用隔离目录。
5. **浏览器验收**：至少覆盖首次登录改密；管理员配置与试算；发布者名单加共享证明、管理员审核、学生查看；学生个人申报与异议；管理员发布、锁定、更正和导出。关键失败场景验证提示与真实状态一致。
6. **运行验收**：在生产构建中执行主要链路，验证 PostgreSQL 迁移、容器健康、重启保留、备份与隔离恢复。类型、代码检查和相关测试通过后再记录构建成功，不能用静态检查代替运行证据。
7. **负载与容量说明**：使用可复现的虚拟名单、记录和模块树，记录环境、数据量、并发操作及结果；超过可处理限制时给出明确错误或进度。真实容量结论基于实际测试数据，不在规格阶段虚构通过人数。

## Out of Scope

1. 多校入驻平台、跨校租户运营、同一学期不同学生匹配不同方案。
2. 在线活动报名、名额分配、签到或教务平台自动同步。
3. 独立审核员、复核员、学院管理员、可信组织免审及多层更正审批。
4. 任意公式或代码编辑器、通用条件编排、复杂奖项身份分值矩阵、复杂奖项互斥及规则版本迁移。
5. 同一活动对不同参与者任意配置不同原始分；需要不同分值的个人项目由管理员建立不同项目表达。
6. 学生自助注册、邮件或短信找回、第三方单点登录、外部付费服务作为运行必需条件。
7. 微服务拆分、多节点分布式运行、高可用集群、无需维护窗口的在线一致备份与零停机升级。
8. 原始旧式 XLS 文件的在线解析、源工作簿逐格版式复刻，以及复制漏公式、重复合计等原表缺陷。首版用户导入格式为 CSV 和 XLSX。
9. 在没有测量证据时承诺无限层级、固定并发容量或已经满足任何特定学校正式验收标准。
